# Kysely vs Prisma

Kysely keeps joined aggregates, per-author thresholds, and pagination in one composable SQL query with inferred results.

Kysely is a SQL query builder. Prisma 7 is an ORM; see [SQL query builder vs ORM](/docs/comparisons/query-builder-vs-orm). The leaderboard below starts with a global minimum, then changes to each author's own target.

Checked with **Prisma Client 7.10.1** and **Kysely 0.29.7** against PostgreSQL, including the pagination case. [Reproduce the checks](https://github.com/kysely-org/kysely/tree/master/site/scripts/comparison-checks/postgres).

Prisma 8 introduces a [SQL query builder](https://docs.prisma.io/docs/orm/v8/reference/sql-query-builder). We'll assess it separately as it takes shape; it's too early to pass judgment on it here. This comparison covers Prisma 7.

## An activity leaderboard, with the same result

Return the top 20 active authors in an organization by published-article count since a cutoff, above a configurable minimum. Include names; break ties by author ID.

Assume configured `prisma`/`db` clients and one author per article.

<details>
<summary>Schema and database types used in this example</summary>

Prisma maps these model fields to the PostgreSQL tables:

```text
model Author {
  id Int @id
  name String
  organizationId Int @map("organization_id")
  active Boolean
  articleTarget Int @map("article_target")
  articles Article[]
  @@map("author")
}

model Article {
  id Int @id
  authorId Int @map("author_id")
  publishedAt DateTime? @map("published_at") @db.Timestamptz(3)
  author Author @relation(fields: [authorId], references: [id])
  @@map("article")
}
```

Kysely describes the same tables through types:

```ts
interface Database {
  author: {
    id: number
    name: string
    organization_id: number
    active: boolean
    article_target: number
  }
  article: { id: number; author_id: number; published_at: Date | null }
}
```

</details>

### Kysely: join, aggregate, and select in one statement

Build the shared activity query:

```ts
function authorActivity(organizationId: number, since: Date) {
  return db
    .selectFrom('author')
    .innerJoin('article', 'article.author_id', 'author.id')
    .select(['author.id as author_id', 'author.name'])
    .select((eb) =>
      eb.cast<number>(eb.fn.count('article.id'), 'integer').as('article_count'),
    )
    .where('author.organization_id', '=', organizationId)
    .where('author.active', '=', true)
    .where('article.published_at', '>=', since)
    .groupBy(['author.id', 'author.name', 'author.article_target'])
}
```

Then add the threshold and page:

```ts
function kyselyLeaderboard(options: {
  organizationId: number
  since: Date
  minArticles: number
}) {
  return authorActivity(options.organizationId, options.since)
    .having((eb) => eb.fn.count('article.id'), '>=', options.minArticles)
    .orderBy('article_count', 'desc')
    .orderBy('author.id')
    .limit(20)
    .execute()
}
```

One SQL statement; inferred result: `{ author_id: number; name: string; article_count: number }[]`. The integer cast makes the count a JavaScript number.

### Prisma Client 7: group, fetch names, assemble the result

Prisma [`groupBy()`](https://www.prisma.io/docs/orm/v7/prisma-client/queries/aggregation-grouping-summarizing) cannot select related author names. This model-API version groups articles, fetches names, and merges:

<details>
<summary>The Prisma Client 7 implementation</summary>

```ts
async function prismaLeaderboard(options: {
  organizationId: number
  since: Date
  minArticles: number
}) {
  const groups = await prisma.article.groupBy({
    by: ['authorId'],
    where: {
      publishedAt: { gte: options.since },
      author: { organizationId: options.organizationId, active: true },
    },
    _count: { id: true },
    having: { id: { _count: { gte: options.minArticles } } },
    orderBy: [{ _count: { id: 'desc' } }, { authorId: 'asc' }],
    take: 20,
  })

  const authors = await prisma.author.findMany({
    where: { id: { in: groups.map((group) => group.authorId) } },
    select: { id: true, name: true },
  })
  const names = new Map(authors.map((author) => [author.id, author.name]))

  return groups.map((group) => ({
    author_id: group.authorId,
    name: names.get(group.authorId)!,
    article_count: group._count.id,
  }))
}
```

</details>

Two reads and a JavaScript merge. Use suitable transaction isolation for one snapshot. TypedSQL and `$queryRaw` offer SQL alternatives.

Prisma also supports [filtered relation counts](https://www.prisma.io/docs/orm/v7/prisma-client/queries/aggregation-grouping-summarizing#filter-the-relation-count) alongside author names. Its relation-count ordering takes a sort direction, without a count filter; relation-list filters also lack an aggregate-count threshold. Selecting a filtered `_count` alone does not express this leaderboard.

## The requirement changes: each author has a target

Replace the global minimum with `author.article_target`, filtering before ranking and pagination:

Reuse `authorActivity` with a column comparison:

```ts
function authorsMeetingTheirTarget(organizationId: number, since: Date) {
  return authorActivity(organizationId, since)
    .having((eb) =>
      eb(eb.fn.count('article.id'), '>=', eb.ref('author.article_target')),
    )
    .orderBy('article_count', 'desc')
    .orderBy('author.id')
    .limit(20)
    .execute()
}
```

The rule stays in SQL before `LIMIT`; the inferred result is unchanged.

Prisma Client 7 rejects the related-model reference:

```ts
prisma.article.groupBy({
  by: ['authorId'],
  having: {
    id: {
      _count: {
        gte: prisma.author.fields.articleTarget, // TypeScript error
      },
    },
  },
})
```

Prisma [restricts field references to one model](https://www.prisma.io/docs/orm/v7/reference/prisma-client-reference#fields-must-be-in-the-same-model). Fetch aggregates and targets and filter before pagination in application code, or use SQL.

Filtering only the first 20 global rows can miss qualifying authors below that page.

## What the change costs

| Requirement                                          | Kysely                                                           | Prisma Client 7 model API                                                                                    |
| ---------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Return grouped activity with author names            | One joined aggregate statement.                                  | Group Article records, fetch names, and merge, or choose a different query workflow.                         |
| Compare the aggregate with a related author's target | Replace the `HAVING` expression with a checked column reference. | Cross-model field references are not supported in the aggregate filter.                                      |
| Filter before ranking and pagination                 | The rule stays inside the SQL statement before `LIMIT`.          | Apply the rule before pagination in application code, or use SQL.                                            |
| Keep the result typed as the query changes           | The builder infers selected names and aggregates.                | Model APIs are typed; raw `$queryRaw<T>` uses an asserted result type, while TypedSQL generates query types. |

Prisma 7 [raw queries](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/raw-queries) bind values and compose `Prisma.sql`/`Prisma.join` fragments. TypedSQL infers SQL-file inputs and outputs.

Kysely can embed [one SQL expression](https://kysely-org.github.io/kysely-apidoc/interfaces/Sql.html) while the surrounding builder stays checked. Prisma 7 model `select` cannot take an arbitrary `Prisma.sql` field; it needs a SQL query workflow.

## Agent experience

Kysely's [installed method docs and checked examples](https://github.com/kysely-org/kysely/blob/v0.29.7/src/query-builder/select-query-builder.ts) guide agents through its API. Prisma 7 supplies model types and separately installed [agent skills](https://www.prisma.io/docs/ai/tools/skills).

## Try Kysely alongside an existing application

Start with a report that needs joined aggregates or SQL fragments. Generate Kysely types with [prisma-kysely](https://github.com/valtyr/prisma-kysely):

1. Keep Prisma's relation reads, nested writes, schema, and migrations.
2. Add its generator and run `prisma generate` after schema changes.
3. [Configure a dialect](/docs/getting-started) and move one query.
4. Compare rows, ordering, empty results, and pagination; inspect `.compile()` before moving more code.

Budget connections for both clients; they do not automatically share transactions.
