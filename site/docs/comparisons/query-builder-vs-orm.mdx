# SQL query builder vs ORM

A SQL query builder exposes SQL's vocabulary and structure through a programmatic API. You compose selections, joins, inserts, updates, and deletes using tables, columns, and expressions. The builder generates the SQL and binds parameters.

An **object–relational mapper (ORM)** maps application models, their properties, and relationships to relational tables, columns, and keys. Its model API typically uses application-oriented vocabulary such as `findMany`, `save`, `include`, and `connect` to load and persist models, abstracting the SQL statements needed to perform the work.

Most modern products marketed as ORMs are broader **data frameworks**. They pair model mapping and persistence with schema definitions, migrations, and development tooling. Some also include code generation or a SQL query builder. Here, **ORM** describes the mapping/persistence layer; **data framework** describes the larger stack.

**Returning plain JavaScript objects does not make a library an ORM.** Even database drivers such as [node-postgres return arrays of plain row objects](https://node-postgres.com/features/queries#row-mode).

A data framework supplies **model, relationship, and persistence conventions** for part of your data-access layer. A query builder leaves more of those decisions to your application.

<SqlAbstractionSpectrum />

The builder groups summarize how directly their core query APIs expose SQL constructs. Knex supports SQL clauses, joins, and recursive CTEs; its application-oriented placement reflects higher-level, cross-dialect operations. For example, [`.onConflict().merge()`](https://knexjs.org/guide/query-builder.html#merge) generates PostgreSQL's `ON CONFLICT ... DO UPDATE` or MySQL's `ON DUPLICATE KEY UPDATE`, which ignores the specified conflict target. [`.jsonExtract()`](https://knexjs.org/guide/query-builder.html#jsonextract) similarly chooses `jsonb_path_query` on PostgreSQL and `json_extract` with `json_unquote` on MySQL.

For these upsert clauses and JSON function calls, the dedicated built-in route is the cross-dialect abstraction. Choosing different engine-specific SQL requires raw SQL; JSON expressions can use `knex.raw` fragments within an otherwise built query. Kysely exposes the upsert clauses separately and provides a general SQL function API.

These categories overlap. Data frameworks can expose SQL builders directly: [MikroORM 7](https://mikro-orm.io/docs/kysely) and [ZenStack 3](https://zenstack.dev/docs/orm/query-builder) expose Kysely; [Objection.js](https://vincit.github.io/objection.js/api/model/static-methods.html#static-knex) exposes Knex. [TypeORM's builder](https://typeorm.io/docs/query-builder/select-query-builder/) supports SQL clauses and either hydrated entities or plain results. Assess the API you use, alongside the responsibilities of the broader library.

## Reading and persisting models

An ORM's model API can express loading related records, saving changes, or creating a model together with its children. For example, [Prisma's nested writes](https://www.prisma.io/docs/orm/v7/prisma-client/queries/relation-queries#nested-writes) can create an author and their articles in one API call, coordinating the inserts, foreign keys, and transaction. With a query builder, your code specifies the inserts, how the author's key reaches the article rows, and the transaction boundary.

For ordinary query execution, a SQL-first query builder runs the statement you explicitly compose. Loading related data is part of that statement or a separate query your code requests. An ORM model operation may issue multiple statements for nested reads or writes, depending on its loading strategy and persistence behavior. **One API call does not necessarily mean one SQL statement.**

For example, [Prisma 7's relation loading strategies](https://www.prisma.io/docs/orm/v7/prisma-client/queries/relation-queries#relation-load-strategies-preview), behind its `relationJoins` preview flag, offer `join` for a single query and `query` for multiple queries assembled in application code. [MikroORM 7](https://mikro-orm.io/docs/loading-strategies) offers `joined`, `select-in` (separate queries), and `balanced` (joins for to-one relations, separate queries for to-many relations).

Multiple queries can be a deliberate performance choice. The builder's advantage is **predictability and control over the statements executed**. Transactions, connection setup, and extensions can issue additional statements even with a query builder.

Some ORMs also track object identity and changes. [MikroORM's unit of work](https://mikro-orm.io/docs/unit-of-work) tracks managed entities and writes their changes through `flush()`. Identity maps and change tracking are not requirements for an ORM. Prisma's model operations work with plain objects. Model persistence does not require class instances or a unit of work.

## When the result doesn't fit a model

One manifestation of the **object–relational impedance mismatch** occurs when a joined projection, grouped aggregate, or recursive lookup does not fit model navigation. Forcing it through relationships can introduce extra reads, overfetching, or application-side assembly. A builder lets the result shape drive the SQL.

## Production queries need room to tune

Tuning hot queries means inspecting plans against real data and adjusting queries alongside indexes. Direct SQL control shortens the path from a plan to the code that produced it.

When model APIs run out, raw SQL restores control. Binding values does not check references or infer results; analyzers and generators provide separate checks. A capable builder keeps more tuning inside its typed API.

## Example: inherited page permissions

A documentation app stores pages in a tree using an optional `page.parent_id`. A user's permission comes from the nearest explicit rule: on the requested page itself, or on one of its ancestors.

The query must return the rule's page, level, and distance. The number of ancestor steps is not known in advance, so a fixed-depth parent selection does not cover the requirement. This PostgreSQL query uses a recursive CTE, assuming an acyclic tree and at most one rule per page/user:

```sql
with recursive ancestors as (
  select id, parent_id, 0 as depth
  from page
  where id = $1
  union all
  select parent.id, parent.parent_id, ancestors.depth + 1
  from page as parent
  inner join ancestors on ancestors.parent_id = parent.id
)
select ancestors.id as page_id, page_access.level, ancestors.depth
from ancestors
inner join page_access on page_access.page_id = ancestors.id
where page_access.user_id = $2
order by ancestors.depth
limit 1;
```

The database performs traversal, rule lookup, ordering, and limiting in one statement. [Docmost uses recursive ancestors for page restrictions](https://github.com/docmost/docmost/blob/7bef7b1a00d31991f009865ec14c8d06540eb1f0/apps/server/src/database/repos/page/page-permission.repo.ts#L325-L373); this query simplifies that requirement.

The category distinction is how you reach that SQL:

| Approach                             | How the query grows                                                                                                                                 |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| A builder with recursive CTE support | Compose the traversal, joins, projection, and limit through SQL-shaped operations.                                                                  |
| An ORM model API                     | Use a dedicated hierarchy feature, its underlying query builder, or a raw SQL escape hatch. Fetching ancestors in a loop adds database round trips. |

## Type safety depends on the library

A query builder does not automatically check joins, references, expression inputs, or inferred outputs. An ORM's typed models do not guarantee those checks in its SQL API either.

Check what happens when a query changes: remove a join, rename a selected alias, add a nullable expression, or compose a conditional selection. Does the caller's type follow the query, or must an annotation change separately?

## “We'll change databases next year”

**A portable model API does not make database engines drop-in replacements.** Translating supported operations leaves data conversion, constraints, collations, JSON behavior, transactions, indexes, query plans, and data movement to address.

Agents can help rewrite query code; proving equivalent behavior and performance remains the hard work. A hypothetical switch is a weak reason to sacrifice database features and explicit SQL today. If multiple engines are required, test their shared behavior; an ORM alone does not establish that contract.

## Querying a database you don't own

Teams querying shared schemas, customer systems, or read-only views may have no control over schema design or migrations. Library authors face the same boundary when integrating with a consumer's database.

A builder can query existing objects without managing their lifecycle, and an adapter or SDK can accept one configured by its consumer. An ORM's model setup must also fit those ownership and permission constraints.

## Agent experience

Using a coding agent may change the authoring tradeoff. An agent may reduce the effort of composing SQL, while ORM relationship APIs can still save work by coordinating related records, nested writes, and transaction boundaries. Which approach is more productive depends on the task and the tooling.

Explicit SQL structure can help you review and compose queries written by an agent. Weigh that against the persistence logic a model API handles for you. Look for compiler feedback and documentation matching the installed version. Neither an ORM nor a builder proves correctness or performance through types alone.

## When a query builder fits

Choose a builder when you want direct SQL composition, custom result shapes, and room to tune database-specific behavior. Choose model APIs when their relationship operations and nested writes match the work. Both can coexist.

Kysely is one example of a SQL-first builder, with query context checks and inferred results. Its [database types](/docs/generating-types) and [migrations](/docs/migrations) are separate choices. [Get started](/docs/getting-started).
