# SQL query builder vs raw SQL in TypeScript

**Raw SQL in TypeScript is a whole statement written as SQL text: a template beside application code, or a `.sql` file compiled to a typed call.** A SQL query builder composes the statement through an API; Kysely also checks each operation against the database types and infers the result.

**A statement that never changes is raw SQL's best case; every statement that does change is the builder's.** A team that composes raw SQL is already maintaining a query builder. A team that writes typed SQL files has done without composition until the first dynamic query. This page starts with the fixed statement, then follows one asset query through optional filters, a shared count, an export, and nested tags, and tries to break it.

## Raw SQL is a whole statement; a query builder composes one

<SqlQueryWorkflows />

This page covers two kinds of raw SQL. **SQL templates** such as [Postgres.js](https://github.com/porsager/postgres/blob/570be764d96c8c13e6a1a262103bf60974571b67/README.md#building-queries) and [Slonik](https://github.com/gajus/slonik) live beside application code, bind values, and compose through fragments; [SafeQL](https://safeql.dev/) checks the statements it can see whole. **Typed SQL files** are whole statements in `.sql` files that a generator, [PgTyped](https://pgtyped.dev/docs/), [Prisma TypedSQL](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/typedsql), or [sqlc](https://docs.sqlc.dev/), turns into typed calls. Both are compared with Kysely below. Knex and Zapatos sit with the builders in the figure: Knex composes through an API without checking references against a schema, and Zapatos types a set of shortcut helpers over SQL templates. Neither is compared here.

## A whole statement still gains checked references in the builder

**Raw SQL is at its strongest in one complete statement, and that is the statement to test the builder against.** A report that keeps each owner's first three assets by name is one statement with two window functions:

```sql
with ranked as (
  select
    asset.id,
    asset.name,
    asset.owner_id,
    row_number() over (partition by asset.owner_id order by asset.name, asset.id) as position,
    count(*) over (partition by asset.owner_id) as owner_total
  from asset
)
select id, name, owner_id, position, owner_total
from ranked
where position <= 3
order by owner_id, position;
```

It runs unchanged in a SQL console, under `EXPLAIN ANALYZE`, and in a review by someone who does not write TypeScript. In application code it is a string: nothing checks `asset.owner_id` against the schema, the result type is whatever the caller annotates, and a renamed column is found by search. The same report in Kysely:

```ts
const topAssets = await db
  .with('ranked', (qb) =>
    qb.selectFrom('asset').select((eb) => [
      'asset.id',
      'asset.name',
      'asset.owner_id',
      eb.fn
        .agg('row_number')
        .over((ob) =>
          ob
            .partitionBy('asset.owner_id')
            .orderBy('asset.name')
            .orderBy('asset.id'),
        )
        .as('position'),
      eb.fn
        .countAll()
        .over((ob) => ob.partitionBy('asset.owner_id'))
        .as('owner_total'),
    ]),
  )
  .selectFrom('ranked')
  .select(['id', 'name', 'owner_id', 'position', 'owner_total'])
  .where('position', '<=', 3)
  .orderBy('owner_id')
  .orderBy('position')
  .execute()
```

Every reference is checked against the database declarations, the result type is inferred from the selection, and renaming `asset.name` turns the report into a compile error. The builder version is longer and reads as an API rather than as SQL. **Raw SQL's best case is a fixed statement, and the builder still checks it.** Whole raw statements keep their place in migrations, bootstrap, and one-off scripts, where there is no composition to check.

## Every variation is a fragment, a file, or a checked operation

An asset list starts as an owner's assets, sorted by name and ID and limited to 50; any of the three forms writes that in a few lines. Then the list needs an optional album filter, which adds a join and a predicate, and an optional name prefix.

### Add the optional join and filters

Put the shared query in a function. Kysely's `$if` applies each addition when its condition is true; the join lives in a callback because it changes the builder's type, and references inside that branch are checked against the joined table. The condition does not narrow `options` inside the callback, hence the assertions:

```ts
function matchingAssets(options: AssetOptions) {
  return db
    .selectFrom('asset')
    .where('asset.owner_id', '=', options.ownerId)
    .$if(options.albumId !== undefined, (qb) =>
      qb
        .innerJoin('album_asset', 'album_asset.asset_id', 'asset.id')
        .where('album_asset.album_id', '=', options.albumId!),
    )
    .$if(options.namePrefix !== undefined, (qb) =>
      qb.where('asset.name', 'like', options.namePrefix! + '%'),
    )
}
```

With raw SQL, the same rules live in fragment helpers, and Postgres.js numbers the parameters:

```ts
const albumJoin = (options: AssetOptions) =>
  options.albumId !== undefined
    ? sql`inner join album_asset on album_asset.asset_id = asset.id`
    : sql``
const albumFilter = (options: AssetOptions) =>
  options.albumId !== undefined
    ? sql`and album_asset.album_id = ${options.albumId}`
    : sql``
const nameFilter = (options: AssetOptions) =>
  options.namePrefix !== undefined
    ? sql`and asset.name like ${options.namePrefix + '%'}`
    : sql``

function matchingAssetSql(options: AssetOptions) {
  return sql`
    from asset ${albumJoin(options)}
    where asset.owner_id = ${options.ownerId}
      ${albumFilter(options)} ${nameFilter(options)}
  `
}
```

```ts
const assets = await sql<{ id: string; name: string }[]>`
  select asset.id, asset.name ${matchingAssetSql(options)}
  order by asset.name, asset.id limit 50
`
```

The album join and its predicate are one callback in Kysely and two fragments that must agree here. **The first conditional in a shared helper takes every statement that uses it out of the checker's coverage.** [SafeQL's Postgres.js integration](https://safeql.dev/compatibility/postgres.js.html#support-matrix) lists conditional fragment selection as unsupported; linting this helper, it reports the interpolation as a type it cannot map and checks nothing around it. Its maintainer [explains the limit as combinatorial](https://github.com/ts-safeql/safeql/issues/100#issuecomment-1311048387): each condition doubles the forms to check. Kysely checks the album branch once, inside its callback.

A typed SQL file cannot add or remove clauses, so each optional filter becomes a nullable parameter guarded by `is null or`, and album membership becomes `exists`. With Prisma TypedSQL, parameters are typed by comments and the rest is plain SQL:

```sql title="findAssets.sql"
-- @param {String} $1:ownerId
-- @param {String} $2:albumId?
-- @param {String} $3:namePrefix?
select asset.id, asset.name
from asset
where asset.owner_id = $1
  and ($2::text is null or exists (
    select 1 from album_asset
    where album_asset.asset_id = asset.id
      and album_asset.album_id = $2
  ))
  and ($3::text is null or asset.name like $3 || '%')
order by asset.name, asset.id
limit 50;
```

PgTyped and sqlc write the same statement with `:albumId` and `sqlc.narg(album_id)`, syntax that fails in a console. **A SQL file with tool syntax is the input to a tool that produces a statement, which is what a builder is too.** [PgTyped's documentation](https://pgtyped.dev/docs/dynamic-queries) states the design: "pgTyped doesn't support query composition or concatenation", and "forces you to move the dynamic logic into the SQL layer".

The nullable parameter, with the casts PostgreSQL [requires on a reused parameter](https://github.com/jackc/pgx/issues/2233), is the mild form of that move. The rest is catalogued in sqlc's [dynamic queries discussion](https://github.com/sqlc-dev/sqlc/discussions/364), open since 2020: `CASE WHEN` switches that defeat indexes, placeholders filled by application code, and a query builder beside the generator. **The composition did not disappear; it moved into the statement, where the planner pays for every variation, or back into application code, where nothing checks it.**

### Reuse the filters for a list and a count

The list chooses its fields and pagination after calling `matchingAssets`; the total reuses the filters without inheriting the limit:

```ts
const assets = await matchingAssets(options)
  .select(['asset.id', 'asset.name'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .limit(50)
  .execute()
// Inferred: { id: string; name: string }[]

const total = await matchingAssets(options)
  .select((eb) => eb.fn.countAll().as('count'))
  .executeTakeFirstOrThrow()
// Inferred: { count: string | number | bigint }
```

The count's union is the driver's truth: PostgreSQL returns `count(*)` as `bigint`, which `pg` delivers as a string unless a type parser is registered, and `countAll<number>()` declares the parsed type once one is.

**Each consumer keeps its own selections and pagination; each inherits the shared query's scope and result type.** Kysely's builders are immutable, so extending one does not change another, and a new shared rule goes into `matchingAssets` once. Fragments give Postgres.js the same reuse, with an annotation per caller. A generated call returns one fixed shape, so the count is a second statement that repeats the predicates. **Checking both statements does not establish that their filtering rules agree.**

### Add a folder name through a left join

An export needs each asset's folder name, and unfiled assets have none:

```ts
const exportedAssets = await matchingAssets(options)
  .leftJoin('folder', 'folder.id', 'asset.folder_id')
  .select(['asset.id', 'asset.name', 'folder.name as folder_name'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .execute()
// Inferred: { id: string; name: string; folder_name: string | null }[]
```

`folder_name` is nullable because the left join made it nullable. The Postgres.js caller annotates the result itself, and nothing objects to `folder_name: string`. A generator has to infer nullability, because PostgreSQL's [`RowDescription`](https://www.postgresql.org/docs/current/protocol-message-formats.html) reports a column's type and source table and nothing about whether it can be null. Put this export in a `.sql` file and Prisma TypedSQL and PgTyped generate `folder_name: string`: the source column is `NOT NULL`, the left join is not consulted, and `folder_name.toUpperCase()` compiles and throws on the first unfiled asset. sqlc tracks the join and emits `string | null`. The same tools lean the other way on `count(*)::integer`, which TypedSQL and PgTyped type `number | null` for a column that is never null. **Nullability is where generated types are weakest, and it is what Kysely tracks through the join.**

### Add optional nested tags

The list needs tags when requested. Add a correlated JSON subquery with `jsonArrayFrom` from `kysely/helpers/postgres`:

```ts
const assets = await matchingAssets(options)
  .select(['asset.id', 'asset.name'])
  .$if(options.includeTags, (qb) =>
    qb.select((eb) =>
      jsonArrayFrom(
        eb
          .selectFrom('asset_tag')
          .innerJoin('tag', 'tag.id', 'asset_tag.tag_id')
          .select(['tag.id', 'tag.name'])
          .whereRef('asset_tag.asset_id', '=', 'asset.id')
          .orderBy('tag.name'),
      ).as('tags'),
    ),
  )
  .orderBy('asset.name')
  .orderBy('asset.id')
  .limit(50)
  .execute()
// Inferred: { id: string; name: string; tags?: { id: string; name: string }[] }[]
```

Requested tags use `[]` when none exist; unrequested tags omit the key and the subquery. The inner references are checked, including the one to the outer `asset`. A fixed statement cannot remove a column, so a SQL file is a second statement chosen in TypeScript, and the database describes its `tags` column as `json`: TypedSQL and PgTyped generate `JsonValue | null` and `Json | null`, and sqlc `string | null`. **A JSON column's shape is where generated types stop; the nested shape is known only to the code that wrote the subquery, and Kysely wrote it.** See [conditional selects](/docs/recipes/conditional-selects) and [nested relations](/docs/recipes/relations).

### What changed as the requirements grew?

| Requirement                              | Kysely                                                 | SQL templates                                              | Typed SQL files                                                 |
| ---------------------------------------- | ------------------------------------------------------ | ---------------------------------------------------------- | --------------------------------------------------------------- |
| Add a conditional join and predicate     | Extend the builder; references checked in the branch.  | Compose fragments; the statements leave SafeQL's coverage. | Nullable parameters and `exists`; one statement, checked whole. |
| Share filters across list, count, export | One unfinished query; each caller selects its fields.  | Share fragments; each caller declares its own annotation. | A statement per shape; repeat the predicates, or use a view.    |
| Left join an optional folder name        | The column arrives as `string \| null`.                | The annotation says whatever the caller wrote.             | A new statement; `string` from TypedSQL and PgTyped, `string \| null` from sqlc. |
| Optional nested tags                     | A conditional selection; the nested shape is inferred. | A conditional fragment; the annotation declares the shape. | A second statement; the column is JSON, or a string.            |

**An established query builder supplies the composition rules and types; a helper layer supplies them through tests and maintenance; a set of SQL files supplies them one statement at a time.**

## Try to break the shared query

The test of a composition layer is what happens when someone changes it without reading all of it.

### A consumer cannot reference a table the shared query only sometimes joins

A per-album export needs each row's album ID. With fragments, the caller adds the column:

```ts
const albumExport = await sql<{ id: string; name: string; album_id: string }[]>`
  select asset.id, asset.name, album_asset.album_id ${matchingAssetSql(options)}
  order by asset.name, asset.id
`
```

This compiles and runs for requests that supply an album. For the rest, the helper omits the join and PostgreSQL rejects `album_asset.album_id`; the fragment records nothing about when `album_asset` is present. The same caller does not compile with Kysely:

```ts
const albumExport = await matchingAssets(options)
  .select(['asset.id', 'asset.name', 'album_asset.album_id']) // TypeScript error
  .execute()
```

`album_asset` is in scope only inside the callback that joins it, so the shared query's type does not offer it. The error names the decision: require the album and join it unconditionally, or select the column inside the branch that has it. **A fragment carries SQL text and bound values; a Kysely builder also carries the tables in scope and the result selected so far.** Whether a join applies the right rule or preserves row counts still needs review and tests.

With SQL files the export is a new statement with its own `exists`. **A generated call cannot be extended by its caller, which prevents the mistake and also prevents the extension.** [TypedSQL documents its dynamic-column limit](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/typedsql#dynamic-sql-queries-with-dynamic-columns) as a hand-off to unsafe raw queries.

### A rename reaches every caller through the compiler

Suppose a migration renames `asset.name` to `asset.label`, and an agent must update the application. With Kysely, [regenerate the declarations](/docs/generating-types) once and type-check:

```ts
interface Database {
  asset: { id: string; label: string; owner_id: string; folder_id: string | null }
  // ...
}

function matchingAssets(options: AssetOptions) {
  return db
    .selectFrom('asset')
    // ...
    .$if(options.namePrefix !== undefined, (qb) =>
      qb.where('asset.name', 'like', options.namePrefix! + '%'), // TypeScript error
    )
}

const assets = await matchingAssets(options)
  .select(['asset.id', 'asset.name']) // TypeScript error
  .orderBy('asset.id')
```

The compiler lists every stale reference: the shared filter and each consumer's selection, in the list, the count, the export, and the tags listing. The same edit in the raw SQL forms is a text search. A SQL template's declared annotation keeps claiming `name` exists until a runtime value is undefined. A generated type catches the drift at the next generation run, against a live database for PgTyped and TypedSQL, and only in the statements it generated. **A type check is a verification step an agent can run on every edit, with nothing but the repository.** The database enters Kysely's loop when the schema changes, not when a query does; a query edit, such as selecting `asset.name as label`, changes the consumer's inferred type and its callers' errors with no generation step.

## SQL checkers verify a statement; Kysely verifies a composition

**A SQL checker verifies a statement it can see whole; Kysely verifies each operation that application code adds to a query.** SafeQL and the generators ask PostgreSQL to describe a statement, so its grammar, functions, and result columns are checked against the database, and the coverage ends at statements they can see whole. Kysely's grammar is library output, tested per dialect across its API, so a misplaced clause is not a mistake application code can make; a reference, a result shape, or a composition is, and those are what its types check.

Kysely's coverage ends where the statement's meaning depends on the database rather than the declarations. An unqualified `id` after a join of two tables that both have one compiles and PostgreSQL rejects it as ambiguous; a selected column missing from `GROUP BY` compiles; `fn('lower', ['asset.id'])` compiles whatever the column's type; a `sql` expression and the type declared on it are taken on trust. A checker with the database catches each of those in a fixed statement. Tests against a database still have their place with the builder; what they no longer cover is the composition. The checker and the builder are not exclusive: SafeQL's [Kysely plugin](https://safeql.dev/compatibility/kysely.html), experimental, inlines the `sql` expressions in a Kysely query and checks them against the database, so the one input the builder takes on trust can have a checker too.

**Every mistake a builder prevents is one raw SQL finds at runtime, one round trip at a time.** A misspelled column, a parameter numbered wrong, a comparison against the wrong type: each is found by running the statement and reading the database's message, and PostgreSQL reports [one error per attempt](https://www.postgresql.org/docs/current/protocol-error-fields.html). With Kysely those are compile errors, reported together, before a connection is opened. For a developer that is minutes per statement; for a coding agent it is an execution loop per mistake, against a database it may not have.

### Can raw SQL be type-safe?

**Yes, one statement at a time.** A declared result type checks callers against the annotation and says nothing about the SQL. A runtime schema, such as Slonik's with a [parser interceptor](https://github.com/gajus/slonik/blob/5130ed4320686ab8876cb2296d35f9a1b2cccc93/README.md#result-parser-interceptor), rejects an incompatible row when the query runs. SafeQL checks supported statements during linting; generators derive the type from the statement. None of them establish conditional composition. Kysely does not validate returned rows, so runtime validation can still be useful at boundaries.

### Does a query builder prevent SQL injection?

**Not on its own, and raw SQL does not invite it on its own.** Every client here binds values as parameters; injection enters through request text placed in SQL syntax, which [Postgres.js `sql.unsafe`](https://github.com/porsager/postgres/blob/570be764d96c8c13e6a1a262103bf60974571b67/README.md#unsafe-raw-string-queries) and Kysely's `sql.raw` both send as SQL. Column names and sort directions are syntax, so every workflow allow-lists them; pass an allow-listed column to `orderBy` and a misspelled entry is a type error, while Kysely's [dynamic references](https://kysely-org.github.io/kysely-apidoc/classes/DynamicModule.html) leave the allow-list to you. **Safe parameterization is not the reason to adopt a builder; raw SQL has it. The checked composition API is.**

## Performance belongs to the statement, not the authoring tool

**The database receives a parameterized statement either way, and cannot tell which tool wrote it.** Compiling a builder to SQL is work in application memory before the round trip; the comparison that matters is between the statements and their plans. For a request with only an owner filter, [`.compile()`](/docs/recipes/splitting-query-building-and-execution) on the list query returns the parameters `['owner-1', 50]` and this SQL:

```sql title="compiled.sql (formatted)"
select "asset"."id", "asset"."name"
from "asset"
where "asset"."owner_id" = $1
order by "asset"."name", "asset"."id"
limit $2
```

A request without an album sends no `album_asset` reference, while the fixed `($2::text is null or ...)` statement serves every combination with one plan: after five executions of a prepared statement PostgreSQL [may keep a generic plan](https://www.postgresql.org/docs/current/sql-prepare.html#SQL-PREPARE-NOTES), and PgTyped's documentation warns that "highly dynamic SQL queries can lead to worse DB execution times". **The fixed statement asks the planner to handle every combination; the composed one asks the application to own them.**

## Kysely's escape hatch is a typed expression inside the builder

**Raw SQL has a place inside Kysely: as an expression inside a composed query, not a statement beside it.** Kysely does not cover all of SQL; it covers what applications write most, extends that coverage release by release, and types the escape hatch for the rest. A `sql` template inside a builder query is an expression like any other: references passed through `eb.ref` are checked against the tables in scope, values bind as parameters, and the declared result type flows into the query. Wrapped in a function that takes `Expression` inputs, it is a [reusable typed helper](/docs/recipes/reusable-helpers). The prefix filter above passes `%` and `_` through as wildcards; escaping them takes `LIKE ... ESCAPE`, a clause the builder's `like` operator does not have:

```ts
import { Expression, sql } from 'kysely'

function startsWith(column: Expression<string>, prefix: string) {
  const pattern = prefix.replace(/[\\%_]/g, '\\$&') + '%'
  return sql<boolean>`${column} like ${pattern} escape '\\'`
}
```

In the shared query, the helper takes a checked reference and returns a boolean expression:

```ts
const matches = await matchingAssets(options)
  .where((eb) => startsWith(eb.ref('asset.name'), prefix))
  .select(['asset.id', 'asset.name'])
  .limit(50)
  .execute()
// Inferred: { id: string; name: string }[]
```

A prefix of `%` now matches nothing instead of everything, and the helper is the only place that knows how. Functions and operators rarely need the template: `fn` calls any function with checked references, and `@@`, `<->`, `~*`, and the JSON operators are already in the builder. A whole statement through the `sql` tag gives up every check on this page; keep that form for migrations and scripts, and `sql.raw` for trusted syntax such as an identifier. Adoption runs one helper at a time: Kysely's PostgreSQL dialect takes an existing node-postgres `Pool`, so a shared helper moves to the builder while the remaining `pool.query` calls keep running. See [raw expressions](/docs/recipes/raw-sql) and the [SQL template API](https://kysely-org.github.io/kysely-apidoc/interfaces/Sql.html).

## Production code draws the same line

- [Immich](https://github.com/immich-app/immich/blob/0733cc10ee7a0c8ebd5d37b1804b5c28944b7cdd/server/src/repositories/asset.repository.ts#L572-L624) composes optional relation selections and a lateral subquery for stacked assets.

## Other practical considerations

<details>
<summary>Engines, drivers, and portability</summary>

Raw SQL is written in one engine's grammar, with its placeholder style, identifier quoting, and functions. PgTyped is PostgreSQL only. Prisma TypedSQL supports PostgreSQL, MySQL, and SQLite, with argument types declared manually on SQLite. sqlc supports the same three; its TypeScript plugin targets `pg`, Postgres.js, `mysql2`, and `better-sqlite3`, and its README states that it is "still in early access". Kysely ships dialects for PostgreSQL, MySQL, SQLite, and Microsoft SQL Server, compiles the same operations to each engine's syntax, and exposes engine-specific features such as PostgreSQL conflict handling and MySQL duplicate-key updates.

Most applications never change engines, so portability is a weak reason on its own to adopt a builder; it matters for libraries, multi-engine products, and teams that test on a lighter engine.

</details>

## Choosing raw SQL or Kysely

### Why use a query builder instead of raw SQL?

**Because application queries change, and a query builder checks each change: the reference it adds, the result it selects, and the tables a shared query puts in scope.** Raw SQL binds the same parameters and sends the same statement; what it leaves to review, tests, and search, Kysely's types report before a connection is opened.

### When does raw SQL belong in a TypeScript application?

**Where there is no composition to check: migrations and DDL, bootstrap, one-off scripts, and the expression a builder cannot express.** Typed SQL files give each such statement the strongest check available and a derived type. Raw SQL also costs nothing at the type level: Kysely's checks are computed by the compiler, and a schema with hundreds of tables or a deeply composed query can slow type-checking and the editor. Generated declarations keep that cost tied to schema size, not query count, and `$if` branches and helpers typed with `Expression` keep individual queries shallow.

What each side maintains itself, for the asset list above:

| Responsibility                             | Raw SQL in TypeScript                                                          | Kysely                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| Which tables a shared helper puts in scope | Convention, review, and tests.                                                 | The builder's type; a consumer cannot reference a table it may not have. |
| Each caller's result type                  | A declared annotation, a runtime schema, or a generated type per statement.    | Inferred from the selection, including outer-join nullability.           |
| A new shared rule                          | One edit per helper or statement, checked by tests.                            | One edit in the shared function, inherited by every consumer.            |
| A schema rename                            | Search, or regeneration where a checker is in the loop.                        | Regenerate declarations; the compiler lists every stale reference.       |

Try one endpoint whose filters are repeated across a list and count. Add a shared rule, change a selected alias, and let a consumer reference a conditional join. Compare the edits, the steps before anything can tell you the edit was valid, and the statements the database receives.

The examples ran against PostgreSQL 18.4 with Kysely 0.29.7, Postgres.js 3.4.9, Slonik 49.11.0, Prisma TypedSQL 7.10.1, PgTyped 2.4.3, sqlc 1.31.1 with sqlc-gen-typescript 0.1.3, and TypeScript 7.0.2 and 6.0.3; the [comparison fixtures](https://github.com/kysely-org/kysely/tree/3698df09/site/scripts/comparison-checks/postgres) reproduce them.
