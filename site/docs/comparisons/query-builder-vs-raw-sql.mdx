# SQL query builder vs raw SQL in TypeScript

**A team that composes raw SQL is already maintaining a query builder. The question is whether it is checked.** Helpers that choose joins, predicates, and selections take on a builder's job: which tables are in scope, which result each combination returns, and where interpolation is safe. Raw SQL can be parameterized, checked, and typed. What a typed builder adds is checking that composition as application code changes it.

A SQL query builder constructs SQL through a programming language API; raw SQL expresses the statement directly. Both give you control over tables, joins, subqueries, and expressions. Kysely is a query builder that checks references against your database types and infers each query's result.

Statements that stay whole and fixed are well served by raw SQL, and this page starts there. The case for a builder begins when a list gains optional filters, a count reuses them, and an export selects different fields. The examples follow one asset query through those changes, then try to break it.

## Raw SQL in TypeScript takes three forms

<SqlQueryWorkflows />

[node-postgres](https://node-postgres.com/features/queries#parameterized-query) with `$1` placeholders is the baseline most teams mean by raw SQL: a string, an array of values, and a result type the caller declares. SQL templates such as [Postgres.js](https://github.com/porsager/postgres/blob/570be764d96c8c13e6a1a262103bf60974571b67/README.md#building-queries) and Slonik keep statements beside application code, compose fragments, and bind interpolated values; [SafeQL](https://safeql.dev/) adds schema-aware checking to the call forms it supports. SQL-file tools connect complete statements to generated application calls: [PgTyped](https://pgtyped.dev/docs/), [Prisma TypedSQL](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/typedsql), and [sqlc](https://docs.sqlc.dev/) are compared separately in [SQL query builder vs typed SQL files](/docs/comparisons/query-builder-vs-sql-files). With Kysely, you compose operations such as `selectFrom`, `where`, and `innerJoin`, and it compiles them into SQL and parameters.

## Whole statements are raw SQL's home ground

**When the unit of work is one complete statement, raw SQL is the clearest way to write it.** A report that ranks each owner's assets by name and keeps the first three per owner is one statement with two window functions:

```sql
with ranked as (
  select
    asset.id,
    asset.name,
    asset.owner_id,
    row_number() over (partition by asset.owner_id order by asset.name, asset.id) as position,
    count(*) over (partition by asset.owner_id) as owner_total
  from asset
)
select id, name, owner_id, position, owner_total
from ranked
where position <= 3
order by owner_id, position;
```

This runs unchanged in a SQL console, under `EXPLAIN ANALYZE`, in a code review by someone who does not write TypeScript, and in a message to a database specialist. Kysely expresses the same statement:

```ts
const topAssets = await db
  .with('ranked', (qb) =>
    qb.selectFrom('asset').select((eb) => [
      'asset.id',
      'asset.name',
      'asset.owner_id',
      eb.fn
        .agg<number>('row_number')
        .over((ob) =>
          ob
            .partitionBy('asset.owner_id')
            .orderBy('asset.name')
            .orderBy('asset.id'),
        )
        .as('position'),
      eb.fn
        .countAll<number>()
        .over((ob) => ob.partitionBy('asset.owner_id'))
        .as('owner_total'),
    ]),
  )
  .selectFrom('ranked')
  .select(['id', 'name', 'owner_id', 'position', 'owner_total'])
  .where('position', '<=', 3)
  .orderBy('owner_id')
  .orderBy('position')
  .execute()
```

It compiles to the SQL above with the limit bound as a parameter, and every column reference is checked. It is also longer, it reads as an API rather than as SQL, and the `number` on each window function is a declaration, not a finding: PostgreSQL returns `bigint` for both, which node-postgres delivers as a string unless the column is cast or a type parser is configured. Kysely does not verify a declared type. A tool that asks the database to describe the statement derives the type instead.

**A query being long or complex is not itself a reason to move it to a builder.** If a statement is written once, reviewed as SQL, and changed by editing SQL, keep it as SQL; [Kysely runs it on the same connection](#raw-sql-stays-available-inside-kysely) as composed queries. The case for a builder is not the hard query. It is the query that keeps changing.

## Shared SQL helpers grow into an unchecked query builder

An asset list starts with an owner's assets, sorted by name and ID and limited to 50. Assume configured clients and an `asset` table with string `id`, `name`, and `owner_id` columns.

With Postgres.js, the statement is close to the SQL you would run in a console:

```ts
const rows = await sql<{ id: string; name: string }[]>`
  select id, name from asset
  where owner_id = ${ownerId}
  order by name, id
  limit 50
`
```

With Kysely, the same operations use its builder API:

```ts
const rows = await db
  .selectFrom('asset')
  .select(['id', 'name'])
  .where('owner_id', '=', ownerId)
  .orderBy('name')
  .orderBy('id')
  .limit(50)
  .execute()
// Inferred: { id: string; name: string }[]
```

Both handle this query well. Now the list needs an optional album filter and name prefix. The album filter adds both a join and a predicate; other requests should omit them.

### Add the optional join and filters

Put the shared query in a function. Kysely's `$if` applies each addition when its condition is true. The join changes the builder's type, which is why the addition lives in a callback rather than a reassigned variable; the non-null assertions restate the conditions checked outside the callbacks:

```ts
function matchingAssets(options: AssetOptions) {
  return db
    .selectFrom('asset')
    .where('asset.owner_id', '=', options.ownerId)
    .$if(options.albumId !== undefined, (qb) =>
      qb
        .innerJoin('album_asset', 'album_asset.asset_id', 'asset.id')
        .where('album_asset.album_id', '=', options.albumId!),
    )
    .$if(options.namePrefix !== undefined, (qb) =>
      qb.where('asset.name', 'like', options.namePrefix! + '%'),
    )
}
```

The join and its album predicate are composed together. Inside that branch, Kysely checks references against the added table.

Postgres.js keeps the same rules in fragments. Each conditional fragment is its own helper so that a later caller can reuse the parts, and `matchingAssetSql` assembles them:

```ts
const albumJoin = (options: AssetOptions) =>
  options.albumId !== undefined
    ? sql`inner join album_asset on album_asset.asset_id = asset.id`
    : sql``
const albumFilter = (options: AssetOptions) =>
  options.albumId !== undefined
    ? sql`and album_asset.album_id = ${options.albumId}`
    : sql``
const nameFilter = (options: AssetOptions) =>
  options.namePrefix !== undefined
    ? sql`and asset.name like ${options.namePrefix + '%'}`
    : sql``

function matchingAssetSql(options: AssetOptions) {
  return sql`
    from asset ${albumJoin(options)}
    where asset.owner_id = ${options.ownerId}
      ${albumFilter(options)} ${nameFilter(options)}
  `
}

const assets = await sql<{ id: string; name: string }[]>`
  select asset.id, asset.name ${matchingAssetSql(options)}
  order by asset.name, asset.id limit 50
`
const totals = await sql<{ count: number }[]>`
  select count(*)::int as count ${matchingAssetSql(options)}
`
```

Both implementations centralize the filters and leave pagination out of the count.

### The first conditional takes the statement out of the checker

**The first conditional in a shared helper takes every statement that uses the helper out of the checker's coverage.** A checker can verify fragments in the forms it supports, and [SafeQL's Postgres.js integration](https://safeql.dev/compatibility/postgres.js.html#support-matrix) lists conditional fragment selection such as these ternaries as unsupported. Linting this helper confirms what that means: SafeQL flags each branch fragment as an invalid query, reports the `${matchingAssetSql(options)}` interpolation as a type it cannot map, and checks nothing about the statement around it. A misspelled column or a wrong result annotation in the list or count goes unreported.

SafeQL's maintainer [explains the limit as combinatorial](https://github.com/ts-safeql/safeql/issues/100#issuecomment-1311048387): each condition doubles the statement forms a checker would have to run, so three conditions mean eight queries and ten mean 1024. The limit belongs to the approach rather than to SafeQL. A checker verifies statements it can see whole, and a helper with a conditional produces statements it cannot. Moving the conditional into SQL, with a nullable parameter and an `is null or` predicate, restores full checking at the cost of a fixed statement; [typed SQL files](/docs/comparisons/query-builder-vs-sql-files) are built around that trade.

Kysely does not enumerate the forms either. It checks each operation against the tables in scope at the point where application code adds it, so the branch that joins `album_asset` is checked once, inside its callback, whatever combination a request produces.

### Reuse the filters for a list and a count

The list chooses its fields and pagination after calling `matchingAssets`:

```ts
const assets = await matchingAssets(options)
  .select(['asset.id', 'asset.name'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .limit(50)
  .execute()
// Inferred: { id: string; name: string }[]
```

The total reuses the same filters without inheriting the list's limit. The cast makes PostgreSQL return an integer instead of a `bigint` string, and it is what the `number` type is based on:

```ts
const total = await matchingAssets(options)
  .select((eb) => eb.cast<number>(eb.fn.countAll(), 'integer').as('count'))
  .executeTakeFirstOrThrow()
// Inferred: { count: number }
```

**Each consumer keeps its own selections and pagination; each inherits the shared query's scope and result type.** Kysely's builders are immutable, so extending one does not change another. A new shared rule, such as excluding archived albums, goes into `matchingAssets` once and reaches every consumer. Shared fragments give the SQL-template version the same reuse; each caller's result type is still a separate annotation.

### Add a folder name through a left join

An export needs each asset's folder name, and unfiled assets have none. Join the folder optionally:

```ts
const exportedAssets = await matchingAssets(options)
  .leftJoin('folder', 'folder.id', 'asset.folder_id')
  .select(['asset.id', 'asset.name', 'folder.name as folder_name'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .execute()
// Inferred: { id: string; name: string; folder_name: string | null }[]
```

**The left join makes `folder_name` nullable in the result type, because the query made it nullable in the result.** A caller that treats it as a string gets a type error, not an empty cell in a spreadsheet.

The Postgres.js helper bundles `from` and `where` in one fragment, so a caller with its own join reassembles the clauses from the helper's parts. The annotation is then whatever the caller writes:

```ts
const exportedAssets = await sql<
  { id: string; name: string; folder_name: string }[]
>`
  select asset.id, asset.name, folder.name as folder_name
  from asset ${albumJoin(options)}
  left join folder on folder.id = asset.folder_id
  where asset.owner_id = ${options.ownerId} ${albumFilter(options)} ${nameFilter(options)}
  order by asset.name, asset.id
`
```

Nothing objects to `folder_name: string`. A nullable column arriving in an annotation as non-null is a drift no handwritten type can catch, and SQL-aware checkers must derive outer-join nullability themselves, because PostgreSQL's result metadata reports each column's type and source but not whether it can be null (see [database support for checking](/docs/comparisons/query-builder-vs-sql-files#database-support-for-checking)).

### Add optional nested tags

The list now needs tags when requested. Add a correlated JSON subquery using `jsonArrayFrom` from `kysely/helpers/postgres`:

```ts
function assetListing(options: AssetOptions) {
  return matchingAssets(options)
    .select(['asset.id', 'asset.name'])
    .$if(options.includeTags, (qb) =>
      qb.select((eb) =>
        jsonArrayFrom(
          eb
            .selectFrom('asset_tag')
            .innerJoin('tag', 'tag.id', 'asset_tag.tag_id')
            .select(['tag.id', 'tag.name'])
            .whereRef('asset_tag.asset_id', '=', 'asset.id')
            .orderBy('tag.name'),
        ).as('tags'),
      ),
    )
    .orderBy('asset.name')
    .orderBy('asset.id')
    .limit(50)
}
```

```ts
const assets = await assetListing(options).execute()
// Inferred: { id: string; name: string; tags?: { id: string; name: string }[] }[]
```

Requested tags use `[]` when none exist; unrequested tags omit the key and the subquery, and the outer result stays at one row per asset. Kysely checks the inner references, including the one to the outer `asset`, and carries the nested shape into `tags`. See [conditional selects](/docs/recipes/conditional-selects) and [nested relations](/docs/recipes/relations).

### What changed as the requirements grew?

| Requirement                                    | Kysely                                                                    | SQL templates in TypeScript                                             | [Typed SQL files](/docs/comparisons/query-builder-vs-sql-files)          |
| ---------------------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Add a conditional join and predicate           | Extend the builder; references are checked against the added table.       | Compose fragments; statements using the helper leave SafeQL's coverage. | Parameter-controlled predicates, or separate statement variants.         |
| Share filters across a list, count, and export | One function returns an unfinished query; each caller selects its fields. | Share fragments; keep each caller's result annotation aligned by hand.  | Repeat the rules in each file, or centralize them in a view or function. |
| Left join an optional folder name              | The selected column arrives as `string \| null`.                          | The annotation says whatever the caller wrote.                          | Nullability depends on the tool's analysis of the outer join.            |
| Change a selected field                        | The caller's result type re-infers.                                       | A handwritten type drifts until analysis catches it.                    | Regenerate the typed call.                                               |

**An established builder supplies the composition rules and types; a custom helper layer supplies them through tests and maintenance.**

## Try to break the shared query

The test of a composition layer is what happens when someone changes it without reading all of it.

### A consumer cannot reference a table the shared query only sometimes joins

A per-album export needs each row's album ID. With fragments, the caller adds the column to its selection:

```ts
const albumExport = await sql<{ id: string; name: string; album_id: string }[]>`
  select asset.id, asset.name, album_asset.album_id ${matchingAssetSql(options)}
  order by asset.name, asset.id
`
```

This compiles, and it runs for requests that supply an album. For requests that don't, the helper omits the join and PostgreSQL rejects `album_asset.album_id`. The fragment's type records nothing about when `album_asset` is present, and SafeQL does not check this statement because of the conditional helper it inlines.

The same caller does not compile with Kysely:

```ts
const albumExport = await matchingAssets(options)
  .select(['asset.id', 'asset.name', 'album_asset.album_id']) // TypeScript error
  .execute()
```

`album_asset` is in scope only inside the callback that joins it, so the shared query's type does not offer it to consumers. The error names the decision the export has to make: require the album and join it unconditionally, or select the column inside the branch that has it. The same check holds inside the shared function: remove the join from the `$if` callback and its album predicate becomes a type error.

**A fragment carries SQL text and bound values; a Kysely builder also carries the tables in scope and the result selected so far.** It does not prove that a join applies the right business rule or preserves row counts; those still need review and tests.

### A rename reaches every caller without a database in the loop

Suppose an agent must rename the export's `name` field to `label` without changing the list or count. It changes only the export selection:

```ts
const exportedAssets = await matchingAssets(options)
  .select(['asset.id', 'asset.name as label'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .execute()
// Inferred: { id: string; label: string }[]

exportedAssets.map((asset) => asset.name) // TypeScript error
exportedAssets.map((asset) => asset.label) // string[]
```

The compiler lists the stale callers using the existing database declarations. **A type check is a verification step an agent can run on every edit, with nothing but the repository.** No database connection, no generation step, and no search for the string `name`. A handwritten `sql<{ id: string; name: string }[]>` annotation keeps claiming `name` exists until a runtime value is undefined. A generated type catches the same drift after the next generation run, with a database or schema in that loop.

The same loop covers the schema. Rename `asset.name` to `asset.title`, regenerate the declarations, and TypeScript lists every reference to the old column: the shared filter, the list, the export alias, and the raw expressions that reference it through `eb.ref`. With SQL strings, a search for `name` is the checker, and the failures otherwise arrive at runtime one statement at a time.

**Kysely reports every mistake in a statement in one pass, at the operation that introduced it.** With the asset schema above, this statement has three independent errors:

```sql
select id, nmae
from asset
where owner_id = 42
  and label like 'F%'
order by name;
```

PostgreSQL reports errors with a [message, hint, and position](https://www.postgresql.org/docs/current/protocol-error-fields.html), but stops at the first one, so these take three round trips, and in a query assembled from fragments the position refers to the assembled SQL. TypeScript reports all three at once:

```ts
db.selectFrom('asset')
  .where('asset.owner_id', '=', 42)
  // Argument of type '42' is not assignable to parameter of type
  // 'OperandValueExpressionOrList<Database, "asset", "asset.owner_id">'.
  .where('asset.label', 'like', 'F%')
  // Argument of type '"asset.label"' is not assignable to parameter of type
  // 'ReferenceExpression<Database, "asset">'.
  .select(['asset.id', 'asset.nmae'])
  // Argument of type 'string[]' is not assignable to parameter of type
  // 'SelectExpression<Database, "asset">'.
  .orderBy('asset.name')
```

Those are the messages TypeScript 7 produces, and they show the cost. **Each error names the Kysely type the argument failed to satisfy, not the column that was misspelled.** The selection error reports the whole array; select `asset.nmae` on its own and the message quotes it. PostgreSQL's message names the column and often suggests the nearest match. The errors are shorter than Kysely's reputation suggests and an editor places each at the offending argument, but they are compiler diagnostics, not SQL diagnostics. SafeQL supplies the database's own messages for the statements it supports, during linting.

## Typed SQL tools check a statement; Kysely checks a composition

**The unit a SQL checker verifies is a statement it can see whole. The unit Kysely verifies is each operation application code adds to a query.** Both are real guarantees; they cover different things, and they arrive through different loops.

**For a whole statement, a SQL-aware checker verifies more than Kysely does.** SafeQL and the SQL-file generators ask PostgreSQL to describe the statement, so its grammar, functions, expression types, and result columns are checked against the database, and the result type is derived rather than declared. Kysely verifies table and column references and the result shape they produce; anything expressed through `sql` keeps the type you declared, including the window functions above. Each checker is also bounded by its support matrix and its engine: SafeQL is built for PostgreSQL and PgTyped reads types from a running PostgreSQL database, which leaves MySQL and SQLite teams with fewer statement checkers to choose from.

### Can raw SQL be type-safe?

**Yes. Raw SQL can have static checking, generated types, and runtime validation.** A handwritten result type checks callers against the annotation and says nothing about whether the SQL returns that shape. A runtime schema, such as Slonik's with a configured [parser interceptor](https://github.com/gajus/slonik/blob/5130ed4320686ab8876cb2296d35f9a1b2cccc93/README.md#result-parser-interceptor), rejects an incompatible row when the query runs. [SafeQL](https://safeql.dev/) checks supported statements against PostgreSQL during linting, and its [Slonik integration](https://safeql.dev/compatibility/slonik.html#zod-schema-validation) catches a stale Zod schema before execution. Generators such as PgTyped, TypedSQL, and sqlc produce the result type from the statement itself. None of them establish arbitrary conditional composition; each verifies the forms its support matrix lists.

Kysely's checks depend on accurate database declarations and the driver's runtime value mapping; [generating database types](/docs/generating-types) keeps those declarations aligned. Kysely does not validate returned rows or convert values, so runtime validation can still be useful at application boundaries. Raw `sql<T>` expressions declare their result type explicitly, and SafeQL's [Kysely integration](https://safeql.dev/compatibility/kysely.html), which SafeQL labels experimental, checks supported raw forms. Result inference belongs to particular tools, not to query builders as a category.

### Typed SQL files move composition into SQL

A SQL-file tool keeps every statement fixed so that it can be checked whole. The asset list's optional filters become nullable parameters with `is null or` predicates, the optional tags become a second statement, and a shared visibility rule is repeated in each file or centralized in a database view. Editing a statement means running generation again, with a database or a schema file in the loop. That workflow has real strengths and its own costs, and [SQL query builder vs typed SQL files](/docs/comparisons/query-builder-vs-sql-files) runs the same asset list through PgTyped, Prisma TypedSQL, and sqlc.

## Values bind safely everywhere; syntax needs a boundary either way

**All three workflows bind values safely. Dynamic SQL syntax needs a separate boundary.** Owner IDs and prefixes are values; column names and sort directions are syntax. Narrow a request's sort column to an allow-list of column references, and the builder accepts the narrowed value directly:

```ts
const sortColumns = ['asset.name', 'asset.owner_id', 'asset.id'] as const
type SortColumn = (typeof sortColumns)[number]

function parseSortColumn(value: unknown): SortColumn {
  if (sortColumns.includes(value as SortColumn)) return value as SortColumn
  throw new Error('Unsupported sort column')
}

const rows = await matchingAssets(options)
  .select(['asset.id', 'asset.name'])
  .orderBy(parseSortColumn(requestSort))
  .orderBy('asset.id')
  .execute()
```

Misspell a column in the allow-list and the `orderBy` call is a type error. When column names are known only at runtime, Kysely's [dynamic references](https://kysely-org.github.io/kysely-apidoc/classes/DynamicModule.html) pass them as identifiers rather than values; the allow-list remains your responsibility.

Postgres.js chooses between trusted fragments just as safely, with `sort` already validated to one of two values:

```ts
const ordering =
  sort === 'name' ? sql`asset.name, asset.id` : sql`asset.id desc`

const rows = await sql<{ id: string; name: string }[]>`
  select asset.id, asset.name ${matchingAssetSql(options)}
  order by ${ordering} limit 50
`
```

Both keep request text out of SQL syntax; Kysely additionally checks the column references against the query. SQL files can encode a fixed set of sort choices with SQL expressions or separate statements.

### Does a query builder prevent SQL injection?

**Not on its own, and raw SQL does not invite it on its own.** Every client here binds values as parameters. Injection enters through request text placed in SQL syntax: [Postgres.js `sql.unsafe`](https://github.com/porsager/postgres/blob/570be764d96c8c13e6a1a262103bf60974571b67/README.md#unsafe-raw-string-queries) and Kysely's `sql.raw` both send their string as SQL, and a TypeScript cast does not validate it. **Safe parameterization is not the reason to adopt a builder; raw SQL has it. The checked composition API is.**

## Performance belongs to the statement, not the authoring tool

**Compare statements and execution plans to assess database performance.** A builder does not inherently make a query faster, and handwritten SQL does not inherently produce a better plan.

### Is a query builder slower than raw SQL?

The database receives a parameterized statement either way. For a request with only an owner filter, Kysely exposes the statement and parameters before execution:

```ts
const compiled = matchingAssets({ ownerId: 'owner-1', includeTags: false })
  .select(['asset.id', 'asset.name'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .limit(50)
  .compile()
// compiled.parameters: ['owner-1', 50]
```

```sql title="compiled.sql (formatted)"
select "asset"."id", "asset"."name"
from "asset"
where "asset"."owner_id" = $1
order by "asset"."name", "asset"."id"
limit $2
```

Building and compiling it is in-process work proportional to the statement's size, with no round trip; measure it against your workload if it matters, and compare plans against representative data. Use [`.compile()`](/docs/recipes/splitting-query-building-and-execution) to inspect other combinations before executing them. The [comparison fixtures](https://github.com/kysely-org/kysely/tree/fa14c49ac9240987a5df9811aacf50e31c1d0a5f/site/scripts/comparison-checks/postgres) establish equivalent results, not a speed ranking. A rewrite, such as a join turned into a subquery, stays in the shared builder and updates the inferred result for its callers.

## Raw SQL stays available inside Kysely

### Can you use raw SQL with Kysely?

**Yes, as an expression inside a composed query or as a whole statement, on the same connection.** A builder can cover most of a statement while SQL expresses one local operation. For example, add a lowercase name to the shared query:

```ts
import { sql } from 'kysely'

const normalizedAssets = await matchingAssets(options)
  .select(['asset.id', 'asset.name'])
  .select((eb) =>
    sql<string>`lower(${eb.ref('asset.name')})`.as('normalized_name'),
  )
  .execute()
// Inferred: { id: string; name: string; normalized_name: string }[]
```

The builder still checks the `asset.name` reference and composes the filters. The fragment's `string` result is an explicit declaration; Kysely does not check the `lower(...)` grammar or verify that type. A whole statement can run through Kysely too, against the instance or a transaction, with interpolated values bound as parameters:

```ts
const { rows } = await sql<{ id: string; name: string }>`
  select id, name from asset
  where owner_id = ${ownerId}
  order by name, id
  limit 50
`.execute(db)
// rows: { id: string; name: string }[]
```

**Adopting a builder for composed queries does not require a second client for fixed statements.** The ranked report above, a recursive statement, or a vendor-specific one can stay as SQL, with its result type declared, and share the pool, transactions, plugins, and logging of the queries the builder composes. See [raw expressions](/docs/recipes/raw-sql) and the [SQL template API](https://kysely-org.github.io/kysely-apidoc/interfaces/Sql.html).

## Production code draws the same line

OpenClaw's [contributor guide](https://github.com/openclaw/openclaw/blob/28340c41f8b88ae6d11488e523808315319747b5/AGENTS.md#L71) states the division directly: use Kysely for ordinary SQLite access, and limit raw SQL to schema, migrations, bootstrap, and justified primitives. **Statements that stay fixed are written as SQL; queries that application code composes go through the builder.** The guide is written for coding agents, which makes the checked feedback loop above part of the policy, and a contributor guide of your own can state the same rule in one line.

The composition pattern from the asset example appears in larger codebases:

- [Immich](https://github.com/immich-app/immich/blob/0733cc10ee7a0c8ebd5d37b1804b5c28944b7cdd/server/src/repositories/asset.repository.ts#L572-L624) composes optional relation selections and a lateral subquery for stacked assets. Different requests extend the query with different data.
- [Open Collective](https://github.com/opencollective/opencollective-api/blob/0a59b37c8b33574ee8d9d9a586d5a19506fd5921/server/graphql/v2/query/collection/OrdersCollectionQuery.ts#L780-L826) conditionally adds currency conversion through a correlated exchange-rate lookup. A request option changes the selected expression.
- [Docmost](https://github.com/docmost/docmost/blob/7bef7b1a00d31991f009865ec14c8d06540eb1f0/apps/server/src/database/repos/page/page-permission.repo.ts#L326-L366) composes recursive ancestors for page restrictions. Traversal, joins, and filtering use the same builder interface as simpler queries.

Each could be written as raw SQL. The builder's value is carrying checked references and results through the application code that composes them.

<details>
<summary>Complete Postgres.js implementation</summary>

Postgres.js composes fragments and binds values. Without additional SQL-aware checking, its `AssetRow` result annotation is maintained separately from the query. Assume a configured Postgres.js client named `sql`:

```ts
type AssetRow = {
  id: string
  name: string
  tags?: { id: string; name: string }[]
}

function findAssetsWithPostgres(options: AssetOptions) {
  const albumJoin =
    options.albumId !== undefined
      ? sql`inner join album_asset on album_asset.asset_id = asset.id`
      : sql``
  const albumFilter =
    options.albumId !== undefined
      ? sql`and album_asset.album_id = ${options.albumId}`
      : sql``
  const nameFilter =
    options.namePrefix !== undefined
      ? sql`and asset.name like ${options.namePrefix + '%'}`
      : sql``
  const tagsSelection = options.includeTags
    ? sql`, coalesce((
        select json_agg(tag_rows)
        from (
          select tag.id, tag.name
          from asset_tag
          inner join tag on tag.id = asset_tag.tag_id
          where asset_tag.asset_id = asset.id
          order by tag.name
        ) as tag_rows
      ), '[]'::json) as tags`
    : sql``

  return sql<AssetRow[]>`
    select asset.id, asset.name ${tagsSelection}
    from asset ${albumJoin}
    where asset.owner_id = ${options.ownerId}
      ${albumFilter} ${nameFilter}
    order by asset.name, asset.id
    limit 50
  `
}
```

Slonik composes the same fragments and takes its result type from a `sql.type` schema, which a configured parser interceptor also validates at runtime. The fixtures run that implementation as well.

<details>
<summary>Database-specific features and portability</summary>

Raw SQL is written in one engine's grammar, with that engine's placeholder style, identifier quoting, and functions. A SQL template client hides the placeholder style for its one engine; the rest of the statement stays engine-specific. Kysely ships dialects for PostgreSQL, MySQL, SQLite, and Microsoft SQL Server, and compiles the same builder operations to each engine's syntax while exposing engine-specific features such as PostgreSQL conflict handling and MySQL duplicate-key updates where they exist.

Most applications never change engines, and portability is a weak reason on its own to adopt a builder. It matters for libraries and adapters that must run against whichever database their consumer brings, for products that ship with more than one supported engine, and for teams that run a lighter engine in tests. Differences in constraints, collations, JSON behavior, transactions, and query plans still require testing against each engine you support.

</details>

## Choosing raw SQL or Kysely

**Choose raw SQL when complete statements are the clearest unit of work for your team.** SQL templates keep them beside application code; typed SQL files suit statements reviewed in a SQL workflow. Runtime schemas, SQL-aware checkers, and generated APIs supply strong guarantees for the statements they can see whole, and for a whole statement those guarantees reach further than Kysely's.

The cost of Kysely is another API between you and the statement. Your team must learn its composition rules, keep database declarations aligned with the schema and driver mappings, supply explicit types for raw expressions, and read compiler diagnostics instead of SQL diagnostics. Kysely does not choose indexes, prove that joins preserve row counts, or validate returned values. A query being long or complex is not itself a reason to move it.

Try one endpoint whose filters are repeated across a list and count. Add a shared rule, change a selected alias, and let a consumer reference a conditional join. Compare the edits required, the feedback loop, and the resulting statements. Fixed statements can keep running as SQL through Kysely's `sql` tag, on the same connection as the composed ones.

**Choose Kysely when queries keep acquiring variations and shared rules, and you want the composition layer checked rather than maintained.**
