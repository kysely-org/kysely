# SQL query builder vs raw SQL in TypeScript

**A SQL query builder constructs SQL through a programming language API; raw SQL expresses the statement directly.** Both give you control over tables, joins, subqueries, and expressions. Kysely adds checked references and inferred TypeScript results to its builder API.

**Raw SQL makes a complete statement easy to express. A typed query builder makes shared, changing statements easier to maintain.** A list gains optional filters, a count reuses those filters, and an export selects different fields. Kysely lets each caller extend a shared query while keeping its references and result type connected.

**A team that composes raw SQL is already maintaining a query builder. The question is whether it is checked.** Helpers that choose joins, predicates, and selections take on a builder's job: which tables are in scope, which result each combination returns, and where interpolation is safe. Raw SQL can be parameterized, checked, and typed. The examples below follow one query to show what stays checked as application code composes it.

## A fragment carries SQL text; a builder carries the query's scope and result

<SqlQueryWorkflows />

With raw SQL, you write the statement and bind values through placeholders or a client's tagged template. [Postgres.js](https://github.com/porsager/postgres#building-queries) and Slonik compose fragments; plain SQL strings with separate parameters fit here too, as with node-postgres. [SafeQL](https://safeql.dev/) adds schema-aware checking to supported calls.

SQL-file tools connect complete statements to application calls. [PgTyped](https://pgtyped.dev/docs/) generates typed query objects from SQL or TypeScript files. [Prisma TypedSQL](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/typedsql) generates functions executed through Prisma Client. [sqlc](https://docs.sqlc.dev/) analyzes schema and query inputs; its [TypeScript language plugin](https://github.com/sqlc-dev/sqlc-gen-typescript) is documented as early access.

With Kysely, you compose operations such as `selectFrom`, `where`, and `innerJoin`; it compiles them into SQL and parameters. The reusable unit is an unfinished query that carries the tables in scope and the result type so far.

The examples below follow one asset query as requirements arrive. For model mapping and related writes, see [query builders vs ORMs](/docs/comparisons/query-builder-vs-orm).

## Shared SQL helpers grow into an unchecked query builder

An asset list starts with an owner's assets, sorted by name and ID and limited to 50. Assume configured clients and an `asset` table with string `id`, `name`, and `owner_id` columns.

With Postgres.js, the statement is close to the SQL you would run in a console:

```ts
const rows = await sql<{ id: string; name: string }[]>`
  select id, name from asset
  where owner_id = ${ownerId}
  order by name, id
  limit 50
`
```

With Kysely, the same operations use its builder API:

```ts
const rows = await db
  .selectFrom('asset')
  .select(['id', 'name'])
  .where('owner_id', '=', ownerId)
  .orderBy('name')
  .orderBy('id')
  .limit(50)
  .execute()
// Inferred: { id: string; name: string }[]
```

Both handle this query well. Now the list needs an optional album filter and name prefix. The album filter adds both a join and a predicate; other requests should omit them.

<details>
<summary>Database types and request options for the following examples</summary>

```ts
interface Database {
  asset: { id: string; name: string; owner_id: string }
  album_asset: { album_id: string; asset_id: string }
  asset_tag: { asset_id: string; tag_id: string }
  tag: { id: string; name: string }
}
```

```ts
type AssetOptions = {
  ownerId: string
  albumId?: string
  includeTags: boolean
  namePrefix?: string
}
```

Assume a `Kysely<Database>` instance named `db`, one row per album/asset pair, and PostgreSQL. The prefix filter uses SQL LIKE-pattern semantics: `%` and `_` in the input remain wildcards.

### Add the optional join and filters

Put the shared query in a function. Kysely's `$if` applies each addition when its condition is true. The join changes the builder's type, which is why the addition lives in a callback rather than a reassigned variable; the non-null assertions restate the conditions checked outside the callbacks:

```ts
function matchingAssets(options: AssetOptions) {
  return db
    .selectFrom('asset')
    .where('asset.owner_id', '=', options.ownerId)
    .$if(options.albumId !== undefined, (qb) =>
      qb
        .innerJoin('album_asset', 'album_asset.asset_id', 'asset.id')
        .where('album_asset.album_id', '=', options.albumId!),
    )
    .$if(options.namePrefix !== undefined, (qb) =>
      qb.where('asset.name', 'like', options.namePrefix! + '%'),
    )
}
```

The join and its album predicate are composed together. Inside that branch, Kysely checks references against the added table.

Postgres.js keeps the same rules in one function. Return the join and predicates together so consumers reuse both:

```ts
function matchingAssetSql(options: AssetOptions) {
  const albumJoin =
    options.albumId !== undefined
      ? sql`inner join album_asset on album_asset.asset_id = asset.id`
      : sql``
  const albumFilter =
    options.albumId !== undefined
      ? sql`and album_asset.album_id = ${options.albumId}`
      : sql``
  const nameFilter =
    options.namePrefix !== undefined
      ? sql`and asset.name like ${options.namePrefix + '%'}`
      : sql``

  return sql`
    from asset ${albumJoin}
    where asset.owner_id = ${options.ownerId}
      ${albumFilter} ${nameFilter}
  `
}

const assets = await sql<{ id: string; name: string }[]>`
  select asset.id, asset.name ${matchingAssetSql(options)}
  order by asset.name, asset.id limit 50
`
const totals = await sql<{ count: number }[]>`
  select count(*)::integer as count ${matchingAssetSql(options)}
`
```

Both implementations centralize the filters and leave pagination out of the count. **The fragment carries SQL text and bound values; the Kysely builder also carries the tables in scope and the selected result type.** A checker can verify fragments in the forms it supports: [SafeQL's Postgres.js integration](https://safeql.dev/compatibility/postgres.js.html#support-matrix) excludes conditional fragment selection such as these ternaries.

### Keep a predicate connected to its join

Suppose a refactor removes `albumJoin` from `matchingAssetSql` but leaves `albumFilter`. Its returned fragment becomes:

```ts
// Inside matchingAssetSql, after the incomplete refactor:
return sql`
  from asset
  where asset.owner_id = ${options.ownerId}
    ${albumFilter} ${nameFilter}
`
```

Both callers still compile. When `albumId` is supplied, they reference `album_asset` without joining it and fail at the database. Keeping fragments together prevents consumers from forgetting one; it does not check the relationship between their contents.

The same edit to the builder produces a TypeScript error at the remaining reference:

```ts
db.selectFrom('asset')
  .where('asset.owner_id', '=', options.ownerId)
  .$if(
    options.albumId !== undefined,
    (qb) => qb.where('album_asset.album_id', '=', options.albumId!), // TypeScript error
  )
```

Restore the join inside the callback and that reference becomes valid again. **Kysely checks the predicate against the query being extended.** It does not prove that a join uses the right business rule or preserves row counts; those still need review and tests.

### Reuse the filters for a list, count, and export

The list chooses its fields and pagination after calling `matchingAssets`:

```ts
const assets = await matchingAssets(options)
  .select(['asset.id', 'asset.name'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .limit(50)
  .execute()
// Inferred: { id: string; name: string }[]
```

The total reuses the same filters without inheriting the list's limit:

```ts
function assetCount(options: AssetOptions) {
  return matchingAssets(options).select((eb) =>
    eb.cast<number>(eb.fn.countAll(), 'integer').as('count'),
  )
}
```

Execute with `await assetCount(options).executeTakeFirstOrThrow()`. PostgreSQL's integer cast makes the count a JavaScript number within the PostgreSQL integer range.

An export adds `owner_id` and omits pagination:

```ts
const exportedAssets = await matchingAssets(options)
  .select(['asset.id', 'asset.name', 'asset.owner_id'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .execute()
// Inferred: { id: string; name: string; owner_id: string }[]
```

**Each consumer keeps its own selections, ordering, and pagination, and each extension carries its query context and result type with it.** Kysely's builders are immutable, so extending one does not change another; adding `owner_id` to the export updates its inferred result without changing the list. Shared filter fragments give the SQL-template version the same reuse; the result type of each caller is still a separate annotation.

### Change one shared rule without changing the callers

Now albums gain a visibility setting: assets in an archived album must be excluded when filtering by that album. Assume an `album` table with `{ id: string; archived: boolean }` is added to the database declarations. Extend the existing album branch in `matchingAssets`:

```ts
.$if(options.albumId !== undefined, (qb) =>
  qb
    .innerJoin('album_asset', 'album_asset.asset_id', 'asset.id')
    .innerJoin('album', 'album.id', 'album_asset.album_id')
    .where('album_asset.album_id', '=', options.albumId!)
    .where('album.archived', '=', false),
)
```

The list, count, and export inherit the rule without caller edits. Their selected fields and pagination stay independent. Removing the new join while retaining `where('album.archived', ...)` produces a TypeScript error at that reference.

The SQL-template implementation makes the same change once, in `albumJoin` and `albumFilter`, and its callers also stay unchanged. The guarantee Kysely adds is checking those references as the shared query changes. Tests must still establish that the visibility rule is correct and applies to every intended request.

The remaining examples use the original schema and filters.

### Add optional nested tags

The list now needs tags when requested. Add a correlated JSON subquery using `jsonArrayFrom` from `kysely/helpers/postgres`:

```ts
function assetListing(options: AssetOptions) {
  return matchingAssets(options)
    .select(['asset.id', 'asset.name'])
    .$if(options.includeTags, (qb) =>
      qb.select((eb) =>
        jsonArrayFrom(
          eb
            .selectFrom('asset_tag')
            .innerJoin('tag', 'tag.id', 'asset_tag.tag_id')
            .select(['tag.id', 'tag.name'])
            .whereRef('asset_tag.asset_id', '=', 'asset.id')
            .orderBy('tag.name'),
        ).as('tags'),
      ),
    )
    .orderBy('asset.name')
    .orderBy('asset.id')
    .limit(50)
}
```

Execute with `await assetListing(options).execute()`. Inferred: `{ id: string; name: string; tags?: { id: string; name: string }[] }[]`.

Requested tags use `[]` when none exist; unrequested tags omit the key and subquery. The nested query keeps the outer result at one row per asset. Kysely checks the inner table references and their reference to the outer `asset`, then carries the nested result shape into `tags`.

The optional property reflects the runtime condition: callers must account for tags being absent. See [conditional selects](/docs/recipes/conditional-selects) and [nested relations](/docs/recipes/relations).

### What changed as the requirements grew?

| Requirement                                    | Kysely                                                                    | SQL templates in TypeScript                                               | Typed SQL files                                                          |
| ---------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Add a conditional join and predicate           | Extend the builder; references are checked against the added table.       | Compose fragments; the checker's supported forms decide what is verified. | Parameter-controlled predicates, or separate statement variants.         |
| Share filters across a list, count, and export | One function returns an unfinished query; each caller selects its fields. | Share fragments; keep each caller's result annotation aligned by hand.    | Repeat the rules in each file, or centralize them in a view or function. |
| Change a selected field                        | The caller's result type re-infers.                                       | A handwritten type drifts until analysis catches it.                      | Regenerate the typed call.                                               |
| Change one shared rule                         | Edit the function; callers inherit it with checked references.            | Edit the fragment; callers inherit it.                                    | Edit every statement that applies the rule.                              |

SQL-template clients already handle fragments and parameter binding. As helpers start choosing joins, aliases, predicates, and selections, the application takes on more of a builder's job: preserving which tables are in scope and which result shape each combination returns, as well as assembling valid SQL.

**An established builder supplies those composition rules and types; a custom layer supplies them through tests and maintenance.** Your shared functions return unfinished Kysely queries, and callers extend them with the same API. The equivalent custom layer must also keep its combinations, result contracts, and interpolation boundaries covered as they change.

## Typed SQL tools check a statement; Kysely checks a composition

### Can raw SQL be type-safe?

**Yes. Raw SQL can have static checking, generated types, and runtime validation.** These guarantees differ from a handwritten result annotation:

| Mechanism                        | What it checks                                                                                      | What it does not establish                                                                |
| -------------------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Handwritten result type          | TypeScript callers against the supplied type.                                                       | That the SQL returns that shape.                                                          |
| Runtime result schema            | Returned rows against the schema, when validation is enabled.                                       | That the statement and schema agree before execution.                                     |
| SQL-aware analysis or generation | Supported SQL against schema inputs; inferred output or a supplied contract, depending on the tool. | That arbitrary conditional composition is supported.                                      |
| Kysely builder inference         | Builder references and operations against database declarations; results as the query is extended.  | Actual returned values, raw-expression correctness, or success against the live database. |

A handwritten `sql<{ id: string; name: string }[]>` annotation can keep claiming `name` exists after the selection changes to `name as label`. Slonik's separately maintained result schema can reject an incompatible returned row when runtime validation is configured. Neither mechanism alone checks the SQL-to-result contract before execution. Kysely infers `label` from the changed selection, so a caller using `name` fails TypeScript checking; the [agent editing example below](#a-query-edit-an-agent-can-verify-locally) shows that change.

### Checking composed SQL

[SafeQL](https://safeql.dev/) checks supported SQL calls against PostgreSQL. For supported forms, its [Slonik integration](https://safeql.dev/compatibility/slonik.html#zod-schema-validation) compares SQL output with a supplied Zod schema during linting, so a stale contract is caught before execution. **The unit a SQL checker verifies is a statement it can see whole.** Check its supported composition forms against your actual queries, including conditional fragments like the album filter above.

Kysely's checks depend on accurate database declarations and the driver's runtime value mapping. [Generating database types](/docs/generating-types) keeps those declarations aligned. Kysely does not validate returned rows or convert values to match declared types; runtime validation can still be useful at application boundaries. Raw `sql<T>` expressions in Kysely also declare their result type explicitly; SafeQL's [Kysely integration](https://safeql.dev/compatibility/kysely.html) checks supported raw forms. Result inference belongs to particular tools, not to query builders as a category.

### A schema change finds every affected query

Rename `asset.name` to `asset.title` in a migration. Every SQL string that selects, filters, or orders by `name` still compiles; the failures arrive at runtime, one statement at a time, and a search for `name` across the codebase is the checker. A SQL-aware linter connected to the migrated database reports the statements it can analyze, and a generator rejects them on the next run.

With Kysely, regenerate the declarations and TypeScript lists every reference to the old column: the shared filter, the list, the export, and the raw expression below that references it through `eb.ref`. The same list is what a reviewer or an agent works through, in one pass, before the change reaches a database.

## One type check reports every error; the database reports one

**Kysely checks query edits through TypeScript without per-query generation or a live database connection.** PostgreSQL reports errors with a [message, hint, and position](https://www.postgresql.org/docs/current/protocol-error-fields.html), but generally stops at the first error in a statement.

With the asset schema above, this statement has three independent errors:

```sql
select id, nmae
from asset
where owner_id = 42
  and label like 'F%'
order by name;
```

PostgreSQL first reports the missing `nmae` column. Correct it to `name` and resubmit: comparing the text `owner_id` to an integer now fails. Change `42` to a string and resubmit: the missing `label` column is reported next. These successive diagnostics were checked against PostgreSQL.

In a long query assembled from fragments, the reported position refers to the assembled SQL. You must also trace that position back to the fragment or helper that produced it. Each correction can mean rebuilding the statement and asking the database again.

Kysely reports these mistakes in one TypeScript check, at the operations that introduce them:

```ts
db.selectFrom('asset')
  .where('asset.owner_id', '=', 42) // Error: owner_id requires a string.
  .where('asset.label', 'like', 'F%') // Error: label is not a column.
  .select(['asset.id', 'asset.nmae']) // Error: nmae is not a column.
  .orderBy('asset.name')
```

TypeScript 6 and 7 both report all three operations in this example. **Feedback arrives while editing, without submitting the query or reaching the application path that executes it.** Completion also offers the tables, columns, and operations available at the current point in the builder.

SafeQL supplies editor diagnostics for supported SQL, and a generator rejects an invalid statement before application execution. Assess the actual feedback loop: where an error appears, how many problems one check exposes, and whether the checked form covers your conditional query. Kysely's compile-time checks do not replace database validation: raw expressions, stale schema declarations, constraints, and SQL rules beyond its types can still fail at the database.

### Query changes can require generation even when the schema is stable

Adding a selection or renaming an alias can require refreshing generated query code even when the schema is unchanged. A watcher can automate that step. Compare the schema inputs and query-edit workflow:

| Tool                                                                                      | Schema input for checking                                                  | What happens after a query edit?                                                                                |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Kysely                                                                                    | Existing TypeScript database declarations.                                 | TypeScript checks the builder and re-infers its result; no per-query generation or live connection is required. |
| [PgTyped](https://pgtyped.dev/docs/cli)                                                   | A running PostgreSQL database.                                             | Run generation, manually or in watch mode, to refresh typed query code.                                         |
| [Prisma TypedSQL](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/typedsql) | A database connection for generation.                                      | Refresh query functions with `prisma generate --sql`, optionally in watch mode.                                 |
| [sqlc](https://docs.sqlc.dev/en/stable/howto/generate.html)                               | Local schema/query files by default; database-backed analysis is optional. | Run generation to refresh application code, including TypeScript plugin output.                                 |

Adding `owner_id` to the Kysely export uses the existing declarations; TypeScript immediately re-infers the result. Schema changes still require updating or regenerating declarations, and runtime behavior still needs database tests.

### A query edit an agent can verify locally

Suppose an agent must rename the export's `name` field to `label` without changing the list or count. It changes only the export selection:

```ts
const exportedAssets = await matchingAssets(options)
  .select(['asset.id', 'asset.name as label', 'asset.owner_id'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .execute()
// Inferred: { id: string; label: string; owner_id: string }[]

exportedAssets.map((asset) => asset.name) // TypeScript error
exportedAssets.map((asset) => asset.label) // string[]
```

The compiler identifies stale callers using the existing database declarations. The agent repairs those callers and checks again without generating a query API or connecting to a database. The earlier missing-join edit produces feedback at the predicate instead. **A type check is a verification step an agent can run on every edit, with nothing but the repository.** SQL-aware raw-SQL tools provide comparable feedback for the forms they support, with a database or a generation step in the loop.

Database tests still establish that the list and count use the same rules, the export has the intended fields, and optional joins preserve row counts. TypeScript checks references and result shapes, not the intended access policy.

## Values bind safely everywhere; syntax needs a boundary either way

**All three workflows bind values safely. Dynamic SQL syntax needs a separate boundary.** Owner IDs and prefixes are values; column names and sort directions are syntax. A request's sort choice should select from supported operations.

For example, accept only two ordering choices and reject other input:

```ts
function parseSort(value: unknown): 'name' | 'id-desc' {
  if (value === 'name' || value === 'id-desc') return value
  throw new Error('Unsupported sort')
}

const sort = parseSort(requestSort)
const query = matchingAssets(options).select(['asset.id', 'asset.name'])
const sorted =
  sort === 'name'
    ? query.orderBy('asset.name').orderBy('asset.id')
    : query.orderBy('asset.id', 'desc')
```

Postgres.js chooses between trusted fragments just as safely:

```ts
const ordering =
  sort === 'name' ? sql`asset.name, asset.id` : sql`asset.id desc`

const rows = await sql<{ id: string; name: string }[]>`
  select asset.id, asset.name ${matchingAssetSql(options)}
  order by ${ordering} limit 50
`
```

Both keep request text out of SQL syntax. Kysely additionally checks the column references against the query. SQL files can encode a fixed set of sort choices with SQL expressions or separate statements.

Passing request text to [Postgres.js `sql.unsafe`](https://github.com/porsager/postgres#unsafe-raw-string-queries) or Kysely's `sql.raw` bypasses those boundaries. Parameter binding elsewhere does not protect that text, and a TypeScript cast does not validate it. **Safe parameterization is not the reason to adopt a builder; raw SQL has it. The checked composition API is.**

## Performance belongs to the statement, not the authoring tool

**Compare statements and execution plans to assess database performance.** A builder does not inherently make a query faster, and handwritten SQL does not inherently produce a better plan. The joins, predicates, indexes, row counts, and database behavior still matter.

For a request with only an owner filter, Kysely exposes the statement and parameters before execution:

```ts
const compiled = matchingAssets({ ownerId: 'owner-1', includeTags: false })
  .select(['asset.id', 'asset.name'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .limit(50)
  .compile()
// compiled.parameters: ['owner-1', 50]
```

```sql title="compiled.sql (formatted)"
select "asset"."id", "asset"."name"
from "asset"
where "asset"."owner_id" = $1
order by "asset"."name", "asset"."id"
limit $2
```

This request emits only the owner filter, ordering, and limit. Use [`.compile()`](/docs/recipes/splitting-query-building-and-execution) to inspect other combinations before executing them. Compare plans and timings against representative data, and measure application overhead separately if it matters to your workload. The [comparison fixtures](https://github.com/kysely-org/kysely/tree/112f4f7a3ddd863968a7b92d4d5d525db670ae33/site/scripts/comparison-checks/postgres) establish equivalent results, not a speed ranking.

Both approaches let you rewrite a join as a subquery or adjust the ordering. With Kysely, that edit stays in the shared builder and updates the inferred result for its callers.

## Raw expressions keep SQL where it reads best

A builder can cover most of a statement while SQL expresses one local operation. For example, add a lowercase name to the shared query:

```ts
import { sql as kyselySql } from 'kysely'

const normalizedAssets = await matchingAssets(options)
  .select(['asset.id', 'asset.name'])
  .select((eb) =>
    kyselySql<string>`lower(${eb.ref('asset.name')})`.as('normalized_name'),
  )
  .execute()
// Inferred: { id: string; name: string; normalized_name: string }[]
```

The builder still checks the `asset.name` reference and composes the filters. The SQL fragment's `string` result is an explicit declaration; Kysely does not check the `lower(...)` grammar or verify that result type. See [raw expressions](/docs/recipes/raw-sql) and the [SQL template API](https://kysely-org.github.io/kysely-apidoc/interfaces/Sql.html).

**Adopting a builder for the parts that benefit from composition does not require giving up SQL for the parts that don't.** Using an expression never turns the whole statement into a raw query.

## Production code draws the same line

OpenClaw's [contributor guide](https://github.com/openclaw/openclaw/blob/28340c41f8b88ae6d11488e523808315319747b5/AGENTS.md#L71) states the division directly: use Kysely for ordinary SQLite access, and limit raw SQL to schema, migrations, bootstrap, and justified primitives. **Statements that stay fixed are written as SQL; queries that application code composes go through the builder.** The same guide is written for coding agents, which makes the checked feedback loop above part of the policy.

The composition pattern from the asset example appears in larger codebases:

- [Immich](https://github.com/immich-app/immich/blob/0733cc10ee7a0c8ebd5d37b1804b5c28944b7cdd/server/src/repositories/asset.repository.ts#L570-L624) composes optional relation selections and a lateral subquery for stacked assets. Different requests extend the query with different data.
- [Open Collective](https://github.com/opencollective/opencollective-api/blob/0a59b37c8b33574ee8d9d9a586d5a19506fd5921/server/graphql/v2/query/collection/OrdersCollectionQuery.ts#L780-L826) conditionally adds currency conversion through a correlated exchange-rate lookup. A request option changes the selected expression.
- [Docmost](https://github.com/docmost/docmost/blob/7bef7b1a00d31991f009865ec14c8d06540eb1f0/apps/server/src/database/repos/page/page-permission.repo.ts#L325-L373) composes recursive ancestors for page restrictions. Traversal, joins, and filtering use the same builder interface as simpler queries.

Each of these could be written as raw SQL. The builder's value is carrying checked references and results through the application code that composes them.

## Other practical considerations

<details>
<summary>SQL files and tool-specific syntax</summary>

SQL-file tools can introduce syntax that needs translation before the database can analyze it. For example, [sqlc's parameter macros](https://docs.sqlc.dev/en/stable/reference/macros.html) name inputs and control their nullability:

```sql title="sqlc input"
select id, name
from asset
where owner_id = sqlc.arg(owner_id)
  and (sqlc.narg(name_prefix)::text is null
    or name like sqlc.narg(name_prefix) || '%');
```

For PostgreSQL, expansion produces:

```sql title="Database SQL"
select id, name
from asset
where owner_id = $1
  and ($2::text is null or name like $2 || '%');
```

The source needs macro expansion before it can run in a SQL console, then parameter values. [PgTyped's parameter expansions and required-parameter syntax](https://pgtyped.dev/docs/sql-file) also add tool syntax. Ordinary `CASE` expressions remain database SQL, and metadata stored only in comments does not change executable syntax.

Kysely also requires compilation before its output runs in a SQL console. With either workflow, inspect the database-facing statement, supply parameters, tune it, then carry changes back into the source. Compare the abstraction you learn with the checking and reuse it supplies.

</details>

<details>
<summary>Typed SQL files: shared filters, a count, and optional tags</summary>

A SQL-file implementation can keep the statement fixed and let parameters enable its filters. This Prisma TypedSQL example uses `exists` for album membership:

<details>
<summary>findAssets.sql</summary>

```sql title="findAssets.sql"
-- @param {String} $1:ownerId
-- @param {String} $2:albumId?
-- @param {String} $3:namePrefix?
select asset.id, asset.name
from asset
where asset.owner_id = $1
  and ($2::text is null or exists (
    select 1 from album_asset
    where album_asset.asset_id = asset.id
      and album_asset.album_id = $2
  ))
  and ($3::text is null or asset.name like $3 || '%')
order by asset.name, asset.id
limit 50;
```

</details>

After `prisma generate --sql`, call the generated `findAssets` through `prisma.$queryRawTyped`, passing the owner ID and nullable filter parameters. The inputs and returned columns are typed from the SQL. Other SQL-file tools have their own parameter syntax and analysis workflow.

A count needs the same matching rules with a different selection and no limit:

<summary>countAssets.sql</summary>

```sql title="countAssets.sql"

-- @param {String} $2:albumId?
-- @param {String} $3:namePrefix?
select count(*)::integer as count
from asset
where asset.owner_id = $1
  and ($2::text is null or exists (
    select 1 from album_asset
    where album_asset.asset_id = asset.id
      and album_asset.album_id = $2
```

**Checking both statements does not establish that their filtering rules agree.** A new visibility rule must reach the list, count, and export. In these separate files, that means changing each statement. A shared database view or function can centralize the rule too, with its own schema and deployment lifecycle. Tools with preprocessing or composition facilities offer other options.

Kysely keeps the common rule in a TypeScript function whose returned builder each consumer can extend. SQL files keep each complete statement together. The maintenance question is where the common rule lives as more outputs need it.

**Optional output from SQL files**

A fixed statement can return a tags column and use `CASE` to choose its value. That still selects the column: returning `null` differs from omitting `tags`. Either contract can be useful. To preserve this example's absent-key contract directly in SQL, use a second statement that selects tags and choose between the typed calls in TypeScript. An application mapper could remove the key instead.

<details>
<summary>The SQL file with tags and its application wrapper</summary>

```sql title="findAssetsWithTags.sql"
-- @param {String} $1:ownerId
-- @param {String} $2:albumId?
-- @param {String} $3:namePrefix?
select asset.id, asset.name,
  coalesce((
    select json_agg(tag_rows)
    from (
      select tag.id, tag.name
      from asset_tag
      inner join tag on tag.id = asset_tag.tag_id
      where asset_tag.asset_id = asset.id
      order by tag.name
    ) as tag_rows
  ), '[]'::json) as tags
from asset
where asset.owner_id = $1
  and ($2::text is null or exists (
    select 1 from album_asset
    where album_asset.asset_id = asset.id
      and album_asset.album_id = $2
  ))
  and ($3::text is null or asset.name like $3 || '%')
order by asset.name, asset.id
limit 50;
```

<details>
<summary>Database support for checking: PostgreSQL, MySQL, SQLite, and SQL Server</summary>

**Executing SQL and analyzing its result types are different capabilities.** A client's engine support does not establish its checker's support. Preparing or describing a statement can obtain metadata without executing the application query, but the available information differs by engine.

| Database                                                                                                                                    | Metadata available without executing the application query                                                                      | Limits to account for                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| [PostgreSQL](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY)                                            | The extended protocol's statement `Describe` returns parameter and result-column metadata before `Execute`.                     | That metadata alone does not describe every TypeScript-level property, such as a nested JSON object's shape.                                 |
| [MySQL](https://dev.mysql.com/doc/c-api/8.4/en/mysql-stmt-result-metadata.html)                                                             | Prepared-statement result metadata is available after preparation and before execution.                                         | Pre-execution types are determined by the optimizer; the documented types after execution can differ.                                        |
| [SQLite](https://www.sqlite.org/c3ref/column_decltype.html)                                                                                 | A statement can be prepared without stepping through its results; declared-type metadata is available for direct table columns. | The declared-type API returns no type for an expression or subquery. Dynamic value types and computed expressions need additional analysis.  |
| [SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-describe-first-result-set-transact-sql) | `sp_describe_first_result_set` statically analyzes a batch's first result set.                                                  | Some constructs cannot be described, including statements using temporary tables; control flow can also prevent a usable result description. |

This summarizes database facilities, not what every checker uses. Tools can supplement metadata with catalog queries or their own SQL analysis, as sqlc does. For a particular tool, check its engine and driver support, parameter inference, nullability, expression types, and JSON handling, and whether checking prepares statements, analyzes them locally, or executes anything.

## Choosing raw SQL or Kysely

**Choose raw SQL when complete statements are the clearest unit of work for your team.** SQL templates keep them beside application code; typed SQL files suit statements reviewed and edited in a SQL workflow. A complex recursive query can be a good SQL file. Runtime schemas, SQL-aware checkers, and generated APIs supply strong guarantees for the statements they can see whole.

The cost of Kysely is another API between you and the statement. Your team must learn its expression and composition rules, keep database declarations aligned with the schema and driver mappings, and supply explicit types for raw expressions. Complete, specialized statements may be easier to maintain as SQL. Kysely also does not choose indexes, prove that joins preserve row counts, or validate returned values. A query being long or complex is not itself a reason to move it.

Try one endpoint whose filters are repeated across a list and count. Add a shared rule, change a selected alias, and introduce a conditional join. Compare the edits required, the feedback loop, and the resulting statements. Before switching the caller, compare rows, ordering, pagination, and optional fields. Other queries can continue using their existing clients.

**Choose Kysely when queries keep acquiring variations and shared rules, and you want the composition layer checked rather than maintained.**
