# Kysely vs Drizzle ORM

Kysely and Drizzle ORM start from the same premise: SQL is the interface, and TypeScript should check it. Both compose statements through a typed API and bind values as parameters, with no generated client. **Both infer the result of a query; Drizzle knows what each column is, and Kysely also knows whether the query can see it.**

Drizzle is the most downloaded ORM on npm: [47.9 million drizzle-orm downloads](https://api.npmjs.org/downloads/point/2026-10-31:2026-11-06/drizzle-orm) in the week of October 31, 2026, ahead of [`@prisma/client`](https://api.npmjs.org/downloads/point/2026-10-31:2026-11-06/@prisma/client) and [Kysely](https://api.npmjs.org/downloads/point/2026-10-31:2026-11-06/kysely). All counts include installs pulled in by other packages. Its team builds it [from Ukraine](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/sustainability.mdx#L256-L258), and kept shipping through the war. **Drizzle brought SQL-first TypeScript to the mainstream, and every SQL-first library, Kysely included, has a bigger audience for it.**

Drizzle's builder is SQL-like in clause order and JavaScript in the rest: columns are objects, operators are imported functions, and aliases are variables. Kysely writes SQL's own operators and aliases, and carries the tables in scope through every step, so a reference is checked where it is written.

The differences that cost most are the quiet ones. A JSON or CASE expression that Drizzle writes as an annotated template can return a wrong value under a type that still compiles, and in Drizzle's dynamic mode [a second `where()` replaces the first](#shared-queries-branch-without-mutation) with no error, even when the first was a tenant filter.

Kysely is a type-safe SQL query builder. Drizzle calls itself [a headless TypeScript ORM](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/overview.mdx#L8); in this site's terms it is a [data framework](/docs/comparisons/query-builder-vs-orm#orms-data-frameworks-and-plain-objects), the familiar stack: models, which Drizzle calls tables, migrations generated from them, a relational query API, and a SQL-style query builder. This page compares that builder with Kysely.

Drizzle here means 0.45.4 and 1.0.0-rc.5, its stable release and its release candidate in November 2026. Its behavior below is the same in both unless stated.

## Both infer the result of a join

Assume configured Kysely (`db`) and Drizzle (`drizzleDb`) clients over the same two tables:

<details>
<summary>Database interface and Drizzle table objects</summary>

Kysely's `Database` interface is types only, handwritten or [generated](/docs/generating-types) from the database:

```ts
interface Database {
  person: { id: number; first_name: string; age: number | null }
  pet: { id: number; name: string; owner_id: number }
}
```

Drizzle's tables are runtime objects, which Drizzle Kit also reads to generate migrations:

```ts
import { integer, pgTable, text } from 'drizzle-orm/pg-core'

const person = pgTable('person', {
  id: integer().notNull(),
  first_name: text().notNull(),
  age: integer(),
})
const pet = pgTable('pet', {
  id: integer().notNull(),
  name: text().notNull(),
  owner_id: integer().notNull(),
})
```

</details>

Select adults with their pets' names, keeping people who have no pet.

With Drizzle:

```ts
const rows = await drizzleDb
  .select({ first_name: person.first_name, pet_name: pet.name })
  .from(person)
  .leftJoin(pet, eq(pet.owner_id, person.id))
  .where(gte(person.age, 18))
  .orderBy(person.first_name)
```

With Kysely:

```ts
const rows = await db
  .selectFrom('person')
  .leftJoin('pet', 'pet.owner_id', 'person.id')
  .select(['person.first_name', 'pet.name as pet_name'])
  .where('person.age', '>=', 18)
  .orderBy('person.first_name')
  .execute()
```

The rows match, and so do the inferred types: `{ first_name: string; pet_name: string | null }[]`. Both libraries make `pet_name` nullable because the join is a left join. Drizzle can go further: [select the pet's columns as a nested object](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/joins.mdx#L278-L279), and the pet is one object that is `null` as a whole. Kysely makes each joined column nullable on its own. **Written correctly, the two queries are equivalent; the libraries differ in what the compiler says when a query is wrong.**

## Drizzle checks each column; Kysely checks the query

Production queries collect their filters. Put the query above in a function with an optional pet name, collecting conditions the way [Drizzle's guide](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/guides/conditional-filters-in-query.mdx#L76-L93) does. Then a later change drops the pet's name from the result, and the join with it:

```ts
function matchingPeople(options: { petName?: string }) {
  const filters = [gte(person.age, 18)]
  if (options.petName) filters.push(eq(pet.name, options.petName))

  return drizzleDb
    .select({ first_name: person.first_name })
    .from(person)
    .where(and(...filters))
}
```

It compiles, and it runs for every request without a pet name. A request with one fails in PostgreSQL: the filter still reads `pet`, and the change never touched that line. The same function after the same change in Kysely:

```ts
function matchingPeople(options: { petName?: string }) {
  let query = db
    .selectFrom('person')
    .select('person.first_name')
    .where('person.age', '>=', 18)

  if (options.petName) {
    // TypeScript error: pet is not available in this query.
    query = query.where('pet.name', '=', options.petName)
  }
  return query
}
```

A Drizzle column is a value. `pet.name` has one type wherever it is passed, `eq()` returns a condition that records no table, and `select()` is called before `from()`, so a selection is typed before the query has a table. Kysely's `selectFrom` comes first, and every later method is typed against the tables and aliases accumulated so far. **Drizzle's compiler accepts a column object in any query; Kysely's checks every reference written on the query's own builder.**

The gap is structural, not a missing feature, and it is a choice. Asked in 2024 for [a fully type-safe query builder](https://github.com/drizzle-team/drizzle-orm/discussions/2409), Drizzle's team [answered](https://github.com/drizzle-team/drizzle-orm/discussions/2409#discussioncomment-9614641) that it had "deliberately switched to our current API" because "it will provide better DX than huge type errors that are quite hard to understand for average TS developers", and that full type safety would need joins to come before the selection, "deviating the API from SQL even more".

By that account, closing the gap means changing the order every query is written in. Kysely's order is the one PostgreSQL [processes a query in](https://www.postgresql.org/docs/current/sql-select.html): the `FROM` list first, the output expressions after it. **Kysely puts `from` first for the reason SQL evaluates it first: a query's inputs have to be known before its outputs can be checked.** Its bet is that a mistake reported at compile time costs less than the same mistake at runtime, for a developer and for a coding agent alike.

The same design decides where a name is declared. SQL writes an alias where the table is used, `join person as other`, and so does Kysely: `.innerJoin('person as other', 'other.age', 'person.age')`. In Drizzle a column has to hang off an object before a selection or a join condition can name it, so an alias, a derived table, and a CTE are each declared in a variable ahead of the query.

A Drizzle CTE then takes three steps: `$with('adults').as(...)` declares it, `.with(adults)` attaches it, and `.from(adults)` uses it. A query that skips the middle step compiles and fails in PostgreSQL. Kysely's `.with('adults', ...)` declares the CTE and puts it in scope in one call, and `selectFrom('adults')` without it is a type error. **Drizzle keeps SQL's clause order and builds the rest from JavaScript values; Kysely keeps SQL's words, scope, and single statement, and moves one clause to check them.**

The split is the same wherever a reference lands. That includes ORDER BY, GROUP BY, HAVING, an update's SET, a delete's WHERE, and these:

| Invalid reference                                                   | Kysely                              | Drizzle                                                     |
| ------------------------------------------------------------------- | ----------------------------------- | ----------------------------------------------------------- |
| Select `pet.name` without joining `pet`                             | TypeScript error.                   | Passes TypeScript; Drizzle throws while generating the SQL. |
| Filter on `pet.name` without joining `pet`                          | TypeScript error.                   | Passes TypeScript; PostgreSQL rejects the query.            |
| Join a subquery aliased `pets`, then compare `pet.owner_id` in `on` | TypeScript error.                   | Passes TypeScript; PostgreSQL rejects the query.            |
| Partition a window by a column of a table the query never joined    | TypeScript error.                   | Passes TypeScript; PostgreSQL rejects the query.            |
| Reference a table the query never joined inside a `sql` fragment    | TypeScript error, through `eb.ref`. | Passes TypeScript; PostgreSQL rejects the query.            |

Drizzle catches the first of these itself, with an error that names the table and asks whether you forgot to join it. The check exists; it runs while generating the SQL, after the compiler has passed the code. Harminder Virk, the creator of AdonisJS, [documented the first three rows in December 2023](https://github.com/thetutlage/meta/discussions/8), and all three still pass TypeScript in 0.45.4 and 1.0.0-rc.5.

**Every row in that table is a failed run with Drizzle and a compile error with Kysely.** PostgreSQL [stops at the first error](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY), so unchecked mistakes surface one execution at a time, against a database. The compiler reports them together, before a connection is opened, which is also the loop a coding agent can run on every edit.

<details>
<summary>Operand types, select alias scope, and RETURNING</summary>

Operands follow the same split. Drizzle's operators are imported functions, `inArray` for `IN` and `ne` for `<>`, and each checks a literal against its column: `eq(person.id, 'one')` is a type error, while `eq(person.first_name, person.id)`, a text column compared with an integer column, compiles and PostgreSQL rejects it. So does `where(and(person.id))`, a column that is not a condition.

Kysely takes SQL's operators as strings and completes them in place, and an expression past a plain comparison is written inside an `(eb) => ...` callback. Its expression builder checks an expression against an expression, so `eb('first_name', '=', eb.ref('id'))` is a type error, and so is a condition that is not boolean.

PostgreSQL computes `WHERE` and `HAVING` before the selection, so a select alias is not visible to them: Kysely's `where` and `having` reject one at compile time, and `groupBy` and `orderBy` accept it. Drizzle compiles all four. An expression named with `.as('name')` and passed to `where()` is sent as `where "name" = $1`, and PostgreSQL rejects it; reached through the `where` callback, Drizzle repeats the expression and the query runs.

One reference failure is quiet: `returning({ id: pet.id })` on an insert into `person` compiles and returns the person's `id`, because Drizzle writes the column without its table.

</details>

Most of these failures are loud once a test runs the branch that builds the reference; `matchingPeople` above passes every test that leaves the pet name out.

The failures further down this page are quiet: [a misspelled JSON key](#json-traversal) returns `null`, [a CASE without an ELSE](#case-expressions) returns `null` under a `string` type, a `limit()` on one branch of [a shared query](#shared-queries-branch-without-mutation) applies to the other, and a second `where()` drops the first. **A wrong reference fails only when its branch runs; an unchecked template or a mutated builder returns the wrong result with no error at all.**

**No query builder is perfectly type-safe, and Kysely is no exception; type safety is what it is built around, and every gap is treated as work to do.**

<details id="where-kyselys-checks-stop">
<summary>Where Kysely's checks stop</summary>

Kysely's check is made where a reference is written, on a builder that knows the query, and it stops there. A reference written with `sql.ref` or as template text, a [dynamic reference](https://kysely-org.github.io/kysely-apidoc/classes/DynamicModule.html), an expression built ahead of time on a standalone `expressionBuilder`, and a helper whose builder parameter declares more tables than the caller's query has are all taken on trust. The reference shorthands `whereRef`, `onRef`, and the three-argument join take two column names without comparing their types.

Its scope rules are PostgreSQL's on every dialect. It rejects a select alias in `where` and `having`; MySQL accepts one in `HAVING`, SQLite in `WHERE` as well, and Kysely makes you repeat the expression there.

Column objects pay Drizzle back here. An editor can rename one and jump to its declaration, and Drizzle qualifies it with its table in a join. Kysely's references are strings read by the type system: completed and checked, yet an unqualified `id` after joining two tables that both have one compiles, and PostgreSQL rejects it as ambiguous.

Two more Kysely gaps are quiet: `where('age', '=', null)` compiles and matches no rows, where Drizzle's `eq(person.age, null)` is a type error, and a `union` whose sides list the same columns in a different order returns values under the wrong keys, where Drizzle throws before sending it.

</details>

## Kysely builds the expressions Drizzle writes as templates

Past selections, joins, filters, and plain aggregates, Drizzle's builder hands over to its [`sql` template](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/sql.mdx#L25). JSON traversal, CASE, aggregate FILTER, and window clauses are SQL text with a result type declared by hand. Kysely has a builder for each, so the references are checked, and for JSON and CASE the type is inferred.

### JSON traversal

A `user_settings.profile` column holds JSON typed as `Profile`, which is `{ addresses: { city: string }[] }`, in both libraries: in Kysely's `Database` interface, and through `jsonb().$type<Profile>()` on Drizzle's `settings` table object. Read the first address's city. With Drizzle:

```ts
const rows = await drizzleDb
  .select({
    id: settings.id,
    first_city: sql<string | null>`
      ${settings.profile}->'addresses'->0->'city'
    `.as('first_city'),
  })
  .from(settings)
// The string | null type is supplied by hand.
```

With Kysely:

```ts
const rows = await db
  .selectFrom('user_settings')
  .select('id')
  .select((eb) =>
    eb.ref('profile', '->').key('addresses').at(0).key('city').as('first_city'),
  )
  .execute()
// Inferred: { id: number; first_city: string | null }[]
```

Kysely infers `string | null` because the array may be empty. Now misspell `city` as `ctiy`:

```ts
// Drizzle: compiles, runs, and returns null for every row.
sql<string | null>`${settings.profile}->'addresses'->0->'ctiy'`

// Kysely: TypeScript error, ctiy is not a key of an address.
eb.ref('profile', '->').key('addresses').at(0).key('ctiy')
```

**A misspelled JSON key is a silent `null` in Drizzle and a compile error in Kysely.** Kysely also rejects reading `city` before indexing `addresses`. Both libraries trust the declared `Profile` type; neither validates the stored JSON.

### CASE expressions

Label each person by age, including people whose age is unknown. With Drizzle:

```ts
const query = drizzleDb
  .select({
    id: person.id,
    age_group: sql<string>`case
      when ${gte(person.age, 18)} then ${'adult'}
      when ${lt(person.age, 18)} then ${'minor'}
      else ${'unknown'}
    end`.as('age_group'),
  })
  .from(person)
```

With Kysely:

```ts
const query = db
  .selectFrom('person')
  .select('id')
  .select((eb) =>
    eb
      .case()
      .when('age', '>=', 18)
      .then('adult')
      .when('age', '<', 18)
      .then('minor')
      .else('unknown')
      .end()
      .as('age_group'),
  )
// Inferred: { id: number; age_group: string }[]
```

Both return the same labels. Now remove the `else`. Kysely infers `string | null`, and a caller's `.toUpperCase()` stops compiling until it handles the null. Drizzle's `sql<string>` is unchanged, still claims a string, and a person with no age returns `null`. Drizzle's [own guide](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/guides/update-many-with-different-value.mdx#L17) writes CASE as a template, and the request for [native CASE support](https://github.com/drizzle-team/drizzle-orm/issues/1065) has been open since August 2023. **A `sql<T>` annotation is a claim about the expression; Kysely's inferred type is derived from it.**

### Aggregate filters and windows

Count images and videos in one row, the shape [Immich](https://immich.app/) builds with Kysely. Each count is one selection:

```ts
// Drizzle: a template.
sql<string>`count(*) filter (where ${eq(asset.kind, 'image')})`

// Kysely: a builder.
eb.fn.countAll<string>().filterWhere('kind', '=', 'image')
```

Both declare `string` here, as `pg` returns a PostgreSQL `bigint` by default; Kysely's `countAll` takes the type as a parameter and converts nothing. Drizzle's [`count()` with `.where()`](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/guides/count-rows.mdx#L127-L140) and [`db.$count(table, filter)`](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/mdx/%24count-pg.mdx#L3-L15) cover a single conditional count and return it as a `number`. Its `count()` has no FILTER or OVER methods, so several filtered aggregates in one row, or any window, are templates.

In Kysely a window is `.over()` on the aggregate, and a partition by a table the query never joined is the fourth row of the table above. **A filtered or windowed aggregate is a template in Drizzle and a builder in Kysely: both declare its result type, and only the builder checks its references against the query.**

## Kysely's escape hatch keeps references checked

Kysely does not cover all of SQL either; it covers what applications write most, extends that coverage release by release, and types the escape hatch for the rest. Neither library's `like` takes an `ESCAPE` clause, so both write one in a `sql` template that binds its values as parameters. They differ in what an interpolated reference is:

```ts
// Drizzle: compiles. pet is not in the query, and PostgreSQL rejects it.
drizzleDb
  .select({ id: person.id })
  .from(person)
  .where(sql<boolean>`${pet.name} like ${pattern} escape '!'`)

// Kysely: eb.ref is checked against the tables in scope.
db.selectFrom('person')
  .select('id')
  .where(
    (eb) => sql<SqlBool>`${eb.ref('first_name')} like ${pattern} escape '!'`,
  )
// Replace first_name with pet.name: TypeScript error, pet is not joined.
```

Neither library checks a fragment's grammar or its declared result type. **Drizzle's `sql` template carries SQL text, bound values, and a declared type; Kysely's also carries the references `eb.ref` checked.** Wrap repeated fragments in [reusable helpers](/docs/recipes/reusable-helpers) that take `Expression<T>`; see the [`sql` API](https://kysely-org.github.io/kysely-apidoc/interfaces/Sql.html) for more. For whole queries written as templates, see [query builder vs raw SQL](/docs/comparisons/query-builder-vs-raw-sql).

## Nested results stay in the same builder

Drizzle's [relational queries](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/rqb.mdx#L7-L12) are the shortest way to read a declared relation. Return each person with their first two pets by name, in 1.0 syntax:

```ts
const rows = await drizzleDb.query.person.findMany({
  columns: { first_name: true },
  with: {
    pets: { columns: { name: true }, orderBy: { name: 'asc' }, limit: 2 },
  },
})
// { first_name: string; pets: { name: string }[] }[]
```

One statement, an inferred nested type, and `[]` for a person with no pets. Kysely returns the same rows and the same type with `jsonArrayFrom`, from `kysely/helpers/postgres`:

```ts
const rows = await db
  .selectFrom('person')
  .select((eb) => [
    'person.first_name',
    jsonArrayFrom(
      eb
        .selectFrom('pet')
        .select('pet.name')
        .whereRef('pet.owner_id', '=', 'person.id')
        .orderBy('pet.name')
        .limit(2),
    ).as('pets'),
  ])
  .execute()
// { first_name: string; pets: { name: string }[] }[]
```

Drizzle's version is shorter, and it is a different API from the one in the rest of this page: relations are declared ahead of the query, filters and ordering are objects, not operators, and 1.0 [redesigned it](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/relations-v1-v2.mdx#L9). It is a model API; [SQL query builder vs ORM](/docs/comparisons/query-builder-vs-orm) compares that kind of API with a query builder.

It reads declared relations, and in 1.0 a per-parent count fits beside them, as a [`db.$count` subquery in `extras`](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/rqb.mdx#L917-L932). A read that needs a join outside the relations or a GROUP BY moves to the SQL-style builder, and for other aggregates [the docs](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/rqb.mdx#L822) point there too: "As of now aggregations are not supported in extras, please use core queries for that." There a nested array is a hand-written `json_agg` with a `coalesce` fallback and a declared type.

In Kysely the nested subquery is an ordinary query: join inside it, aggregate it, filter it, with the same methods and the same checks. **Drizzle's relational API is a second query language beside its SQL builder; Kysely nests results in the builder it already has.** The helpers are per dialect, and a driver that returns JSON as text needs [`ParseJSONResultsPlugin`](/docs/recipes/relations#the-json-data-type-and-functions). See [nested relations](/docs/recipes/relations).

## Shared queries branch without mutation

Drizzle mutates the shared base:

```ts
const base = drizzleDb
  .select({ id: person.id })
  .from(person)
  .where(gte(person.age, 18))

const preview = base.limit(1)
const everyone = base
// Both now have LIMIT 1.
```

Kysely branches independently:

```ts
const base = db.selectFrom('person').select('id').where('age', '>=', 18)
const preview = base.limit(1)
const everyone = base
// everyone has no limit.
```

Drizzle's builder is designed for a query written in one go. Outside [dynamic mode](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/dynamic-query-building.mdx#L19), its types remove a method once it has been called, which the docs say "becomes a problem" for "a shared function that takes a query builder and enhances it". `$dynamic()` lifts that restriction and keeps the mutation, and a second `where()` replaces the first:

```ts
const ownedPets = drizzleDb
  .select({ id: pet.id })
  .from(pet)
  .where(eq(pet.owner_id, ownerId))
  .$dynamic()

const named = ownedPets.where(eq(pet.name, 'Catto'))
// select "id" from "pet" where "pet"."name" = $1
// The owner filter is gone, from ownedPets too.
```

The query now returns every owner's pets named Catto, with no error. When the first filter is an owner or a tenant scope, that is a data leak.

A Drizzle maintainer called this [expected behavior](https://github.com/drizzle-team/drizzle-orm/issues/2321#issuecomment-2429838380) and closed the request to [merge the calls](https://github.com/drizzle-team/drizzle-orm/issues/1644) as not planned. The documented pattern is to [collect conditions](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/guides/conditional-filters-in-query.mdx#L76-L93) and call `where(and(...))` once, with a function that builds a fresh query for each branch. In Kysely each `where()` adds to the last with AND and returns a new builder, so a shared function can add a filter, a join, or a limit without knowing what its caller added.

**In Drizzle, sharing a builder means building it again; in Kysely, every builder is a value you can share.** Immutability has one trap of its own: a returned builder that is not kept is a change that never happened. Keep each returned builder, and use [`$if`](/docs/recipes/conditional-selects) when conditional selections change the result type.

## Building a query never executes it

A Drizzle builder is a promise: awaiting it runs the query. That keeps simple calls short, and it means an `async` helper executes a query it meant to return for further composition:

```ts
async function adultQuery() {
  return drizzleDb
    .select({ id: person.id })
    .from(person)
    .where(gte(person.age, 18))
}

const rows = await adultQuery()
// Already executed. These are rows, not a builder to extend.
```

Keep the helper synchronous, or return an object containing the builder to avoid promise assimilation. With Kysely, even an async helper returns a composable builder:

```ts
async function adultQuery() {
  return db.selectFrom('person').select('id').where('age', '>=', 18)
}

const query = await adultQuery()
const rows = await query.where('first_name', '=', 'Jennifer').execute()
```

**A Drizzle builder runs when it is awaited; a Kysely builder runs when you call `.execute()`.**

Execution also takes a signal. Every Kysely `execute()` and `stream()` accepts a web-standard [`AbortSignal`](https://kysely-org.github.io/kysely-apidoc/interfaces/AbortableQueryOptions.html), and an option chooses what happens to a query already running: stop waiting, cancel it on the database, or kill its session. The PostgreSQL, MySQL, and MSSQL dialects implement the database side. Drizzle's query API takes no signal in 0.45.4 or 1.0.0-rc.5, and the request for one has been [open since December 2023](https://github.com/drizzle-team/drizzle-orm/issues/1602). Drizzle's own PostgreSQL driver, `@drizzle-team/postgres`, [cancels a query by `timeout` or `signal`](https://github.com/drizzle-team/drizzle-orm/blob/f251e997d78320e1b1f28db0745aacdddaf45d59/postgres/README.md#L66-L70) on a pooled connection, below the query builder.

## Kysely is extended through its query tree, not its builders

Neither library has a public API for adding methods to its builders, and both are extended with functions. Kysely's `$call` applies a function that takes and returns a builder in the middle of a chain, and anything that implements [`Expression<T>`](https://kysely-org.github.io/kysely-apidoc/interfaces/Expression.html) is accepted wherever Kysely takes an expression, which is how [your own helpers](/docs/recipes/extending-kysely) add what the builder lacks. Drizzle's helpers do the same by returning `sql<T>`.

What only Kysely opens is the query underneath. Before it is SQL, every Kysely query is an immutable tree of [operation nodes](https://kysely-org.github.io/kysely-apidoc/interfaces/OperationNode.html): a select node that holds its joins, its `where`, and its limit as nodes of their own. `toOperationNode()` returns it from any builder, the node types and [`OperationNodeTransformer`](https://kysely-org.github.io/kysely-apidoc/classes/OperationNodeTransformer.html) are exported, and plugins and dialects are interfaces built on it.

### Plugins see the query

A [Kysely plugin](https://kysely-org.github.io/kysely-apidoc/interfaces/KyselyPlugin.html) receives that tree before it compiles, and the result after it runs. The [built-in plugins](/docs/plugins) are written against that interface: they convert camelCase, qualify tables with a schema, deduplicate joins, handle empty `in` lists, make null comparisons safe, and parse JSON results. `withPlugin` scopes one to a query or a derived instance and leaves the original unchanged.

Drizzle's extension points are per concern: a [logger](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/goodies.mdx#L23-L24) that receives the SQL text and its parameters, a [cache](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/cache.mdx#L4), [casing](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/sql-schema-declaration.mdx#L203-L207) in the schema declaration, and [custom column types](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/custom-types.mdx#L3) that convert values. A Drizzle builder keeps its clauses in a protected field, and its dialect writes them out as chunks of text, names, columns, and parameters. Neither version has an interface that receives the query in between.

<details>
<summary>A custom plugin: a read-only instance</summary>

A plugin is a class with two methods. This one makes an instance read-only, for a reporting endpoint or a coding agent, by refusing any statement that is not a select:

```ts
class ReadOnlyPlugin implements KyselyPlugin {
  transformQuery({ node }: PluginTransformQueryArgs) {
    if (!SelectQueryNode.is(node)) {
      throw new Error('This instance is read-only.')
    }
    return node
  }

  async transformResult({ result }: PluginTransformResultArgs) {
    return result
  }
}

const reports = db.withPlugin(new ReadOnlyPlugin())
```

The plugin reads the statement itself, so an insert, update, delete, or merge is refused whichever helper built it, before anything is sent. So is a statement written whole as a `sql` template, which reaches it as a raw node.

It is a runtime check, not a type error, and it reads the root node: a select that wraps a data-modifying CTE passes, and finding one takes the exported transformer. A read-only database role is still the boundary; the plugin reports the mistake earlier, in application code.

</details>

Schema-per-tenant shows the difference. A Drizzle table is bound to its schema when it is declared, and the issue titled "working with dynamic schemas is practically impossible" has been [open since April 2023](https://github.com/drizzle-team/drizzle-orm/issues/423). The [workaround a maintainer gave there](https://github.com/drizzle-team/drizzle-orm/issues/423#issuecomment-1501232679) is a factory that declares each table again for a schema name, `pgSchema(name).table(...)`, with every query built from the tables it returns. In Kysely the schema is chosen per query, by a plugin:

```ts
const tenantDb = db.withSchema('tenant_1')
// tenantDb.selectFrom('person') compiles to: from "tenant_1"."person"
```

**Drizzle's options cover the cases it names; Kysely's plugins see the query.**

### Dialects are a public interface

A Kysely [dialect](https://kysely-org.github.io/kysely-apidoc/interfaces/Dialect.html) is four exported factories: a driver, a query compiler, an adapter, and an introspector. A new database implements that interface, and the [community dialects](/docs/dialects) for BigQuery, ClickHouse, Oracle, and Firebird are built that way. The `Database` interface and the query API are the same types on every dialect, and do not know which one they target: `returning()` compiles on a MySQL instance, and MySQL rejects the statement.

Drizzle's dialects ship inside Drizzle, one per database family, each with its own table function, column builders, query builder, and dialect class, and with no shared interface to implement. **A new database implements Kysely's dialect interface; in Drizzle it extends a database Drizzle already ships.**

<details>
<summary>Drizzle's dialect families and third-party databases</summary>

The families are PostgreSQL, MySQL, SQLite, and SingleStore, plus Gel in 0.45 and MSSQL and CockroachDB in 1.0. Because each has its own builder, its MySQL builder has no `returning()` to call, and a schema is written per family.

A [proxy driver](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/connect-drizzle-proxy.mdx#L8) lets you supply the transport for a database Drizzle supports; it does not add one. A third-party database starts from one of the shipped families instead: [drizzle-duckdb](https://www.npmjs.com/package/@duckdbfan/drizzle-duckdb), "based on drizzle's Postgres client", subclasses Drizzle's `PgDialect`, `PgSession`, and `PgDatabase`.

</details>

## Migrate from Drizzle to Kysely one query at a time

A move from Drizzle to Kysely does not have to happen at once, or at all for the schema.

### Can Kysely and Drizzle be used together?

Yes. Keep [Drizzle Kit](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/migrations.mdx#L12) for schema and migrations, and write queries in Kysely against the same database:

1. [Generate Kysely's types](/docs/generating-types) from the migrated database, in the migration step or in CI.
2. Give both clients the same `pg` pool: `drizzle({ client: pool })` and `new PostgresDialect({ pool })`.
3. Start with a query that shared functions extend, that traverses JSON, or that declares its types through `sql<T>`. Move it, inspect `.compile()`, and compare rows, nulls, ordering, and empty results.
4. Keep each transaction on one client. The two share a pool, not a transaction.

On Drizzle 0.45.4, the `Kyselify` type from `drizzle-orm/kysely` also derives Kysely's table types from the Drizzle table objects, with no generation step. 1.0.0-rc.5 no longer ships that export, so generated types are the path that survives the upgrade.

## Other practical considerations

<details>
<summary>Schema, migrations, and value conversion</summary>

One Drizzle declaration is the source for types and for migrations: Drizzle Kit diffs the tables and generates SQL migrations, and can push to or pull from a database. It also runs [Drizzle Studio](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/drizzle-kit-studio.mdx#L12-L15), a database browser, and [drizzle-seed](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/seed-overview.mdx#L8-L10) fills the declared tables with deterministic test data. Kysely has no migration generator. Its [migrations](/docs/migrations) are written by hand through the schema builder or any migration tool, and its types are declared or [generated](/docs/generating-types) from the database, so a migration applied without regenerating them is drift the compiler cannot see.

It also makes the database the source of truth: Kysely queries a schema that another service or migration tool owns, with nothing declared a second time. Drizzle reaches one through [`drizzle-kit pull`](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/drizzle-kit-pull.mdx#L13), which writes the declarations to keep in step with it.

Drizzle's columns also convert values, through date modes and [custom types](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/custom-types.mdx#L3), and the same tables derive validation schemas for [Zod](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/zod.mdx#L10), [Valibot](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/valibot.mdx#L10), [TypeBox](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/typebox.mdx#L12), and [ArkType](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/arktype.mdx#L10). Kysely does neither: its types describe what the driver returns, conversion belongs to the driver's configuration or a plugin, and a validator is written separately.

</details>

<details>
<summary>Drivers and runtimes</summary>

Both have zero runtime dependencies and run on Node.js, Deno, Bun, and edge runtimes. Drizzle ships its driver adapters, including Neon, PlanetScale, Cloudflare D1, libSQL, and Bun SQL, inside one package. Kysely's core dialects are PostgreSQL, MySQL, MSSQL, SQLite, and PGlite; the rest are [organization and community dialects](/docs/dialects), installed separately. Drizzle also has a batch API for its [Neon HTTP](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/batch-api.mdx#L3-L5) driver and its [libSQL and D1](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/sqlite/batch-api.mdx#L4-L6) drivers; Kysely has none.

</details>

<details id="type-checking-cost">
<summary>Type-checking cost</summary>

Both libraries compute their types in the compiler. The cost below is TypeScript's instantiation count for one table shape at three schema sizes, and for the same ten queries in each library, four joins among them, returning the same rows.

| Instantiations, TypeScript 6.0.3          | Kysely 0.29.8 | Drizzle 0.45.4 | Drizzle 1.0.0-rc.5 |
| ----------------------------------------- | ------------- | -------------- | ------------------ |
| Schema of 10 tables, no queries           | 196           | 1,220          | 679                |
| Schema of 1,000 tables, no queries        | 196           | 24,980         | 17,509             |
| Ten more queries, 10 tables               | 15,396        | 23,012         | 19,239             |
| Ten more queries, 100 tables              | 22,686        | 23,012         | 19,239             |
| Ten more queries, 1,000 tables            | 95,586        | 23,012         | 19,239             |
| Ten more queries, `$pickTables`, any size | 17,844        | 23,012         | 19,239             |

Kysely's schema is an interface, which the compiler does not have to infer. Drizzle's is inferred from its table objects, at 24 instantiations per table in 0.45.4 and 17 in 1.0.0-rc.5, once per program.

Queries go the other way. Drizzle's cost per query does not depend on the size of the schema. Kysely's is lower on a small schema, and each join adds about 24 instantiations for every table in the `Database` interface. The two cross near 100 tables, and at 1,000 tables these ten queries cost Kysely four to five times what they cost Drizzle.

A Drizzle query sees only the tables it imports. A Kysely query sees the whole `Database` interface unless [`$pickTables`](https://kysely-org.github.io/kysely-apidoc/classes/Kysely.html#picktables) narrows it to the tables it reads, in the same line that starts the query. Written that way, the ten cost the same at every schema size, below both Drizzle versions, for about 250 instantiations more per query on a small schema and a line nobody writes until the compiler is slow.

"Ten more" is the cost of the ten in a program that already has ten of the same kind. The first ten cost more in each library, because shared types are instantiated once: 78,983, 31,394, and 29,835 at 10 tables. About 59,000 of Kysely's figure is the first CTE in a program, and Kysely 0.30.0-beta.2 removes it, for 20,019.

Check time on one machine agrees. At 1,000 tables, Drizzle's schema took about 0.3 seconds to check before any query. Ten more queries then added about 1.6 seconds for Kysely on TypeScript 6 and 0.1 seconds on TypeScript 7, and under 0.1 seconds for Drizzle on either.

Measured **November 9, 2026**. TypeScript 7.0.2, run single-threaded, counts within 3% of these. A deeply composed query can also reach TypeScript's instantiation limit, and [`$assertType`](/docs/recipes/excessively-deep-types) simplifies the type at that point. `tsc --extendedDiagnostics` on your own schema is the number that counts.

</details>

## Choosing Drizzle or Kysely

### Is Drizzle an ORM or a query builder?

**Drizzle is an ORM in the data framework sense: models, generated migrations, relational reads, and a query builder.** Its tables are models under another name: each maps property names to columns and converts values, with relations declared beside it. This page compares its builder with Kysely, which is a query builder only. [SQL query builder vs ORM](/docs/comparisons/query-builder-vs-orm) covers model APIs like Drizzle's relational queries.

### Is Drizzle type-safe?

**For values and results, yes; for scope, no.** Drizzle infers each row and checks a literal against its column. It does not check that a column belongs to the query: [a column object is accepted in any query](#drizzle-checks-each-column-kysely-checks-the-query). Kysely checks that too, with [gaps of its own](#where-kyselys-checks-stop).

### Is Kysely faster than Drizzle?

**The database cannot tell them apart: both send one parameterized statement, and [performance belongs to the statement](/docs/comparisons/query-builder-vs-raw-sql#performance-belongs-to-the-statement-not-the-authoring-tool).** Drizzle describes itself as ["a thin TypeScript layer on top of SQL with almost 0 overhead"](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/perf-queries.mdx#L2-L3), and its [prepared statements](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/perf-queries.mdx#L14) build the SQL once, with `sql.placeholder()` for the values that change, and reuse it on every call. Kysely has no placeholder API: it builds the statement on each call, and [`.compile()`](/docs/recipes/splitting-query-building-and-execution) splits building from execution only for a query whose values are fixed. Neither library is benchmarked here.

### Is Kysely smaller than Drizzle?

**In a bundle, stable Drizzle is smaller; as an installed package, Kysely is.** One PostgreSQL query bundles to 20.1 KiB gzipped with Drizzle 0.45.4, 30.2 KiB with Kysely 0.29.8, and 36.4 KiB with Drizzle 1.0.0-rc.5. Kysely's published package is a 319.6 KiB download, against 1,205.7 KiB and 2,989.0 KiB for those two Drizzle versions. The [measurements](#measured-sizes) and what they exclude are above.

### Which type-checks faster?

**Per query, Kysely on a small schema; on a large one, Drizzle by default, and Kysely again once a query names its tables with `$pickTables`.** Kysely's schema is an interface the compiler does not have to infer, and Drizzle's costs more with every table. Each Kysely join costs more as the schema grows, and Drizzle's queries do not, so on the same ten queries the two cross near 100 tables. The [measurements](#type-checking-cost) are above.

### Which is easier for a coding agent to use?

**Both ship examples where an agent reads them; Kysely checks more of what the agent writes.** An agent works by editing and running the compiler again, and the checks on this page sit inside that loop: a wrong reference or a misspelled JSON key is a compile error it can read and fix without a database, where Drizzle gives it a failed run or a silent `null`.

Drizzle's team [kept its API order](https://github.com/drizzle-team/drizzle-orm/discussions/2409#discussioncomment-9614641) to spare developers "huge type errors that are quite hard to understand", a trade priced for a person reading the error. An agent reads a long type error in the same loop as a short one, and before any query runs; what no loop reports is a `null` that arrives under a `string` type. Each library documents its methods in the type declarations it installs, and each site publishes an `llms.txt`. Kysely's inline examples are [type-checked in CI](/docs/integrations/llms) against the release they ship with.

### Why use Kysely instead of Drizzle?

**Choose Kysely when queries are composed, shared, and changed, and you want TypeScript to check each change.**

- References are [checked against the query](#drizzle-checks-each-column-kysely-checks-the-query) in every clause, with aliases and CTEs written inside the statement.
- JSON and CASE expressions are [built, and their types inferred](#kysely-builds-the-expressions-drizzle-writes-as-templates); filtered aggregates and windows are built instead of templated.
- Builders behave like values: [shared without rebuilding](#shared-queries-branch-without-mutation), [executed only when asked](#building-a-query-never-executes-it), and cancelled with an `AbortSignal`.
- The [query tree is public](#kysely-is-extended-through-its-query-tree-not-its-builders), and plugins and dialects build on it.

Its types come from the database itself, so it fits a schema that another tool, service, or team migrates. Immich, Open Collective, and Docmost [compose production queries with it](/docs/comparisons/query-builder-vs-raw-sql#production-code-draws-the-same-line).

### When is Drizzle the better choice?

**Keep Drizzle when a person writes the schema and the queries, one TypeScript declaration should drive types, migrations, validation schemas, and relational reads, and the queries are mostly written whole, in one place.** A schema change is one edit there: [`drizzle-kit push`](https://github.com/drizzle-team/drizzle-orm-docs/blob/7f7f847a41005aabd08b22fbb3d36030ef968479/src/content/docs/pg/drizzle-kit-push.mdx#L14) applies it to the database without a migration file, and the types, validators, and relational queries follow with no generation step.

That value is priced for a person writing the code. When an agent writes most of it, it writes a migration as SQL as readily as a query, inspects the database through `psql` or a script instead of a studio, and already knows SQL, where a model API's options are a second vocabulary per library. [OpenClaw's contributor guide](https://github.com/openclaw/openclaw/blob/28340c41f8b88ae6d11488e523808315319747b5/AGENTS.md#L71), written for agents, draws that line: schema and migrations as SQL, queries in Kysely. Drizzle Kit can stay either way, and Kysely can run beside it for the queries that are composed.

**Both put SQL first; Drizzle types the columns a query uses, and Kysely types the query.**
