# Kysely vs Drizzle ORM

Kysely and Drizzle ORM start from the same premise: SQL is the interface, and TypeScript should check it. Both compose statements through a typed API, bind values as parameters, and infer result types without generating a client. Kysely is a type-safe SQL query builder. Drizzle describes itself as [a headless TypeScript ORM](https://orm.drizzle.team/docs/overview): tables declared in TypeScript, a SQL-like query builder, a relational query API beside it, and Drizzle Kit to generate migrations from the declarations. This page compares the two as query builders, and says where the rest of Drizzle earns its place.

**Both infer the result of a query; Drizzle knows what each column is, and Kysely also knows whether the query can see it.** Kysely carries the tables and aliases in scope through every step, so a reference is checked where it is written: in a selection, a filter, a join condition, a window, or through `eb.ref` in a `sql` fragment. It builds the JSON, CASE, and aggregate expressions that Drizzle writes as annotated templates, and its builders are immutable values that run only when asked. The differences that cost most are the quiet ones: an annotated template or a mutated builder returns the wrong rows with no error.

Drizzle is the most downloaded ORM on npm: [47.9 million drizzle-orm downloads](https://api.npmjs.org/downloads/point/2026-10-31:2026-11-06/drizzle-orm) in the week of October 31, 2026, ahead of [`@prisma/client`](https://api.npmjs.org/downloads/point/2026-10-31:2026-11-06/@prisma/client) and [Kysely](https://api.npmjs.org/downloads/point/2026-10-31:2026-11-06/kysely). All counts include installs pulled in by other packages. Its team builds it [from Ukraine](https://orm.drizzle.team/docs/sustainability#drizzle-llc), and kept shipping through the war. **Drizzle brought SQL-first TypeScript to the mainstream, and every SQL-first library, Kysely included, has a bigger audience for it.**

Drizzle here means 0.45.4 and 1.0.0-rc.5, its stable release and its release candidate in November 2026. Its behavior below is the same in both unless stated.

## Both infer the result of a join

Assume configured Kysely (`db`) and Drizzle (`drizzleDb`) clients over the same two tables:

<details>
<summary>Database interface and Drizzle table objects</summary>

Kysely's `Database` interface is types only, handwritten or [generated](/docs/generating-types) from the database:

```ts
interface Database {
  person: { id: number; first_name: string; age: number | null }
  pet: { id: number; name: string; owner_id: number }
}
```

Drizzle's tables are runtime objects, which Drizzle Kit also reads to generate migrations:

```ts
import { integer, pgTable, text } from 'drizzle-orm/pg-core'

const person = pgTable('person', {
  id: integer().notNull(),
  first_name: text().notNull(),
  age: integer(),
})
const pet = pgTable('pet', {
  id: integer().notNull(),
  name: text().notNull(),
  owner_id: integer().notNull(),
})
```

</details>

Select adults with their pets' names, keeping people who have no pet.

With Drizzle:

```ts
const rows = await drizzleDb
  .select({ first_name: person.first_name, pet_name: pet.name })
  .from(person)
  .leftJoin(pet, eq(pet.owner_id, person.id))
  .where(gte(person.age, 18))
  .orderBy(person.first_name)
```

With Kysely:

```ts
const rows = await db
  .selectFrom('person')
  .leftJoin('pet', 'pet.owner_id', 'person.id')
  .select(['person.first_name', 'pet.name as pet_name'])
  .where('person.age', '>=', 18)
  .orderBy('person.first_name')
  .execute()
```

The rows match, and so do the inferred types: `{ first_name: string; pet_name: string | null }[]`. Both libraries make `pet_name` nullable because the join is a left join. Drizzle can go further: [select the pet's columns as a nested object](https://orm.drizzle.team/docs/joins#partial-select), and the pet is one object that is `null` as a whole. Kysely makes each joined column nullable on its own. **Written correctly, the two queries are equivalent; the libraries differ in what the compiler says when a query is wrong.**

## Drizzle checks each column; Kysely checks the query

Production queries collect their filters. Put the query above in a function with an optional pet name, collecting conditions the way [Drizzle's guide](https://orm.drizzle.team/docs/guides/conditional-filters-in-query) does. Then a later change drops the pet's name from the result, and the join with it:

```ts
function matchingPeople(options: { petName?: string }) {
  const filters = [gte(person.age, 18)]
  if (options.petName) filters.push(eq(pet.name, options.petName))

  return drizzleDb
    .select({ first_name: person.first_name })
    .from(person)
    .where(and(...filters))
}
```

It compiles, and it runs for every request without a pet name. A request with one fails in PostgreSQL: the filter still reads `pet`, and the change never touched that line. The same function after the same change in Kysely:

```ts
function matchingPeople(options: { petName?: string }) {
  let query = db
    .selectFrom('person')
    .select('person.first_name')
    .where('person.age', '>=', 18)

  if (options.petName) {
    // TypeScript error: pet is not available in this query.
    query = query.where('pet.name', '=', options.petName)
  }
  return query
}
```

A Drizzle column is a value. `pet.name` has one type wherever it is passed, `eq()` returns a condition that records no table, and `select()` is called before `from()`, so a selection is typed before the query has a table. Kysely's `selectFrom` comes first, and every later method is typed against the tables and aliases accumulated so far. **Drizzle's compiler accepts a column object in any query; Kysely's checks every reference written on the query's own builder.**

The gap is structural, not a missing feature, and it is a choice. Asked in 2024 for [a fully type-safe query builder](https://github.com/drizzle-team/drizzle-orm/discussions/2409), Drizzle's team [answered](https://github.com/drizzle-team/drizzle-orm/discussions/2409#discussioncomment-9614641) that it had "deliberately switched to our current API" because "it will provide better DX than huge type errors that are quite hard to understand for average TS developers", and that full type safety would need joins to come before the selection, "deviating the API from SQL even more".

By that account, closing the gap means changing the order every query is written in. Kysely makes the opposite bet: a mistake reported at compile time costs less than the same mistake at runtime, for a developer and for a coding agent alike.

The split is the same wherever a reference lands. That includes ORDER BY, GROUP BY, HAVING, a CTE the query never attached, an update's SET, a delete's WHERE, and these:

| Invalid reference                                                   | Kysely                              | Drizzle                                                     |
| ------------------------------------------------------------------- | ----------------------------------- | ----------------------------------------------------------- |
| Select `pet.name` without joining `pet`                             | TypeScript error.                   | Passes TypeScript; Drizzle throws while generating the SQL. |
| Filter on `pet.name` without joining `pet`                          | TypeScript error.                   | Passes TypeScript; PostgreSQL rejects the query.            |
| Join a subquery aliased `pets`, then compare `pet.owner_id` in `on` | TypeScript error.                   | Passes TypeScript; PostgreSQL rejects the query.            |
| Partition a window by a column of a table the query never joined    | TypeScript error.                   | Passes TypeScript; PostgreSQL rejects the query.            |
| Reference a table the query never joined inside a `sql` fragment    | TypeScript error, through `eb.ref`. | Passes TypeScript; PostgreSQL rejects the query.            |

Drizzle catches the first of these itself, with an error that names the table and asks whether you forgot to join it. The check exists; it runs while generating the SQL, after the compiler has passed the code. Harminder Virk, the creator of AdonisJS, [documented the first three rows in December 2023](https://github.com/thetutlage/meta/discussions/8), and all three still pass TypeScript in 0.45.4 and 1.0.0-rc.5.

**Every row in that table is a failed run with Drizzle and a compile error with Kysely.** PostgreSQL [stops at the first error](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY), so unchecked mistakes surface one execution at a time, against a database. The compiler reports them together, before a connection is opened, which is also the loop a coding agent can run on every edit.

Operands follow the same split. Drizzle checks a literal against its column: `eq(person.id, 'one')` is a type error, while `eq(person.first_name, person.id)`, a text column compared with an integer column, compiles and PostgreSQL rejects it. So does `where(and(person.id))`, a column that is not a condition. Kysely's expression builder checks an expression against an expression, so `eb('first_name', '=', eb.ref('id'))` is a type error, and so is a condition that is not boolean.

Most of these failures are loud once a test runs the branch that builds the reference; the function above passes every test that leaves the pet name out. One is quiet: `returning({ id: pet.id })` on an insert into `person` compiles and returns the person's `id`, because Drizzle writes the column without its table.

The failures further down this page are quiet too: a misspelled JSON key returns `null`, a CASE without an ELSE returns `null` under a `string` type, a `limit()` on one branch of a shared query applies to the other, and a second `where()` drops the first. **A wrong reference fails only when its branch runs; an unchecked template or a mutated builder returns the wrong result with no error at all.**

### Is Kysely fully type-safe?

**No query builder is perfectly type-safe; Kysely checks more of the query than Drizzle does, and treats the rest as work to do.** Its check is made where a reference is written, on a builder that knows the query, and it stops there. A reference written with `sql.ref` or as template text, a [dynamic reference](https://kysely-org.github.io/kysely-apidoc/classes/DynamicModule.html), an expression built ahead of time on a standalone `expressionBuilder`, and a helper whose builder parameter declares more tables than the caller's query has are all taken on trust. The reference shorthands `whereRef`, `onRef`, and the three-argument join take two column names without comparing their types.

Column objects pay Drizzle back here. An editor can rename one and jump to its declaration, and Drizzle qualifies it with its table in a join. Kysely's references are strings read by the type system: completed and checked, yet an unqualified `id` after joining two tables that both have one compiles, and PostgreSQL rejects it as ambiguous.

Two more Kysely gaps are quiet: `where('age', '=', null)` compiles and matches no rows, where Drizzle's `eq(person.age, null)` is a type error, and a `union` whose sides list the same columns in a different order returns values under the wrong keys, where Drizzle throws before sending it.

## Kysely builds the expressions Drizzle writes as templates

Past selections, joins, filters, and plain aggregates, Drizzle's builder hands over to its [`sql` template](https://orm.drizzle.team/docs/sql). JSON traversal, CASE, aggregate FILTER, and window clauses are SQL text with a result type declared by hand. Kysely has a builder for each, so the references are checked, and for JSON and CASE the type is inferred.

### JSON traversal

A `user_settings.profile` column holds JSON typed as `Profile`, which is `{ addresses: { city: string }[] }`, in both libraries: in Kysely's `Database` interface, and through `jsonb().$type<Profile>()` on Drizzle's `settings` table object. Read the first address's city. With Drizzle:

```ts
const rows = await drizzleDb
  .select({
    id: settings.id,
    first_city: sql<string | null>`
      ${settings.profile}->'addresses'->0->'city'
    `.as('first_city'),
  })
  .from(settings)
// The string | null type is supplied by hand.
```

With Kysely:

```ts
const rows = await db
  .selectFrom('user_settings')
  .select('id')
  .select((eb) =>
    eb.ref('profile', '->').key('addresses').at(0).key('city').as('first_city'),
  )
  .execute()
// Inferred: { id: number; first_city: string | null }[]
```

Kysely infers `string | null` because the array may be empty. Now misspell `city` as `ctiy`:

```ts
// Drizzle: compiles, runs, and returns null for every row.
sql<string | null>`${settings.profile}->'addresses'->0->'ctiy'`

// Kysely: TypeScript error, ctiy is not a key of an address.
eb.ref('profile', '->').key('addresses').at(0).key('ctiy')
```

**A misspelled JSON key is a silent `null` in Drizzle and a compile error in Kysely.** Kysely also rejects reading `city` before indexing `addresses`. Both libraries trust the declared `Profile` type; neither validates the stored JSON.

### CASE expressions

Label each person by age, including people whose age is unknown. With Drizzle:

```ts
const query = drizzleDb
  .select({
    id: person.id,
    age_group: sql<string>`case
      when ${gte(person.age, 18)} then ${'adult'}
      when ${lt(person.age, 18)} then ${'minor'}
      else ${'unknown'}
    end`.as('age_group'),
  })
  .from(person)
```

With Kysely:

```ts
const query = db
  .selectFrom('person')
  .select('id')
  .select((eb) =>
    eb
      .case()
      .when('age', '>=', 18)
      .then('adult')
      .when('age', '<', 18)
      .then('minor')
      .else('unknown')
      .end()
      .as('age_group'),
  )
// Inferred: { id: number; age_group: string }[]
```

Both return the same labels. Now remove the `else`. Kysely infers `string | null`, and a caller's `.toUpperCase()` stops compiling until it handles the null. Drizzle's `sql<string>` is unchanged, still claims a string, and a person with no age returns `null`. Drizzle's [own guide](https://orm.drizzle.team/docs/guides/update-many-with-different-value) writes CASE as a template, and the request for [native CASE support](https://github.com/drizzle-team/drizzle-orm/issues/1065) has been open since August 2023. **A `sql<T>` annotation is a claim about the expression; Kysely's inferred type is derived from it.**

### Aggregate filters and windows

Count images and videos in one row, the shape [Immich](https://immich.app/) builds with Kysely. Each count is one selection:

```ts
// Drizzle: a template.
sql<string>`count(*) filter (where ${eq(asset.kind, 'image')})`

// Kysely: a builder.
eb.fn.countAll<string>().filterWhere('kind', '=', 'image')
```

Both declare `string` here, as `pg` returns a PostgreSQL `bigint` by default; Kysely's `countAll` takes the type as a parameter and converts nothing. Drizzle's [`count()` with `.where()`](https://orm.drizzle.team/docs/guides/count-rows) and [`db.$count(table, filter)`](https://orm.drizzle.team/docs/select#count) cover a single conditional count and return it as a `number`. Its `count()` has no FILTER or OVER methods, so several filtered aggregates in one row, or any window, are templates.

In Kysely a window is `.over()` on the aggregate, and a partition by a table the query never joined is the fourth row of the table above. **A filtered or windowed aggregate is a template in Drizzle and a builder in Kysely: both declare its result type, and only the builder checks its references against the query.**

## Kysely's escape hatch keeps references checked

Kysely does not cover all of SQL either; it covers what applications write most, extends that coverage release by release, and types the escape hatch for the rest. Both libraries have a `sql` template that binds values as parameters. They differ in what an interpolated reference is:

```ts
// Drizzle: compiles. pet is not in the query, and PostgreSQL rejects it.
drizzleDb
  .select({ name: sql<string>`lower(${pet.name})`.as('name') })
  .from(person)

// Kysely: eb.ref is checked against the tables in scope.
db.selectFrom('person').select((eb) =>
  sql<string>`lower(${eb.ref('first_name')})`.as('name'),
)
// Replace first_name with pet.name: TypeScript error, pet is not joined.
```

Neither library checks a fragment's grammar or its declared result type. **Drizzle's `sql` template carries SQL text, bound values, and a declared type; Kysely's also carries the references `eb.ref` checked.** Wrap repeated fragments in [reusable helpers](/docs/recipes/reusable-helpers) that take `Expression<T>`; see the [`sql` API](https://kysely-org.github.io/kysely-apidoc/interfaces/Sql.html) for more. For whole queries written as templates, see [query builder vs raw SQL](/docs/comparisons/query-builder-vs-raw-sql).

## Nested results stay in the same builder

Drizzle's [relational queries](https://orm.drizzle.team/docs/rqb-v2) are the shortest way to read a declared relation. Return each person with their first two pets by name, in 1.0 syntax:

```ts
const rows = await drizzleDb.query.person.findMany({
  columns: { first_name: true },
  with: {
    pets: { columns: { name: true }, orderBy: { name: 'asc' }, limit: 2 },
  },
})
// { first_name: string; pets: { name: string }[] }[]
```

One statement, an inferred nested type, and `[]` for a person with no pets. Kysely returns the same rows and the same type with `jsonArrayFrom`, from `kysely/helpers/postgres`:

```ts
const rows = await db
  .selectFrom('person')
  .select((eb) => [
    'person.first_name',
    jsonArrayFrom(
      eb
        .selectFrom('pet')
        .select('pet.name')
        .whereRef('pet.owner_id', '=', 'person.id')
        .orderBy('pet.name')
        .limit(2),
    ).as('pets'),
  ])
  .execute()
// { first_name: string; pets: { name: string }[] }[]
```

Drizzle's version is shorter, and it is a different API from the one in the rest of this page: relations are declared ahead of the query, filters and ordering are objects, not operators, and 1.0 [redesigned it](https://orm.drizzle.team/docs/relations-v1-v2). It is a model API; [SQL query builder vs ORM](/docs/comparisons/query-builder-vs-orm) compares that kind of API with a query builder.

It reads declared relations, and in 1.0 a per-parent count fits beside them, as a [`db.$count` subquery in `extras`](https://orm.drizzle.team/docs/rqb-v2#include-subqueries). A read that needs a join outside the relations or a GROUP BY moves to the SQL-style builder, and for other aggregates the docs point there too: "As of now aggregations are not supported in extras, please use core queries for that." There a nested array is a hand-written `json_agg` with a `coalesce` fallback and a declared type.

In Kysely the nested subquery is an ordinary query: join inside it, aggregate it, filter it, with the same methods and the same checks. **Drizzle's relational API is a second query language beside its SQL builder; Kysely nests results in the builder it already has.** The helpers are per dialect, and a driver that returns JSON as text needs [`ParseJSONResultsPlugin`](/docs/recipes/relations#the-json-data-type-and-functions). See [nested relations](/docs/recipes/relations).

## Shared queries branch without mutation

Drizzle mutates the shared base:

```ts
const base = drizzleDb
  .select({ id: person.id })
  .from(person)
  .where(gte(person.age, 18))

const preview = base.limit(1)
const everyone = base
// Both now have LIMIT 1.
```

Kysely branches independently:

```ts
const base = db.selectFrom('person').select('id').where('age', '>=', 18)
const preview = base.limit(1)
const everyone = base
// everyone has no limit.
```

Drizzle's builder is designed for a query written in one go. Outside [dynamic mode](https://orm.drizzle.team/docs/dynamic-query-building), its types remove a method once it has been called, which the docs say "becomes a problem" for "a shared function that takes a query builder and enhances it". `$dynamic()` lifts that restriction and keeps the mutation, and a second `where()` replaces the first:

```ts
const ownedPets = drizzleDb
  .select({ id: pet.id })
  .from(pet)
  .where(eq(pet.owner_id, ownerId))
  .$dynamic()

const named = ownedPets.where(eq(pet.name, 'Catto'))
// select "id" from "pet" where "pet"."name" = $1
// The owner filter is gone, from ownedPets too.
```

The query now returns every owner's pets named Catto, with no error. When the first filter is an owner or a tenant scope, that is a data leak.

A Drizzle maintainer called this [expected behavior](https://github.com/drizzle-team/drizzle-orm/issues/2321#issuecomment-2429838380) and closed the request to [merge the calls](https://github.com/drizzle-team/drizzle-orm/issues/1644) as not planned. The documented pattern is to [collect conditions](https://orm.drizzle.team/docs/guides/conditional-filters-in-query) and call `where(and(...))` once, with a function that builds a fresh query for each branch. In Kysely each `where()` adds to the last with AND and returns a new builder, so a shared function can add a filter, a join, or a limit without knowing what its caller added.

**In Drizzle, sharing a builder means building it again; in Kysely, every builder is a value you can share.** Immutability has one trap of its own: a returned builder that is not kept is a change that never happened. Keep each returned builder, and use [`$if`](/docs/recipes/conditional-selects) when conditional selections change the result type.

## Building a query never executes it

A Drizzle builder is a promise: awaiting it runs the query. That keeps simple calls short, and it means an `async` helper executes a query it meant to return for further composition:

```ts
async function adultQuery() {
  return drizzleDb
    .select({ id: person.id })
    .from(person)
    .where(gte(person.age, 18))
}

const rows = await adultQuery()
// Already executed. These are rows, not a builder to extend.
```

Keep the helper synchronous, or return an object containing the builder to avoid promise assimilation. With Kysely, even an async helper returns a composable builder:

```ts
async function adultQuery() {
  return db.selectFrom('person').select('id').where('age', '>=', 18)
}

const query = await adultQuery()
const rows = await query.where('first_name', '=', 'Jennifer').execute()
```

**A Drizzle builder runs when it is awaited; a Kysely builder runs when you call `.execute()`.**

## Kysely is extended through its query tree, not its builders

Neither library has a public API for adding methods to its builders, and both are extended with functions. Kysely's `$call` applies a function that takes and returns a builder in the middle of a chain, and anything that implements [`Expression<T>`](https://kysely-org.github.io/kysely-apidoc/interfaces/Expression.html) is accepted wherever Kysely takes an expression, which is how [your own helpers](/docs/recipes/extending-kysely) add what the builder lacks. Drizzle's helpers do the same by returning `sql<T>`.

What only Kysely opens is the query underneath. Before it is SQL, every Kysely query is an immutable tree of [operation nodes](https://kysely-org.github.io/kysely-apidoc/interfaces/OperationNode.html): a select node that holds its joins, its `where`, and its limit as nodes of their own. `toOperationNode()` returns it from any builder, the node types and [`OperationNodeTransformer`](https://kysely-org.github.io/kysely-apidoc/classes/OperationNodeTransformer.html) are exported, and plugins and dialects are interfaces built on it.

### Plugins see the query

A [Kysely plugin](https://kysely-org.github.io/kysely-apidoc/interfaces/KyselyPlugin.html) receives that tree before it compiles, and the result after it runs. A plugin is a class with two methods. This one refuses to send a delete or an update that has no WHERE clause:

```ts
class RequireWherePlugin implements KyselyPlugin {
  transformQuery({ node }: PluginTransformQueryArgs) {
    if ((DeleteQueryNode.is(node) || UpdateQueryNode.is(node)) && !node.where) {
      throw new Error('Refusing to change every row: add a where clause.')
    }
    return node
  }

  async transformResult({ result }: PluginTransformResultArgs) {
    return result
  }
}

const guarded = db.withPlugin(new RequireWherePlugin())
```

The plugin reads the finished statement, so a filter added by a helper or in a later statement counts, and a statement that reaches execution without one throws before anything is sent. It is a runtime check, not a type error, and a delete written whole as a `sql` template reaches it as a raw node, not a delete.

The [built-in plugins](/docs/plugins) are written against the same interface: they convert camelCase, qualify tables with a schema, deduplicate joins, handle empty `in` lists, make null comparisons safe, and parse JSON results. `withPlugin` scopes one to a query or a derived instance and leaves the original unchanged.

Drizzle's extension points are per concern: a [logger](https://orm.drizzle.team/docs/goodies#logging) that receives the SQL text and its parameters, a [cache](https://orm.drizzle.team/docs/cache), [casing](https://orm.drizzle.team/docs/sql-schema-declaration#camel-and-snake-casing) in the schema declaration, and [custom column types](https://orm.drizzle.team/docs/custom-types) that convert values. A Drizzle builder keeps its clauses in a protected field, and its dialect writes them out as chunks of text, names, columns, and parameters. Neither version has an interface that receives the query in between.

Schema-per-tenant shows the difference. A Drizzle table is bound to its schema when it is declared, and the issue titled "working with dynamic schemas is practically impossible" has been [open since April 2023](https://github.com/drizzle-team/drizzle-orm/issues/423). The [workaround a maintainer gave there](https://github.com/drizzle-team/drizzle-orm/issues/423#issuecomment-1501232679) is a factory that declares each table again for a schema name, `pgSchema(name).table(...)`, with every query built from the tables it returns. In Kysely the schema is chosen per query, by a plugin:

```ts
const tenantDb = db.withSchema('tenant_1')
// tenantDb.selectFrom('person') compiles to: from "tenant_1"."person"
```

**Drizzle's options cover the cases it names; Kysely's plugins see the query.**

### Dialects are a public interface

A Kysely [dialect](https://kysely-org.github.io/kysely-apidoc/interfaces/Dialect.html) is four exported factories: a driver, a query compiler, an adapter, and an introspector. A new database implements that interface, and the [community dialects](/docs/dialects) for BigQuery, ClickHouse, Oracle, and Firebird are built that way. The `Database` interface and the query API are the same types on every dialect, and do not know which one they target: `returning()` compiles on a MySQL instance, and MySQL rejects the statement.

Drizzle's dialects ship inside Drizzle: PostgreSQL, MySQL, SQLite, and SingleStore, plus Gel in 0.45 and MSSQL and CockroachDB in 1.0. Each has its own table function, column builders, query builder, and dialect class, so its MySQL builder has no `returning()` to call, a schema is written per database family, and there is no shared dialect interface to implement.

A [proxy driver](https://orm.drizzle.team/docs/connect-drizzle-proxy) lets you supply the transport for a database Drizzle supports; it does not add one. A third-party database starts from one of the shipped families instead: [drizzle-duckdb](https://www.npmjs.com/package/@duckdbfan/drizzle-duckdb), "based on drizzle's Postgres client", subclasses Drizzle's `PgDialect`, `PgSession`, and `PgDatabase`. **A new database implements Kysely's dialect interface; in Drizzle it extends a database Drizzle already ships.**

## Migrate from Drizzle to Kysely one query at a time

A move from Drizzle to Kysely does not have to happen at once, or at all for the schema.

### Can Kysely and Drizzle be used together?

Yes. Keep [Drizzle Kit](https://orm.drizzle.team/docs/migrations) for schema and migrations, and write queries in Kysely against the same database:

1. [Generate Kysely's types](/docs/generating-types) from the migrated database, in the migration step or in CI.
2. Give both clients the same `pg` pool: `drizzle({ client: pool })` and `new PostgresDialect({ pool })`.
3. Start with a query that shared functions extend, that traverses JSON, or that declares its types through `sql<T>`. Move it, inspect `.compile()`, and compare rows, nulls, ordering, and empty results.
4. Keep each transaction on one client. The two share a pool, not a transaction.

On Drizzle 0.45.4, the `Kyselify` type from `drizzle-orm/kysely` also derives Kysely's table types from the Drizzle table objects, with no generation step. 1.0.0-rc.5 no longer ships that export, so generated types are the path that survives the upgrade.

## Other practical considerations

<details>
<summary>Schema, migrations, and value conversion</summary>

One Drizzle declaration is the source for types and for migrations: Drizzle Kit diffs the tables and generates SQL migrations, and can push to or pull from a database. It also runs [Drizzle Studio](https://orm.drizzle.team/docs/drizzle-kit-studio), a database browser, and [drizzle-seed](https://orm.drizzle.team/docs/seed-overview) fills the declared tables with deterministic test data. Kysely has no migration generator. Its [migrations](/docs/migrations) are written by hand through the schema builder or any migration tool, and its types are declared or [generated](/docs/generating-types) from the database, so a migration applied without regenerating them is drift the compiler cannot see.

It also makes the database the source of truth: Kysely queries a schema that another service or migration tool owns, with nothing declared a second time. Drizzle reaches one through [`drizzle-kit pull`](https://orm.drizzle.team/docs/drizzle-kit-pull), which writes the declarations to keep in step with it.

Drizzle's columns also convert values, through date modes and [custom types](https://orm.drizzle.team/docs/custom-types), and the same tables derive validation schemas for [Zod](https://orm.drizzle.team/docs/zod), [Valibot](https://orm.drizzle.team/docs/valibot), [TypeBox](https://orm.drizzle.team/docs/typebox), and [ArkType](https://orm.drizzle.team/docs/arktype). Kysely does neither: its types describe what the driver returns, conversion belongs to the driver's configuration or a plugin, and a validator is written separately.

</details>

<details>
<summary>Drivers and runtimes</summary>

Both have zero runtime dependencies and run on Node.js, Deno, Bun, and edge runtimes. Drizzle ships its driver adapters, including Neon, PlanetScale, Cloudflare D1, libSQL, and Bun SQL, inside one package. Kysely's core dialects are PostgreSQL, MySQL, MSSQL, SQLite, and PGlite; the rest are [organization and community dialects](/docs/dialects), installed separately. Drizzle also has a [batch API](https://orm.drizzle.team/docs/batch-api) for its Neon HTTP, libSQL, and D1 drivers; Kysely has none.

</details>

<details>
<summary>Type-checking cost</summary>

Both libraries compute their types in the compiler, so both add to type-checking and editor time as the schema and its queries grow. Kysely's checks are part of that cost: every call carries the tables in scope and parses its reference strings. A deeply composed query can reach TypeScript's instantiation limit, and [`$assertType`](/docs/recipes/excessively-deep-types) simplifies the type at that point. Neither library's cost is measured here; `tsc --extendedDiagnostics` on your own schema is the number that counts.

</details>

## Choosing Drizzle or Kysely

### Is Drizzle an ORM or a query builder?

**Both: Drizzle is a SQL-style query builder with an ORM's schema and relational layer around it.** This page compares that builder with Kysely, which is a query builder only. [SQL query builder vs ORM](/docs/comparisons/query-builder-vs-orm) covers model APIs like Drizzle's relational queries.

### Is Kysely faster than Drizzle?

**The database cannot tell them apart: both send one parameterized statement, and [performance belongs to the statement](/docs/comparisons/query-builder-vs-raw-sql#performance-belongs-to-the-statement-not-the-authoring-tool).** Drizzle describes itself as "a thin TypeScript layer on top of SQL with almost 0 overhead", and its [prepared statements](https://orm.drizzle.team/docs/perf-queries) build the SQL once, with `sql.placeholder()` for the values that change, and reuse it on every call. Kysely has no placeholder API: it builds the statement on each call, and [`.compile()`](/docs/recipes/splitting-query-building-and-execution) splits building from execution only for a query whose values are fixed. Neither library is benchmarked here.

### Which is easier for a coding agent to use?

**Both ship examples where an agent reads them; Kysely also checks what the agent writes, and its own examples.** An agent works by editing and running the compiler again, and the checks on this page sit inside that loop: a wrong reference or a misspelled JSON key is a compile error it can read and fix without a database, where Drizzle gives it a failed run or a silent `null`. Each library documents its methods in the type declarations it installs, and each site publishes an `llms.txt`. Kysely's inline examples are [type-checked in CI](/docs/integrations/llms) against the release they ship with; nothing in Drizzle's repository checks its own.

### Why use Kysely instead of Drizzle?

**Choose Kysely when queries are composed, shared, and changed, and you want TypeScript to check each change.** That means references checked against the query in every clause; JSON and CASE expressions whose types are inferred instead of declared, and filtered aggregates and windows built instead of templated; builders that behave like values, shared without rebuilding and executed only when asked; and a public query tree that plugins and dialects build on. Its types come from the database itself, so it fits a schema that another tool, service, or team migrates.

### When is Drizzle the better choice?

**Keep Drizzle when one TypeScript declaration should drive types, migrations, validation schemas, and relational reads, and its queries are mostly written whole, in one place.** It is at its best while a project is still finding its shape, when getting from an idea to a working schema and queries quickly matters most. Drizzle Kit can stay either way, and Kysely can run beside it for the queries that are composed.

**Both put SQL first; Drizzle types the columns a query uses, and Kysely types the query.**
