# SQL query builder vs raw SQL in TypeScript

Kysely updates the result type as you change a selection, join, or optional field. SQL-template clients compose fragments too; their result annotations or schemas describe the output separately.

Checked **Kysely 0.29.7**, **Postgres.js 3.4.9**, and **Slonik 49.11.0** across the same **48 PostgreSQL fixture cases**, plus pagination and binding checks. [Reproduce the checks](https://github.com/kysely-org/kysely/tree/master/site/scripts/comparison-checks/postgres).

## The selected name changes: does the type follow?

Assume configured clients and an `asset` table with string `id` and `name` columns. Rename the selected `name` to `label`. The stale Postgres.js annotation compiles:

```ts
const rows = await sql<{ id: string; name: string }[]>`
  select id, name as label from asset order by id limit 1
`

rows[0]?.name // Typed as a string property; actually undefined.
```

Kysely infers the new field:

```ts
const rows = await db
  .selectFrom('asset')
  .select(['id', 'name as label'])
  .orderBy('id')
  .limit(1)
  .execute()

rows[0]?.label // string | undefined
rows[0]?.name // TypeScript error
```

With Slonik, a result schema that still requires `name` compiles, then fails configured runtime validation. Kysely rejects the stale caller before execution.

## One endpoint, three implementations

List an owner's assets with optional album/prefix filters and optional nested tags. Sort by name and ID; limit to 50.

Assume one row per album/asset pair. The prefix filter uses SQL LIKE-pattern semantics.

<details>
<summary>Database types and request options</summary>

```ts
interface Database {
  asset: { id: string; name: string; owner_id: string }
  album_asset: { album_id: string; asset_id: string }
  asset_tag: { asset_id: string; tag_id: string }
  tag: { id: string; name: string }
}
```

Request options:

```ts
type AssetOptions = {
  ownerId: string
  albumId?: string
  includeTags: boolean
  namePrefix?: string
}
```

</details>

### Kysely: compose clauses and infer the result

Share the filters:

```ts
function matchingAssets(options: AssetOptions) {
  return db
    .selectFrom('asset')
    .where('asset.owner_id', '=', options.ownerId)
    .$if(options.albumId !== undefined, (qb) =>
      qb
        .innerJoin('album_asset', 'album_asset.asset_id', 'asset.id')
        .where('album_asset.album_id', '=', options.albumId!),
    )
    .$if(options.namePrefix !== undefined, (qb) =>
      qb.where('asset.name', 'like', options.namePrefix! + '%'),
    )
}
```

Add fields and optional tags, using `jsonArrayFrom` from `kysely/helpers/postgres`:

```ts
function assetListing(options: AssetOptions) {
  return matchingAssets(options)
    .select(['asset.id', 'asset.name'])
    .$if(options.includeTags, (qb) =>
      qb.select((eb) =>
        jsonArrayFrom(
          eb
            .selectFrom('asset_tag')
            .innerJoin('tag', 'tag.id', 'asset_tag.tag_id')
            .select(['tag.id', 'tag.name'])
            .whereRef('asset_tag.asset_id', '=', 'asset.id')
            .orderBy('tag.name'),
        ).as('tags'),
      ),
    )
    .orderBy('asset.name')
    .orderBy('asset.id')
    .limit(50)
}
```

Execute with `await assetListing(options).execute()`. Inferred: `{ id: string; name: string; tags?: { id: string; name: string }[] }[]`.

Requested tags use `[]` when none exist; unrequested tags omit the key and subquery. See [conditional selects](/docs/recipes/conditional-selects) and [nested relations](/docs/recipes/relations).

### Postgres.js: fragments plus a result annotation

With a configured Postgres.js client named `sql`:

<details>
<summary>The equivalent Postgres.js implementation</summary>

```ts
type AssetRow = {
  id: string
  name: string
  tags?: { id: string; name: string }[]
}

function findAssetsWithPostgres(options: AssetOptions) {
  const albumJoin =
    options.albumId !== undefined
      ? sql`inner join album_asset on album_asset.asset_id = asset.id`
      : sql``
  const albumFilter =
    options.albumId !== undefined
      ? sql`and album_asset.album_id = ${options.albumId}`
      : sql``
  const nameFilter =
    options.namePrefix !== undefined
      ? sql`and asset.name like ${options.namePrefix + '%'}`
      : sql``
  const tagsSelection = options.includeTags
    ? sql`, coalesce((
        select json_agg(tag_rows)
        from (
          select tag.id, tag.name
          from asset_tag
          inner join tag on tag.id = asset_tag.tag_id
          where asset_tag.asset_id = asset.id
          order by tag.name
        ) as tag_rows
      ), '[]'::json) as tags`
    : sql``

  return sql<AssetRow[]>`
    select asset.id, asset.name ${tagsSelection}
    from asset ${albumJoin}
    where asset.owner_id = ${options.ownerId}
      ${albumFilter} ${nameFilter}
    order by asset.name, asset.id
    limit 50
  `
}
```

</details>

Postgres.js [supports conditional fragments](https://github.com/porsager/postgres#building-queries) and binds values. `AssetRow` does not update when the SQL selection changes.

### Slonik: fragments plus a result schema

Slonik composes fragments and takes its result type from `sql.type`. A configured [parser interceptor](https://github.com/gajus/slonik#result-parser-interceptor) also validates returned rows.

<details>
<summary>The equivalent Slonik implementation</summary>

Assume a configured pool named `slonik`, `sql` imported as `slonikSql`, and `z` imported from Zod:

```ts
const assetRowSchema = z.object({
  id: z.string(),
  name: z.string(),
  tags: z.array(z.object({ id: z.string(), name: z.string() })).optional(),
})

function findAssetsWithSlonik(options: AssetOptions) {
  const albumJoin =
    options.albumId !== undefined
      ? slonikSql.fragment`inner join album_asset on album_asset.asset_id = asset.id`
      : slonikSql.fragment``
  const albumFilter =
    options.albumId !== undefined
      ? slonikSql.fragment`and album_asset.album_id = ${options.albumId}`
      : slonikSql.fragment``
  const nameFilter =
    options.namePrefix !== undefined
      ? slonikSql.fragment`and asset.name like ${options.namePrefix + '%'}`
      : slonikSql.fragment``
  const tagsSelection = options.includeTags
    ? slonikSql.fragment`, coalesce((
        select json_agg(tag_rows)
        from (
          select tag.id, tag.name
          from asset_tag
          inner join tag on tag.id = asset_tag.tag_id
          where asset_tag.asset_id = asset.id
          order by tag.name
        ) as tag_rows
      ), '[]'::json) as tags`
    : slonikSql.fragment``

  return slonik.any(slonikSql.type(assetRowSchema)`
    select asset.id, asset.name ${tagsSelection}
    from asset ${albumJoin}
    where asset.owner_id = ${options.ownerId}
      ${albumFilter} ${nameFilter}
    order by asset.name, asset.id
    limit 50
  `)
}
```

</details>

The schema is separately maintained. A required-field mismatch fails at runtime, rather than changing the expected type from the SQL.

## How the endpoint changes

| Change                        | Kysely                                               | Postgres.js                                           | Slonik with result validation                                |
| ----------------------------- | ---------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------ |
| Add a conditional album join  | Builder checks the added table in the query context. | Compose join and filter fragments.                    | Compose join and filter fragments.                           |
| Add optional nested tags      | Infer the nested row shape and optional property.    | Update the result annotation as well as the SQL.      | Update the result schema as well as the SQL.                 |
| Rename a selected field       | Callers see the new inferred field.                  | A stale annotation can still compile.                 | A stale required-field schema fails when a row is validated. |
| Reuse the filters for a count | Extend the shared builder with a count selection.    | Share SQL fragments and supply the count result type. | Share SQL fragments and supply the count result schema.      |

## What SafeQL can check

[SafeQL](https://safeql.dev/) can check supported SQL calls against PostgreSQL schema; annotations are not the only checking option.

Its [Postgres.js support matrix](https://safeql.dev/compatibility/postgres.js.html#support-matrix) supports direct nested fragments but excludes conditional fragment selection, including the ternaries above.

Kysely checks builder composition through TypeScript. Raw `sql<T>` still asserts its result; SafeQL's [Kysely integration](https://safeql.dev/compatibility/kysely.html) checks supported raw forms.

## Choosing a workflow

Use embedded SQL when its fragment API and checking tools cover your queries. Slonik's runtime result validation can be independently useful.

Use Kysely for optional joins/selections and shared typed building blocks, with [raw expressions](/docs/recipes/raw-sql) where useful.

Start with an endpoint that repeats filters or maintains a result annotation separately from its SQL. Move that query, inspect `.compile()`, and compare rows, ordering, and optional fields before switching the caller. [Get started](/docs/getting-started).
