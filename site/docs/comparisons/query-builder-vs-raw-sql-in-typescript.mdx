# SQL query builder vs raw SQL in TypeScript

**A SQL query builder constructs SQL through a programming language API; raw SQL expresses the statement directly.** Both let you choose the tables, joins, subqueries, and expressions the database executes. A builder can preserve that control while making queries easier to extend and reuse in application code.

**The difference becomes useful as queries change.** A list gains optional filters, an export reuses those filters with different selections, and a detail view adds nested data. Kysely lets those queries share typed building blocks, checking references and inferring each result as you extend them.

**Raw SQL can be checked, typed, and parameterized.** It can live in a TypeScript string, a tagged template, or a SQL file imported through a checker or generator. The choice is how to compose changing queries, keep their types accurate, and avoid building a SQL construction layer of your own.

## What is the difference between a query builder and raw SQL?

With raw SQL, you write the statement and pass values separately, through placeholders or a client's tagged template. With a builder, you call operations such as `selectFrom`, `where`, and `innerJoin`; the library compiles those operations into SQL and parameters.

<SqlQueryWorkflows />

Plain SQL strings with separate parameters fit here too: drivers such as node-postgres execute statements without a template or generator. Parameter binding protects values; a handwritten result annotation alone does not check the statement. The groups above show the additional interfaces and checking tools teams can choose.

### SQL in TypeScript and SQL in SQL files

SQL embedded in TypeScript stays close to application control flow. A tagged template can add a predicate or select a fragment conditionally while binding its values. [Postgres.js documents these composition helpers](https://github.com/porsager/postgres#building-queries); [SafeQL](https://safeql.dev/) can add schema-aware checks to supported calls.

SQL-file workflows keep statements in a SQL editor and connect them to application code:

- [PgTyped](https://pgtyped.dev/docs/) analyzes annotated queries against PostgreSQL and generates typed query objects. It supports queries in both SQL and TypeScript files.
- [Prisma TypedSQL](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/typedsql) generates query functions and parameter/result types from SQL files, executed through Prisma Client.
- [sqlc](https://docs.sqlc.dev/) analyzes schema and query inputs to generate application calls. TypeScript output uses a [language plugin](https://github.com/sqlc-dev/sqlc-gen-typescript), whose documented status is early access.

### When a SQL file becomes SQLish

**A `.sql` extension does not guarantee that the file is executable database SQL.** Parameter declarations, expansions, macros, and custom type syntax can turn it into input for a particular tool. You still learn an API, but its syntax lives inside the SQL file.

The pressure grows when a statement needs optional filters, variable-length inputs, conditional selections, or reusable pieces. One route keeps a fixed SQL structure and expresses choices through nullable parameters and `CASE`. Another adds tool-specific syntax or moves query assembly into application code. The latter routes introduce a translation layer between the source you edit and the statement the database executes.

For example, [sqlc's parameter macros](https://docs.sqlc.dev/en/stable/reference/macros.html) name inputs and control their nullability:

```sql title="Tool input: sqlc parameter macros"
select id, name
from asset
where owner_id = sqlc.arg(owner_id)
  and (sqlc.narg(name_prefix)::text is null
    or name like sqlc.narg(name_prefix) || '%');
```

For PostgreSQL, the tool replaces those macros with parameter placeholders. The database-facing form is:

```sql title="Database SQL after parameter expansion"
select id, name
from asset
where owner_id = $1
  and ($2::text is null or name like $2 || '%');
```

**The tool input cannot simply be pasted into TablePlus and executed as ordinary PostgreSQL SQL.** It needs macro expansion and parameter values. A plain parameterized statement also needs values supplied, but it does not additionally need a tool's macro language translated. PgTyped's [parameter expansions and required-parameter syntax](https://pgtyped.dev/docs/sql-file) also add a layer beyond database SQL. Metadata stored only in SQL comments, such as the TypedSQL annotations below, does not itself change the executable syntax.

This affects the SQL-console workflow: inspect the emitted statement, supply its parameters, tune it, then carry the change back into the tool's source syntax. Kysely also requires compilation before its output runs in a SQL console. Its case is that this translation layer provides checked composition, reusable queries, and inferred results as requirements change. The useful comparison is what each translation layer buys: a SQL-file workflow can also have an abstraction to learn and translate.

**Type safety is not exclusive to builders.** Changing a selected alias can update a SQL-file caller's type too, once its query code is regenerated. The stronger builder argument is that callers can keep extending a shared query while its references and result shape stay connected.

A builder has an API to learn alongside SQL. A self-contained statement may read best as SQL; a complex recursive query can still be a good SQL file. For model mapping and related writes, see [query builders vs ORMs](/docs/comparisons/query-builder-vs-orm).

## Composing optional filters, joins, and selections

An asset list starts with an owner's assets, sorted by name and ID and limited to 50. Assume configured clients and an `asset` table with string `id`, `name`, and `owner_id` columns.

With Postgres.js, the statement is close to the SQL you would run in a console:

```ts
const rows = await sql<{ id: string; name: string }[]>`
  select id, name from asset
  where owner_id = ${ownerId}
  order by name, id
  limit 50
`
```

With Kysely, the same operations use its builder API:

```ts
const rows = await db
  .selectFrom('asset')
  .select(['id', 'name'])
  .where('owner_id', '=', ownerId)
  .orderBy('name')
  .orderBy('id')
  .limit(50)
  .execute()
// Inferred: { id: string; name: string }[]
```

Both handle this query well. Now the list needs an optional album filter and name prefix. The album filter adds both a join and a predicate; other requests should omit them.

Assume a `Kysely<Database>` instance named `db`, one row per album/asset pair, and PostgreSQL. The prefix filter uses SQL LIKE-pattern semantics: `%` and `_` in the input remain wildcards.

### Add the optional join and filters

Put the shared query in a function. Kysely's `$if` applies each addition when its condition is true:

```ts
function matchingAssets(options: AssetOptions) {
  return db
    .selectFrom('asset')
    .where('asset.owner_id', '=', options.ownerId)
    .$if(options.albumId !== undefined, (qb) =>
      qb
        .innerJoin('album_asset', 'album_asset.asset_id', 'asset.id')
        .where('album_asset.album_id', '=', options.albumId!),
    )
    .$if(options.namePrefix !== undefined, (qb) =>
      qb.where('asset.name', 'like', options.namePrefix! + '%'),
    )
}
```

The join and its album predicate are composed together. Inside that branch, Kysely checks references against the added table. The non-null assertions correspond to the conditions outside the callbacks.

Postgres.js can express the same condition with fragments:

```ts
const albumJoin =
  options.albumId !== undefined
    ? sql`inner join album_asset on album_asset.asset_id = asset.id`
    : sql``
const albumFilter =
  options.albumId !== undefined
    ? sql`and album_asset.album_id = ${options.albumId}`
    : sql``
```

Those fragments compose the SQL, but their TypeScript types alone do not establish whether `album_asset` is present wherever its columns are referenced. SQL-aware tools can add checks; their supported composition forms matter too.

### When SQL helpers become a homemade query builder

A conditional fragment is small. Then several endpoints need it, so you extract a helper. Another helper adds a join, another chooses fields, and another combines filters and pagination. Soon your code needs rules for aliases, conjunctions, parentheses, parameter ordering, and which selections belong to which result type.

**At that point, you are building a query builder.** Its API might return strings, fragments, or objects such as `{ joins, predicates, selections }`, but it owns the same job: composing valid statements from reusable parts. A typed fragment alone does not prove that a predicate's table was joined, an alias is in scope, or a caller's result annotation matches the assembled selection.

That layer needs tests across its combinations and types that preserve those relationships. If it falls back to string concatenation or raw interpolation, it also owns the SQL injection boundary. These responsibilities are easy to accumulate one helper at a time, without budgeting for a library's testing and maintenance.

**An established builder lets the team spend that effort on its queries.** Kysely supplies the composition operations, parameter handling, and reference/result types; your helpers can return its unfinished builders. SQL-template libraries already solve important parts of this problem too. The question is how much additional query construction your application must maintain on top of them.

### Reuse the filters for a list, count, and export

The list chooses its fields and pagination after calling `matchingAssets`:

```ts
const assets = await matchingAssets(options)
  .select(['asset.id', 'asset.name'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .limit(50)
  .execute()
// Inferred: { id: string; name: string }[]
```

The total reuses the same filters without inheriting the list's limit:

```ts
function assetCount(options: AssetOptions) {
  return matchingAssets(options).select((eb) =>
    eb.cast<number>(eb.fn.countAll(), 'integer').as('count'),
  )
}
```

Execute with `await assetCount(options).executeTakeFirstOrThrow()`. PostgreSQL's integer cast makes the count a JavaScript number within the PostgreSQL integer range.

An export adds `owner_id` and omits pagination:

```ts
const exportedAssets = await matchingAssets(options)
  .select(['asset.id', 'asset.name', 'asset.owner_id'])
  .orderBy('asset.name')
  .orderBy('asset.id')
  .execute()
// Inferred: { id: string; name: string; owner_id: string }[]
```

**Each consumer chooses its result and clauses while sharing the filtering rules.** Kysely's builders are immutable, so extending one does not change another. A SQL-template implementation can share the join and filter fragments too; its result annotations or schemas still need to describe each consumer separately.

### Express the same filters in a SQL file

A SQL-file implementation can keep the statement fixed and let parameters enable its filters. This Prisma TypedSQL example uses `exists` for album membership:

```sql title="findAssets.sql"
-- @param {String} $1:ownerId
-- @param {String} $2:albumId?
-- @param {String} $3:namePrefix?
select asset.id, asset.name
from asset
where asset.owner_id = $1
  and ($2::text is null or exists (
    select 1 from album_asset
    where album_asset.asset_id = asset.id
      and album_asset.album_id = $2
  ))
  and ($3::text is null or asset.name like $3 || '%')
order by asset.name, asset.id
limit 50;
```

After `prisma generate --sql`, call the generated `findAssets` through `prisma.$queryRawTyped`, passing the owner ID and nullable filter parameters. The inputs and returned columns are typed from the SQL. Other SQL-file tools have their own parameter syntax and analysis workflow.

A count needs the same matching rules with a different selection and no limit:

-- @param {String} $2:albumId?
-- @param {String} $3:namePrefix?

**Checking both statements does not establish that their filtering rules agree.** A new visibility rule must reach the list, count, and export. In these separate files, that means changing each statement. A shared database view or function can centralize the rule too, with its own schema and deployment lifecycle. Tools with preprocessing or composition facilities offer other options.

Kysely keeps this reuse in an ordinary TypeScript function whose returned builder each consumer can extend. SQL files keep each complete statement together, though tool-specific syntax may need expansion before the database can analyze it. The maintenance question is where the common rule lives as more outputs need it.

### Add optional nested tags

The list now needs tags when requested. Add a correlated JSON subquery using `jsonArrayFrom` from `kysely/helpers/postgres`:

```ts
function assetListing(options: AssetOptions) {
  return matchingAssets(options)
    .select(['asset.id', 'asset.name'])
    .$if(options.includeTags, (qb) =>
      qb.select((eb) =>
        jsonArrayFrom(
          eb
            .selectFrom('asset_tag')
            .innerJoin('tag', 'tag.id', 'asset_tag.tag_id')
            .select(['tag.id', 'tag.name'])
            .whereRef('asset_tag.asset_id', '=', 'asset.id')
            .orderBy('tag.name'),
        ).as('tags'),
      ),
    )
    .orderBy('asset.name')
    .orderBy('asset.id')
    .limit(50)
}
```

Execute with `await assetListing(options).execute()`. Inferred: `{ id: string; name: string; tags?: { id: string; name: string }[] }[]`.

Requested tags use `[]` when none exist; unrequested tags omit the key and subquery. The nested query keeps the outer result at one row per asset. Kysely checks the inner table references and their reference to the outer `asset`, then carries the nested result shape into `tags`.

The optional property reflects the runtime condition: callers must account for tags being absent. See [conditional selects](/docs/recipes/conditional-selects) and [nested relations](/docs/recipes/relations).

### Optional output from SQL files

A fixed statement can return a tags column and use `CASE` to choose its value. That still selects the column: returning `null` differs from omitting `tags`. Either contract can be useful. To preserve this example's absent-key contract directly in SQL, use a second statement that selects tags and choose between the typed calls in TypeScript. An application mapper could remove the key instead.

<details>
<summary>The SQL file with tags and its application wrapper</summary>

```sql title="findAssetsWithTags.sql"
-- @param {String} $1:ownerId
-- @param {String} $2:albumId?
-- @param {String} $3:namePrefix?
select asset.id, asset.name,
  coalesce((
    select json_agg(tag_rows)
    from (
      select tag.id, tag.name
      from asset_tag
      inner join tag on tag.id = asset_tag.tag_id
      where asset_tag.asset_id = asset.id
      order by tag.name
    ) as tag_rows
  ), '[]'::json) as tags
from asset
where asset.owner_id = $1
  and ($2::text is null or exists (
    select 1 from album_asset
    where album_asset.asset_id = asset.id
      and album_asset.album_id = $2
  ))
  and ($3::text is null or asset.name like $3 || '%')
order by asset.name, asset.id
limit 50;
```

Assume generated query functions and a configured Prisma Client named `prisma`:

```ts
function findAssetsFromFiles(options: AssetOptions) {
  if (options.includeTags) {
    return prisma.$queryRawTyped(
      findAssetsWithTags(
        options.ownerId,
        options.albumId ?? null,
        options.namePrefix ?? null,
      ),
    )
  }
  return prisma.$queryRawTyped(
    findAssets(
      options.ownerId,
      options.albumId ?? null,
      options.namePrefix ?? null,
    ),
  )
}
```

</details>

The tested Prisma TypedSQL 7.10.1 output describes `tags` as `JsonValue | null`; Kysely infers the nested `{ id: string; name: string }[]`. That is a finding about this tool and version. SQL-file tools should be assessed individually.

[PgTyped documents nullable predicates instead of query composition](https://pgtyped.dev/docs/dynamic-queries). [TypedSQL documents its dynamic-column limit](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/typedsql#dynamic-sql-queries-with-dynamic-columns). [sqlc macros](https://docs.sqlc.dev/en/stable/reference/macros.html) add tool-specific preprocessing. Supporting parameters or macros does not by itself mean an application can extend a checked statement with an arbitrary join or selection.

## Error feedback and the query-editing loop

**Finding one error per database round trip makes a long query expensive to correct.** A database generally stops processing a statement when it encounters an error. PostgreSQL can return a [message, hint, and position in the submitted SQL string](https://www.postgresql.org/docs/current/protocol-error-fields.html). That points to the reported problem, not a complete set of mistakes in the query.

With the asset schema above, this statement has three independent errors:

```sql
select id, nmae
from asset
where owner_id = 42
  and label like 'F%'
order by name;
```

PostgreSQL first reports the missing `nmae` column. Correct it to `name` and resubmit: comparing the text `owner_id` to an integer now fails. Change `42` to a string and resubmit: the missing `label` column is reported next. These successive diagnostics were checked against PostgreSQL.

In a long query assembled from fragments, the reported position refers to the assembled SQL. You must also trace that position back to the fragment or helper that produced it. Each correction can mean rebuilding the statement and asking the database again.

Kysely can report these mistakes in one TypeScript check, at the operations that introduce them:

```ts
db.selectFrom('asset')
  .where('asset.owner_id', '=', 42) // Error: owner_id requires a string.
  .where('asset.label', 'like', 'F%') // Error: label is not a column.
  .select(['asset.id', 'asset.nmae']) // Error: nmae is not a column.
  .orderBy('asset.name')
```

TypeScript 6 and 7 both report all three operations in this example. **Feedback arrives while editing, without submitting the query or reaching the application path that executes it.** Completion also offers the tables, columns, and operations available at the current point in the builder.

Raw-SQL tools can move feedback earlier too. SafeQL supplies editor diagnostics for supported SQL. A generator can reject an invalid statement before application execution. Assess the actual feedback loop: where an error appears, how many problems a check exposes, and whether the checked form covers your conditional query. Kysely's compiler checks still do not replace database validation: raw expressions, stale schema declarations, constraints, and SQL rules beyond its types can fail at the database.

### Query changes can require generation even when the schema is stable

**A query changes more often than its tables need to.** Adding a selection, changing a filter, or renaming an alias can require refreshing generated query code even when the database schema has been unchanged for months. A watcher can automate that step, but the generator and its schema inputs still participate in the editing loop.

| Tool                                                                                      | Schema input for checking                                                  | What happens after a query edit?                                                                                |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Kysely                                                                                    | Existing TypeScript database declarations.                                 | TypeScript checks the builder and re-infers its result; no per-query generation or live connection is required. |
| [PgTyped](https://pgtyped.dev/docs/cli)                                                   | A running PostgreSQL database.                                             | Run generation, manually or in watch mode, to refresh typed query code.                                         |
| [Prisma TypedSQL](https://www.prisma.io/docs/orm/v7/prisma-client/using-raw-sql/typedsql) | A database connection for generation.                                      | Refresh query functions with `prisma generate --sql`, optionally in watch mode.                                 |
| [sqlc](https://docs.sqlc.dev/en/stable/howto/generate.html)                               | Local schema/query files by default; database-backed analysis is optional. | Run generation to refresh application code, including TypeScript plugin output.                                 |

**Kysely separates schema declarations from individual query inference.** Adding `owner_id` to the export above uses the existing declarations; the result changes immediately through TypeScript. If the schema itself changes, update or regenerate those declarations. A live database is still needed to test runtime behavior, but it does not need to participate in every query's static check.

### Database support for checking varies

**Executing SQL and analyzing its result types are different capabilities.** A client's supported databases do not establish which databases its checker supports, what metadata it can obtain, or how precisely it can infer a result. Preparing or describing a statement can obtain metadata without executing the application query, but the available information differs by engine.

<details>
<summary>Checking without query execution: PostgreSQL, MySQL, SQLite, and SQL Server</summary>

| Database                                                                                                                                    | Metadata available without executing the application query                                                                      | Limits to account for                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| [PostgreSQL](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-FLOW-EXT-QUERY)                                            | The extended protocol's statement `Describe` returns parameter and result-column metadata before `Execute`.                     | That metadata alone does not describe every TypeScript-level property, such as a nested JSON object's shape.                                 |
| [MySQL](https://dev.mysql.com/doc/c-api/8.4/en/mysql-stmt-result-metadata.html)                                                             | Prepared-statement result metadata is available after preparation and before execution.                                         | Pre-execution types are determined by the optimizer; the documented types after execution can differ.                                        |
| [SQLite](https://www.sqlite.org/c3ref/column_decltype.html)                                                                                 | A statement can be prepared without stepping through its results; declared-type metadata is available for direct table columns. | The declared-type API returns no type for an expression or subquery. Dynamic value types and computed expressions need additional analysis.  |
| [SQL Server](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/sp-describe-first-result-set-transact-sql) | `sp_describe_first_result_set` statically analyzes a batch's first result set.                                                  | Some constructs cannot be described, including statements using temporary tables; control flow can also prevent a usable result description. |

</details>

This is a summary of database facilities, not a claim that every checker uses them. Tools can supplement metadata with catalog queries or their own SQL analysis, as sqlc does. For a particular tool, check its engine and driver support, parameter inference, nullability, expression types, and JSON handling. Also establish whether checking prepares statements, analyzes them locally, or executes anything; database access alone does not mean the application query runs.

Kysely's builder checks use TypeScript database declarations across its supported dialects, without depending on a server's describe API for each query edit. Those checks still depend on accurate declarations and do not prove that a statement will succeed against the database.

## Keeping SQL and TypeScript result types in sync

**Type inference connects the query you change to the callers that use it.** Both Kysely and SQL-aware raw-SQL tools can do this. The following example shows the narrower difference between inferred results and a handwritten annotation.

Rename the selected `name` to `label`. Without an additional SQL checker, a stale Postgres.js annotation still compiles:

```ts
const rows = await sql<{ id: string; name: string }[]>`
  select id, name as label from asset order by id limit 1
`

rows[0]?.name // Typed as a string property; actually undefined.
```

Kysely infers the new field:

```ts
const rows = await db
  .selectFrom('asset')
  .select(['id', 'name as label'])
  .orderBy('id')
  .limit(1)
  .execute()

rows[0]?.label // string | undefined
rows[0]?.name // TypeScript error
```

With Slonik alone, a result schema that still requires `name` compiles, then fails configured runtime validation when an incompatible row is returned. The schema supplies the caller's type; it does not establish that the SQL selects the required fields. Kysely rejects the stale caller before execution.

### Can raw SQL be type-safe?

Yes, but a typed template is not necessarily a statically checked query. Distinguish the guarantees:

- **A handwritten result type is a typed assumption.** TypeScript checks callers against that type, but does not establish that the SQL returns it. Supplying `sql<AssetRow[]>` does not itself check the SQL-to-result contract.
- **A validation schema can verify returned rows at runtime.** The caller's static type can be inferred from the schema, but the SQL string is not thereby checked against it. With validation enabled, incompatible rows cause a failure after execution, when they are validated.
- **SQL-aware analysis can check the statement before execution.** It analyzes supported SQL against a schema and can compare its output with the supplied result contract. This is additional checking, beyond providing a type argument or a validation schema.

[SafeQL](https://safeql.dev/) checks supported SQL calls against PostgreSQL. Its [Postgres.js support matrix](https://safeql.dev/compatibility/postgres.js.html#support-matrix) supports direct nested fragments but excludes conditional fragment selection, including the ternaries in the asset example. Check the supported forms against the queries you actually need to compose.

For supported forms, [SafeQL's Slonik integration](https://safeql.dev/compatibility/slonik.html#zod-schema-validation) can also compare the SQL output with a supplied Zod schema during linting. That supplies the pre-execution check that attaching a schema alone does not provide.

Kysely checks its builder composition through TypeScript. That depends on accurate database declarations and the driver's runtime value mapping. It does not validate returned rows or convert values to match the declared types. [Generating database types](/docs/generating-types) helps keep declarations aligned with the schema; runtime validation can still be useful at application boundaries.

Raw `sql<T>` expressions in Kysely also declare their result type explicitly. SafeQL's [Kysely integration](https://safeql.dev/compatibility/kysely.html) checks supported raw forms. These capabilities belong to particular tools: result inference is not a guarantee every query builder provides.

### Slonik: fragments plus a result schema

Slonik composes fragments and takes its result type from `sql.type`. A configured [parser interceptor](https://github.com/gajus/slonik#result-parser-interceptor) also validates returned rows.

Assume a configured pool named `slonik`, `sql` imported as `slonikSql`, and `z` imported from Zod:

```ts

  id: z.string(),
  name: z.string(),
  tags: z.array(z.object({ id: z.string(), name: z.string() })).optional(),
})

function findAssetsWithSlonik(options: AssetOptions) {
  const albumJoin =
    options.albumId !== undefined
      ? slonikSql.fragment`inner join album_asset on album_asset.asset_id = asset.id`
      : slonikSql.fragment``
  const albumFilter =
    options.albumId !== undefined
      ? slonikSql.fragment`and album_asset.album_id = ${options.albumId}`
      : slonikSql.fragment``
  const nameFilter =
    options.namePrefix !== undefined
      ? slonikSql.fragment`and asset.name like ${options.namePrefix + '%'}`
      : slonikSql.fragment``
  const tagsSelection = options.includeTags
    ? slonikSql.fragment`, coalesce((
        select json_agg(tag_rows)
        from (
          select tag.id, tag.name
          from asset_tag
          inner join tag on tag.id = asset_tag.tag_id
          where asset_tag.asset_id = asset.id
          order by tag.name
        ) as tag_rows
      ), '[]'::json) as tags`
    : slonikSql.fragment``

  return slonik.any(slonikSql.type(assetRowSchema)`
    select asset.id, asset.name ${tagsSelection}
    from asset ${albumJoin}
    where asset.owner_id = ${options.ownerId}
      ${albumFilter} ${nameFilter}
    order by asset.name, asset.id
    limit 50
  `)
}
```

The schema is separately maintained. TypeScript takes the result type from that schema without comparing it to the SQL. With the configured runtime validator, a required-field mismatch fails when an incompatible row is returned; it does not make the query a compile-time error. Additional SQL-aware analysis is needed to check that contract before execution.

### What changes with each requirement?

| Change                              | Kysely                                          | SQL templates in TypeScript                                                      | Typed SQL files                                                                         |
| ----------------------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Add a conditional album join        | Check references in the extended query context. | Compose fragments; checking depends on the client and analyzer.                  | Use parameter-controlled logic, separate statements, or supported composition features. |
| Reuse filters for a count or export | Extend the shared builder; infer each result.   | Share fragments and maintain annotations/schemas, or use supported SQL analysis. | Keep statements aligned or centralize the rule through a shared SQL abstraction.        |
| Add optional nested tags            | Infer the nested shape and optional property.   | Compose the selection; result checking depends on tooling.                       | Choose output variants or a fixed nullable column; JSON inference varies by tool.       |
| Rename a selected field             | Callers see the new inferred field.             | A plain annotation can drift; a SQL-aware checker can detect the change.         | Analysis or regeneration updates the caller's result type.                              |

**The builder keeps references, composition, and inferred results connected through each extension.** Typed raw SQL can provide strong whole-statement checks. Slonik's configured runtime validation checks actual returned values, which Kysely's inference does not do.

## SQL injection and the composition layer

**Parameter binding protects values; the code assembling SQL still needs a safe boundary for syntax.** Drivers with placeholders, tagged-template clients, and typed SQL-file calls can all bind parameters. The examples pass owner IDs, album IDs, and prefixes as values. Plain clients such as [node-postgres support parameterized queries](https://node-postgres.com/features/queries#parameterized-query) too.

The risk appears when a homemade composition layer starts treating input as SQL: concatenating filter values, interpolating an `ORDER BY` string, or passing request data to a raw/unsafe escape hatch. Using a safe tagged template elsewhere in the query does not protect that inserted text.

For example, the [Postgres.js unsafe escape hatch](https://github.com/porsager/postgres#unsafe-raw-string-queries) bypasses the protection for the ordering expression:

```ts
// Unsafe if orderBy comes from a request:
const rows = await sql`
  select id, name from asset
  where owner_id = ${ownerId}
  order by ${sql.unsafe(orderBy)}
`
```

The owner ID remains bound, but `orderBy` is SQL text. A raw string constructor can introduce the same vulnerability when combining otherwise safe fragments. Tests must cover these boundaries as well as ordinary query combinations.

**A maintained builder reduces the amount of SQL construction your application owns.** Kysely binds predicate values and provides operations for identifiers, expressions, and ordering. Dynamic sort choices should still come from a validated set of supported columns and directions. An unchecked cast does not validate request input, and Kysely's own raw SQL escape hatches can also be misused.

SQL-file workflows can avoid much of this assembly by keeping a fixed statement and passing only values, including parameter-controlled filters and sorting. Their checked calls are a strong option when that structure fits. The builder's advantage over an ad hoc SQL layer is making safe composition part of an established API instead of a growing collection of string-handling conventions.

## Generated SQL and performance

**Compare statements and execution plans to assess database performance.** A builder does not inherently make a query faster, and handwritten SQL does not inherently produce a better plan. The joins, predicates, indexes, row counts, and database behavior still matter.

Kysely exposes its statement and parameters before execution:

```ts
const compiled = assetListing(options).compile()
// compiled.sql: SQL text with placeholders
// compiled.parameters: bound values
```

Use [`.compile()`](/docs/recipes/splitting-query-building-and-execution) to inspect whether a request includes the album join or tags subquery. Compare plans and timings against representative data, and measure application overhead separately if it matters to your workload. The fixture checks above establish equivalent results, not a speed ranking.

Both approaches let you rewrite a join as a subquery or adjust the ordering. With Kysely, that edit can stay in the shared builder and update the inferred result for its callers.

## Using raw SQL inside a query builder

A builder can cover most of a statement while SQL expresses one local operation. For example, add a lowercase name to the shared query:

```ts
import { sql as kyselySql } from 'kysely'

const normalizedAssets = await matchingAssets(options)
  .select(['asset.id', 'asset.name'])
  .select((eb) =>
    kyselySql<string>`lower(${eb.ref('asset.name')})`.as('normalized_name'),
  )
  .execute()
// Inferred: { id: string; name: string; normalized_name: string }[]
```

The builder still checks the `asset.name` reference and composes the filters. The SQL fragment's `string` result is an explicit declaration; Kysely does not check the `lower(...)` grammar or verify that result type. See [raw expressions](/docs/recipes/raw-sql) and the [SQL template API](https://kysely-org.github.io/kysely-apidoc/interfaces/Sql.html).

This lets you adopt a builder for the parts that benefit from composition and keep SQL where it reads best. Using an expression does not require turning the whole statement into a raw query.

## Query composition in production

The same approach extends beyond the asset illustration:

- [Immich](https://github.com/immich-app/immich/blob/0733cc10ee7a0c8ebd5d37b1804b5c28944b7cdd/server/src/repositories/asset.repository.ts#L570-L624) composes optional relation selections and a lateral subquery for stacked assets. Different requests extend the query with different data.
- [Open Collective](https://github.com/opencollective/opencollective-api/blob/0a59b37c8b33574ee8d9d9a586d5a19506fd5921/server/graphql/v2/query/collection/OrdersCollectionQuery.ts#L780-L826) conditionally adds currency conversion through a correlated exchange-rate lookup. A request option changes the selected expression.
- [Docmost](https://github.com/docmost/docmost/blob/7bef7b1a00d31991f009865ec14c8d06540eb1f0/apps/server/src/database/repos/page/page-permission.repo.ts#L325-L373) composes recursive ancestors for page restrictions. Traversal, joins, and filtering use the same builder interface as simpler queries.

Raw SQL can express these operations too. The builder's value is carrying checked references and results through the application code that composes them.

## When to choose raw SQL or Kysely

**Choose raw SQL when writing the statement directly is the clearest workflow for your team.** SQL templates suit queries composed close to application code; typed SQL files suit complete statements reviewed and edited as SQL. Runtime schemas, SQL-aware checkers, and generated query APIs can provide strong guarantees. Complexity alone does not require a builder.

For a SQL-file tool, try the next conditional join, selection, and shared filter. Check how much stays database SQL, what becomes tool-specific syntax, and what must be translated to reproduce a request in TablePlus. A file that looks like SQL can still carry a substantial query-construction API.

Also make a few deliberate mistakes and change a selection without changing the schema. Compare how many edit/check cycles it takes to correct the query, whether a database connection is required, and when the caller's result type updates.

**Choose Kysely when queries keep acquiring variations and you want their references and results checked as you compose them.** Shared filters, different list/export selections, optional joins, and nested results are recurring opportunities to reuse a builder. Before building another layer of SQL helpers, account for the composition rules, injection boundaries, tests, and types that layer would need. Kysely lets the application reuse an established implementation of that work.

You still need SQL knowledge and must learn Kysely's API. A builder does not choose indexes, prove that a join preserves row counts, or validate actual returned values. In return, the statement's structure and its TypeScript result can evolve together, with local SQL expressions where useful.

Start with one endpoint that repeats filters or maintains a result annotation separately from its SQL. Move that query, inspect `.compile()`, and compare rows, ordering, pagination, and optional fields before switching the caller. Other queries can continue using their existing clients.
